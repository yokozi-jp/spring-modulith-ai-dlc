# 性能テストの目標値

スループットはベースラインの実績か想定ユースケースから求め、安全係数を掛けて負荷の状態ごとに決める。
オンライン処理の処理時間は、機能の分類ごとの目標値とパーセンタイルの順守率で定め、平均値と最大値を判定に使わない。
リソース使用率は構成要素ごとに上限と下限の範囲で定め、CPUとメモリを必ず含める。

用語は[性能テストの種別と用語](terminology.md)に従う。

## スループット

次の順で根拠を選ぶ。

1. 稼働中の類似システムやリプレース前のシステムがあれば、アクセスログから通常時とピーク時のスループットを求める。
   将来の増加を見込む場合は、その倍率で補正する。
2. ベースラインがなければ、負荷諸元の利用者数と想定ユースケースから求める。

求めた値には、時間枠の中のアクセスの波を見込んで安全係数（2倍か3倍）を掛ける。

```text
利用者 10,000人、1回の利用で17リクエスト、業務時間8時間、ピークは1時間に集中する場合
通常時 = 10,000 × 17 / (8 × 3600) ≒ 5.9 RPS → 安全係数2で 11.8 RPS
ピーク時 = 10,000 × 17 / 3600 ≒ 47.2 RPS → 安全係数2で 94.4 RPS
```

## オンライン処理の処理時間

### 目標値の根拠

稼働中の類似システムやリプレース前のシステムがあれば、その処理時間を測ってベースラインにし、それより悪化させない。
ベースラインがなければ、業界の指標を参考にする。
web.devはTTFB（リクエストからレスポンスの最初のバイトが届くまでの時間）を800ミリ秒未満で良好としており、一般的なオンライン処理の目標の起点に使える。

### 機能の分類と負荷の状態

目標値は一律にせず、機能の重要度と特性で分ける。

- **コア**：決済や注文登録のように業務の中心となる機能。
  厳しい目標値にする。
- **標準**：通常の機能。
- **管理**：レポート出力や管理画面の検索。
  緩い目標値を許容する。

さらに、取得系と更新系で目標値を分ける。
負荷の状態による違いは、目標値ではなく順守率で表す。

### 順守率

順守率はパーセンタイルで定める。
平均値は極端に速い処理と遅い処理の両方に引きずられて大多数の体験を表さず、最大値は制御できない一回の遅延で全体を不合格にするためである。

次を初期値とし、システムの特性に合わせて調整する。

| 分類 | 操作   | 目標値 | 通常時 | ピーク時 | 縮退時 |
| :--- | :----- | -----: | :----- | :------- | :----- |
| コア | 取得系 | 300 ms | p95    | p90      | p80    |
| コア | 更新系 | 500 ms | p95    | p90      | p80    |
| 標準 | 取得系 | 500 ms | p90    | p80      | p60    |
| 標準 | 更新系 | 800 ms | p90    | p80      | p60    |
| 管理 | 取得系 | 800 ms | p90    | p80      | p60    |
| 管理 | 更新系 | 800 ms | p90    | p80      | p60    |

目標値は関係者の期待値になり、後から変えにくい。
計画の時点で見通しの不確実性が大きい場合は、目標値に幅（例：300ミリ秒から800ミリ秒）を持たせる。

## 定時処理の処理時間

定時処理の目標値は、処理に使える時間帯（バッチウィンドウ）から決める。
後続の処理や業務の開始時刻から上限（例：0時から4時の4時間以内）を決め、順守率はパーセンタイルではなく、ウィンドウへの収まり方で定める。

- **コア**：失敗しても再実行できる余裕を残して収まる。
- **標準**：所定の時間に収まる。

## リソース使用率

処理時間とスループットが目標を満たしても、リソースが常にひっ迫していれば小さな負荷変動で性能が劣化する。
逆に、ピーク時にも大きく余っていれば構成が過剰である。
そのため、リソース使用率は範囲で定める。

- 構成要素（アプリケーション、DB、キャッシュなど）ごとに定める。
- CPU使用率とメモリ使用率は必ず定める。
- ストレージが自動で拡張される構成では、ディスク使用率を目標値にしなくてよい。

次を初期値にする。

- **上限**：通常時は50%から60%、ピーク時でも80%以下。
- **下限**：ピーク時に30%から40%以上。
  下回る場合は構成の縮小を検討する。

オートスケールを構成する場合は、スケールアウトとスケールインの閾値を目標値と整合させる。
整合しないと、目標値に達する前にスケールアウトする、または大きく余ってもスケールインしない。

起動して処理を終えたら停止する一回限りの処理（ワンショットの定時処理）は、外からの突発的な負荷を受けないため、CPUを使い切ることを目標にする。
使い切れない場合は、並列度の不足かI/O待ちを疑う。
