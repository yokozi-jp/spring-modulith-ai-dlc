# ロングランテスト

本番相当のデータ量に、通常時の同時アクセスを長時間かけ続け、性能を保って安定して動くかを確かめる。
シナリオはラッシュテストのものを使い、定時処理を通常のスケジュールで裏で動かす。
実行時間は、システムが連続して稼働する期間を網羅する長さにする。

用語は[性能テストの種別と用語](terminology.md)に従う。

## 完了基準

### 性能指標値の評価

- 処理時間とスループットが、全期間で目標値を満たす。
- リソース使用率が目標の範囲に収まる。
- 長時間の稼働による意図しないエラーが発生していない。
- 非同期処理がある場合は、メッセージが滞留せずに処理されている。

### 安定性と信頼性の評価

- メモリをはじめ、リソース使用率に右肩上がりの推移がない。
- DBの接続とアプリケーションのスレッドが枯渇せず、解放されている。
- GCの頻度と実行時間が極端に増えていない。

判定の方法は[性能テストのレポーティング](reporting.md)のロングランテストの節に従う。

## 対象シナリオ

[ラッシュテスト](rush-test.md)のシナリオをそのまま使う。
ピーク時の負荷をかけ続ける必要はなく、通常時の負荷でよい。
定時処理は通常のスケジュールどおりに、テストの裏で動かす。

## 実行時間

実行時間は、システムが停止または再起動せずに稼働する期間を網羅する長さにする。
夜間に停止するシステムなら、日中の稼働時間を網羅すれば一周期のリソースの推移を確かめられる。

常時稼働するシステムでは、どれだけ延ばしても数か月単位で表面化するリークを否定できない。
ローリングアップデートやブルーグリーンデプロイメントで各インスタンスを定期的に入れ替える運用をとる場合は、その入れ替えの間隔（日次なら24時間）を実行時間にする。
入れ替えの運用をとらない場合は、実行時間の根拠を計画書に書いて関係者と合意する。

デプロイ方式は[APIのデプロイ環境とデプロイ方式](../web-api/deployment-environments.md)に従う。

## Full GCが発生しない場合

テスト全体を通してFull GCが一度も発生しない場合は、Old領域の増加がリークによるものか、単にFull GCが走っていないだけかを切り分けられない。
次のどれかでFull GCを複数回発生させ、その状態で推移を確かめる。

- テスト時間を延ばす。
- 負荷を上げる。
- ヒープを意図的に小さくした追加の検証を行う。
