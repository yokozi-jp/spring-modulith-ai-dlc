# ラッシュテスト

本番相当のデータ量に、負荷の状態ごとの同時アクセスをかけ、業務シナリオ単位で性能を測る。
同時アクセスで生じる共有リソースの競合と枯渇を解消し、目標を満たす最小の構成を導く。
構成の比較では、一度に一つの構成要素だけを変える。

用語は[性能テストの種別と用語](terminology.md)に従う。

## 完了基準

### 性能指標値の評価

- 定義したすべての負荷の状態で、処理時間とスループットが目標値を満たす。
- リソース使用率が目標の範囲（上限と下限）に収まる。
- 同時アクセスによる意図しないエラーが発生していない。
- 非同期処理がある場合は、メッセージが滞留せずに処理されている。
- 機能ごとの処理時間の内訳が分かり、[ボリュームテスト](volume-test.md)との差が特定できている。
- その差（同時アクセスによる劣化）を分析し、対応した。

### キャパシティプランニング

- 目標を満たす最小の構成（台数とスペック）を、比較の結果として示した。

## 対象シナリオ

全ユースケースを網羅せず、できるだけ少ないシナリオにする。
機能単体の最適化はボリュームテストで済ませているためである。
シナリオはスループットの目標値を求めたときと同じ根拠で組み立てる。

- アクセスログから目標値を求めた場合は、アクセスログで呼ばれている主要な機能からシナリオを作る。
- 想定ユースケースから目標値を求めた場合は、同じユースケースからシナリオを作る。

オンライン処理と定時処理が同時に動く時間帯がある場合は、ピーク時の負荷をかけている間に、その定時処理を裏で実行する。

## 最適な構成の導き方

- 目標を満たし、リソースに余裕がある場合は、より低いスペックで再び試し、問題なければ低いスペックを選ぶ。
- 水平にスケールできる場合は、低いスペックのノードを多く並べる構成（例：2vCPU/8GBを2台より1vCPU/4GBを4台）を先に検討する。
  ノード障害時の処理能力の低下が小さく、負荷に合わせて細かくスケールできるためである。

ただし、ノードを小さくしすぎると次の理由で費用と性能がかえって悪化するため、釣り合いを見極める。

- OSやランタイムが固定で消費するリソースの割合が大きくなる。
- マルチスレッドの並行処理の利点を受けにくい。
- コンテナイメージの取得の費用、IPアドレスの消費、ノード単位のライセンス費用がノード数に比例して増える。

## 比較の進め方

構成要素を同時に変えると、どの変更が効いたかを切り分けられない。
アプリケーションとDBからなる場合は、次の順に一つずつ決める。

1. DBを十分なスペックで固定し、アプリケーションの最小構成を探る。
2. 決めたアプリケーションの構成で固定し、DBの最小構成を探る。

DBのサイズは、[PostgreSQLの性能対策と負荷分散](../database/postgresql-performance.md)に従い小さく始めて必要なサイズまで上げる。
本番の接続プールの大きさは、[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)に従い、このテストの結果とDBの接続予算から決める。

構成が決まったら、その構成で[ボリュームテスト](volume-test.md)を再実行する。
