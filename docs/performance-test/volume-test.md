# ボリュームテスト

本番相当のデータ量で、同時アクセスなしに機能を逐次実行し、機能単位の処理時間を測ってチューニングする。
対象は原則として全機能とし、典型的なリクエストと最も重いリクエストの両方を試す。
オンライン処理は1機能あたり100回以上試行し、定時処理は1回実行する。

用語は[性能テストの種別と用語](terminology.md)に従う。

## 完了基準

- 対象機能の処理時間（定時処理で目標を定めた場合はスループットも）が目標値を満たす。
- 機能ごとに処理時間の内訳（ネットワーク、アプリケーション、DB、外部呼び出し）が分かっている。
- 問題のある箇所と改善の見込める箇所を分析し、チューニング（SQLの実行計画の確認、インデックスの最適化など）を行った。

## 対象機能

原則として全機能を対象にする。
後続のラッシュテストとロングランテストは主要なシナリオに絞るため、全機能を網羅できるのはこのテストだけである。

人員と期間が足りない場合に限り、次の機能を除外してよい。

- 業務上の重要度と利用頻度が低い機能（管理者向けの機能など）。
- 処理が単純な機能（単一テーブルへの主キーでのアクセスだけの機能など）。

## リクエストのパターン

リクエストパラメータに応じてSQLが変わる機能（検索APIなど）は、全パターンを網羅しなくてよいが、次の両方を試す。

- 通常指定される条件での実行。
- 最も重い条件での実行（全件検索、広い範囲の検索、深いページングなど）。

一覧のページングは[ADR-013](../adr/ADR-013-standardize-http-api-contracts.md)のカーソル方式を既定とする。
offset方式を例外として使う画面では、最後のページに相当する深いoffsetも試す。

## 画面を含めるか

業務システムでは、画面の描画よりAPIのレスポンスタイムが支配的であるため、APIに絞って行う。
複雑な処理を持つ画面がある場合や、画面を含めたターンアラウンドタイムが要件になる場合は、[画面の性能テスト](frontend-performance-test.md)も行う。

## 試行回数

- **オンライン処理**：テストをスクリプト化して負荷ツールから繰り返し実行し、100回以上を基準にする。
- **定時処理**：1回の実行とする。
  実行の費用が大きく、統計的な揺らぎよりデータ量の影響が支配的なためである。

試行回数が足りているかは、相対標準誤差（標準偏差 ÷ √試行回数 ÷ 平均値）が1%以下かで判断する。
ばらつきの大きい機能ほど、多くの試行回数が要る。

## 構成が変わった後の再実行

[ラッシュテスト](rush-test.md)で最終的な構成（スペックと台数）が決まり、ボリュームテストの時点と構成が異なる場合は、その構成でボリュームテストを再実行する。
構成によって機能単位の処理時間も変わるためである。
