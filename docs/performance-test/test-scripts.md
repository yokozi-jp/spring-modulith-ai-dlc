# 負荷ツールとテストスクリプト

負荷ツールは、スクリプトをコードとしてGitで管理でき、想定する最大の負荷を生成できるものを選ぶ。
スクリプトは事前処理、本体、事後処理に分け、本体だけを計測する。
スクリプトは何度でも再実行できるように作り、思考時間とパラメータの分散で現実の負荷に近づける。

## 負荷ツールの選び方

組織やプロジェクトで使い慣れたツールがあれば、それを使う。
新しく選ぶ場合は、次を満たすものを選ぶ。

- シナリオをコードで書き、通常のソースコードと同じくGitで管理してレビューできる。
- CIから実行できる。
- 少ない計算資源で、想定する最大の負荷（目標のRPSの数倍）を生成できる。
- 到達レート（RPS）を指定して段階的に負荷を上げられる。
- 対象のプロトコル（HTTP、WebSocket、gRPCなど）に対応する。

採用する負荷ツールは、後から変えにくい技術の選定であるため、[ADR の運用ルール](../adr/conventions.md)に従いADRに記録する。

## スクリプトの構成

スクリプトは次の三つに分ける。
多くの負荷ツールは、この区分を表す仕組み（setup と teardown など）を持つ。

- **事前処理**：認証によるトークンの取得、対象データのIDの採番、ランダムなパラメータの生成など、本体の準備。
  結果を本体の各リクエストから参照できるようにする。
- **本体**：負荷をかける処理。
  計測の対象はここに含め、事前処理と事後処理の時間を計測に混ぜない。
  シナリオで複数の機能を順に呼ぶ場合は、一覧で取得したIDを詳細の取得に渡すような機能間の関係を正しく表す。
- **事後処理**：テスト中に作ったデータの削除や認証セッションの解除。

## 繰り返し実行

チューニングでは修正と再テストを何度も繰り返し、構成を変えるたびに全テストを再実行するため、すべてのテストをスクリプトにし、手作業なしで再実行できる状態を保つ。
「2回目以降は失敗する」スクリプトを作らない。

- 一意制約のある列には、リクエストごとに一意な値（UUID、仮想ユーザーの番号と繰り返しの番号の組など）を生成して入れる。
- テスト中に作ったデータは、事後処理か専用のクリーンアップスクリプトで消す。
  ロングランテストのように大量のデータを投入し続けるテストでは、テスト後にDBをリストアしてもよい。

## 現実的な負荷パターン

- **思考時間**：利用者は操作のあいだに考えて入力する時間を取る。
  シナリオのリクエストのあいだに思考時間を挟み、連続して投げ続ける過剰な負荷にしない。
- **パラメータの分散**：同じパラメータを繰り返すと、キャッシュに過剰にヒットして実態より良い結果になる。
  検索条件や参照するIDを分散させ、本番のアクセスログがあればその分布に合わせる。
