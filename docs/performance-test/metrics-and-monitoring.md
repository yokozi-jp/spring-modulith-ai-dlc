# 性能テストのメトリクスと監視

インフラ、DB、JVMのメトリクスと、エンドポイントごとのRate、Errors、Durationを集める。
メトリクスは本番の監視設計を基にし、性能テストに必要な詳細を足す。
監視ツールは本番と同じものを使い、処理時間の内訳は分散トレーシングで調べる。

メトリクスは性能テストのためだけでなく、本来は運用監視の設計で決めるものである。
監視設計がなければ、本番運用を見据えてこの時点で決める。

## インフラのメトリクス

- CPU使用率、メモリ使用率、ネットワークI/O、ディスクI/O。
- 使うマネージドサービスが提供するメトリクスから、DBの接続数、コミットの待ち時間、ディスクI/Oの待ち時間、スワップの使用量、コンテナのタスク数とタスクごとのCPUとメモリなど、性能に関わるものを選ぶ。

## DBのメトリクス

- **`pg_stat_statements`**：SQLごとの実行回数、累積実行時間、平均実行時間。
  スロークエリの分析に使う。
- **`pg_stat_activity`**：実行中のプロセスの状態。
  待機イベントの分析と、接続の滞留の検知に使う。

DBの監視項目は[PostgreSQLの監視](../database/postgresql-monitoring.md)に従う。

## JVMのメトリクス

- **ヒープの使用量**：Young領域とOld領域を分けて測る。
  Young領域が急増してMinor GCが頻発する場合は、一時オブジェクトの過剰な生成を疑う。
  Old領域が増え続け、Full GCの後も十分に回収されない場合は、メモリリークを疑う。
- **Metaspaceの使用量**：長時間の稼働で増え続けないかを確かめる。
- **GCの実行時間と回数**：アプリケーションが停止する時間と頻度を、Minor GCとFull GCに分けて測る。
- **スレッド**：スレッドの数と状態（RUNNABLE、BLOCKED、WAITINGなど）を測る。
  仮想スレッドを使うため、プラットフォームスレッドの数と、JFRによる仮想スレッドのpinningも確かめる（[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)）。
- **接続プール**：HikariCPの使用中の接続数、接続を待つリクエスト数、接続の取得にかかる時間。
  仮想スレッドでは同時処理数が接続プールで制限されるため、スループットが伸びない原因の切り分けに使う。

## サービスのメトリクス

利用者に直結するメトリクスとして、エンドポイントごとに次の三つ（REDメトリクス）を集める。

- **Rate**：単位時間あたりのリクエスト数。
  想定した負荷がかかっているかを確かめる。
- **Errors**：リクエストの失敗率。
  負荷の増加でエラーが増えていないかを確かめる。
- **Duration**：リクエストの処理時間。
  エンドツーエンドだけでなく、DBのクエリや外部APIの呼び出しなど、スパンごとの時間まで分けて見られるようにする。

インフラのメトリクスだけでは、CPU使用率の上昇は分かっても、どのエンドポイントのどのクエリが原因かまでは追えない。
エンドポイントとスパンの単位の内訳は、OpenTelemetryの分散トレーシングで取得する。

## 監視ツール

性能テストでは、本番運用で使う監視ツールをそのまま使う。
性能テストで得た平常値と注意すべき閾値を、本番の監視設計へそのまま引き継げるためである。

バックエンドはログ、トレース、メトリクスをOpenTelemetryで送信するため、性能テストでもその経路で集める。
記録してよい値と保持は[可観測性データの規約](../observability/conventions.md)に従う。
