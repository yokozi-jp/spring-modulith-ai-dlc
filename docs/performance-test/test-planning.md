# 性能テストの計画

性能テストは計画、準備、実行、チューニング、レポーティングの順に進め、必要に応じて前の工程へ戻る。
目的、範囲、システム諸元、目標値、実施順序、環境、スケジュールを計画書に定め、関係者と合意する。
テストはボリューム、ラッシュ、ロングラン、ストレスの順に、本番と同等の構成を占有した環境で行う。

用語は[性能テストの種別と用語](terminology.md)に従う。

## 工程

1. **テスト計画**：目的、目標値、完了基準、スケジュールを決める。
2. **テスト準備**：環境、データ、テストスクリプトを用意する。
3. **テスト実行**：負荷をかけて性能指標を測る。
4. **チューニング**：ボトルネックを特定して改善し、再テストする。
5. **レポーティング**：結果を評価し、本番運用に耐えるか、将来の拡張性、残存リスクを報告する。

各項目は「決まっているか」と「関係者と合意できているか」の両方で確認する。

## 目的

次の目的から、プロジェクトで重視するものを選び、優先順位を付ける。
すべてを選ぶ必要はない。

- **性能指標値の評価**：処理時間とスループットが目標値を満たすかを確かめる。
- **安定性と信頼性の評価**：長時間の稼働や急な負荷変動でも、性能を保って動き続けるかを確かめる。
- **スケーラビリティの評価**：どの構成要素を増強すれば性能が上がるかを確かめる。
- **キャパシティプランニング**：性能要件を満たす、費用対効果のよい構成（スペックと台数）を導く。

目的とテスト種別は、次のように対応させる。

| 目的                     | ボリューム | ラッシュ | ロングラン | ストレス | スパイク |
| :----------------------- | :--------: | :------: | :--------: | :------: | :------: |
| 性能指標値の評価         |     ✅     |    ✅    |     ✅     |          |          |
| 安定性と信頼性の評価     |            |          |     ✅     |    ✅    |    ✅    |
| スケーラビリティの評価   |            |          |            |    ✅    |    ✅    |
| キャパシティプランニング |            |    ✅    |            |    ✅    |          |

## テスト対象の範囲

何を含めないかを明示する。

- 外部システムと共通基盤は、原則として範囲に含めず、スタブで置き換える。
  無断で負荷をかけると、攻撃とみなされる、高額な利用料が発生する、相手を停止させるおそれがあるためである。
  連携先が性能テスト用の環境を提供し、合意できた場合に限り含める。
- バックエンドのテストでは、負荷ツールからAPIへ直接リクエストを送り、画面を含めない。
  画面を含めた体感速度が要件になる場合は、[画面の性能テスト](frontend-performance-test.md)として別の範囲で行う。
- 独立して動く複数のサブシステムからなる場合は、サブシステムごとに試してから全体へ広げてよい。

スタブの作り方は[性能テスト環境の準備](test-environment.md)に従う。

## システム諸元

性能テストの前提となる数値を、テストデータとシナリオに落とせる粒度で定義する。

- **データ諸元**：DBの全テーブルのレコード件数と、扱うファイルの最大サイズと平均サイズ。
  稼働から何年後（例：3年後、5年後）の状態を基準にするかを決める。
  稼働中のシステムがあれば、本番のデータ量と増加率から求める。
- **負荷諸元**：同時利用ユーザー数や同時アクセス数。
  通常時、ピーク時、スパイク時など、負荷の状態ごとに見積もる。

目標値の決め方は[性能テストの目標値](performance-targets.md)に従う。

## 実施順序

テストは次の順序で行う。
観点をデータ量、データ量と同時アクセス、データ量と同時アクセスと稼働時間の順に増やすことで、前のテストで機能単体の問題を除いてから、同時アクセスと長時間稼働の問題を調べられる。

|                | ボリューム | ラッシュ | ロングラン     | ストレス     |
| :------------- | :--------- | :------- | :------------- | :----------- |
| データ量       | 本番相当   | 本番相当 | 本番相当       | 本番相当以上 |
| 同時アクセス数 | 1          | 本番相当 | 本番相当       | 本番相当以上 |
| 継続時間       | なし       | 数十分   | 数時間から数日 | 数十分       |
| テストの単位   | 機能       | シナリオ | シナリオ       | シナリオ     |

スパイク性のあるシステムでは、ストレステストと合わせてスパイクテストを計画する。
各テストの完了基準は、目的に対応させて計画書に定める。

## テスト環境

本番環境と同等の構成を持つ環境（検証環境など）で行う。
リリース前の新規システムでは、本番環境をそのまま使ってもよい。

- **環境を占有する**：限界に近い負荷や長時間の稼働をかけるため、他のテストと環境を共有しない。
  午前と午後のような時間帯での使い分けも避ける。
  システムテストの期間中は、他のテストとの環境の割り当てを全体計画で調整する。
- **台数とスペックを落とさない**：スペックを半分にして結果を2倍に見積もる方法は使わない。
  従量課金の環境では、テスト期間だけ本番と同じ構成を立ち上げる。
- **複数の環境を用意する**：性能テストは並行して実行しにくいため、用意できるなら複数の環境を確保して作業を並行させる。

環境は[ADR-008](../adr/ADR-008-single-application-yaml-external-config.md)に従い設定を外部から注入して構築し、本番との差を設定値だけにする。
環境の識別は[APIのデプロイ環境とデプロイ方式](../web-api/deployment-environments.md)に従う。

## スケジュール

性能の課題は原因の特定に時間がかかり、アーキテクチャの見直しに及ぶこともあるため、余裕を持たせ、プロジェクトの早い時期から計画と準備に着手する。
100から200機能の新規システムでは、数名のチームで2か月程度を目安にする。

- 計画と準備（環境、データ、スクリプト）の工数は、実行とチューニングと同じかそれ以上に見積もる。
- 相互に影響するテスト（例：ストレステストとロングランテスト）は同時に実行しない。
- 長時間のテストは、中断すると再実行で同じ日数を失うため、再実行の分のバッファを持つ。
- 次の特性を持つシステムでは、バッファを厚くする。
  - リプレースではない新規システムである。
  - オンライン処理、非同期処理、定時処理が混在する。
  - マルチテナント構成で、他テナントの負荷による影響を考慮する必要がある。
  - 外部システムやSaaSとの連携点が多い。

## プレ性能検証

**プレ性能検証**：本番と同等の環境とシナリオをそろえる前に、最小限の構成で性能リスクの有無を見極める簡易な検証。

新しいアーキテクチャを採用する場合や、非常に大きなデータ量やアクセス量を想定する場合は、プロジェクトの早い時期に行う。
性能の問題が結合テストや総合テストで見つかると、データ構造やアーキテクチャの変更が必要になり、修正費用が大きくなるためである。

- **要件定義でアーキテクチャを決めるとき**：選んだ技術と構成で目標のスループットが出るかを確かめる。
- **開発の初期でコア機能を実装した直後**：最も複雑な業務ロジックや大量データを扱う処理が、単体で重すぎないかを確かめる。

検証する機能は、次の観点で絞る。

- **最重量**：データ量や計算量が多い機能。
  構成に対して大量と言える件数（数百万件など）から対象になる。
- **最頻出**：リクエストやトランザクションが多い機能。
- **最重要**：利用者が最も多い機能や、他の製品との差別化になる機能。

進め方は次のとおりにする。

- データ量だけは本番相当にする。
  データ量によってインデックスの効き方が変わり、少ないデータでの検証は結論を誤るためである。
- 接続数を1、5、10、20と段階的に増やし、処理時間が急に悪化する点だけを特定する。
  ロングランテストは行わない。
- 検証対象以外の構成要素は最小のスペックでよい。
