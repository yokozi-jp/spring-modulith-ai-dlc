# 性能テスト環境の準備

ログレベルは本番と同じにし、キャッシュとオートスケールはテスト種別ごとに決めた方針で有効または無効にする。
外部システムはスタブで置き換え、スタブは独立したプロセスとして動かす。
テストの前に負荷ツールを試運転し、目標の数倍の負荷を安定して生成できることを確かめる。

環境の構成は[性能テストの計画](test-planning.md)のテスト環境の節に従う。

## 負荷ツールの実行環境

負荷ツールを動かす計算資源を、テスト対象とは別に用意する。
負荷ツールが直接アクセスするDB、オブジェクトストレージ、キューへの経路と権限を設定する。

## ログレベル

ログレベルは本番と同じにし、[ログレベルの使い分けと切り替え](../observability/log-levels.md)に従いデプロイ環境では `INFO` 以上を出力する。
`DEBUG` を有効にしたまま測ると、本番で発生しないログ出力のI/Oが上乗せされるためである。

チューニングで原因を調べるために、特定の機能に絞って一時的にレベルを下げてよい。
その場合も、最終的な評価のための計測は本番と同じレベルに戻して行う。

## キャッシュ

キャッシュの扱いで結果が大きく変わるため、テスト種別ごとに方針を決めて適用する。

| キャッシュ                 | ボリューム       | ラッシュ | ロングラン | ストレス |
| :------------------------- | :--------------- | :------- | :--------- | :------- |
| HTTPキャッシュ             | 無効             | 有効     | 有効       | 有効     |
| アプリケーションキャッシュ | 目的に応じて判断 | 有効     | 有効       | 有効     |
| DBのバッファキャッシュ     | 有効             | 有効     | 有効       | 有効     |

- **HTTPキャッシュ**：入口やCDNが保持するAPIの応答。
  ボリュームテストでは機能そのものの処理時間を測るため無効にする。
  他のテストでは本番と同じ設定で有効にし、想定どおりのヒット率になっていることを確かめる。
- **アプリケーションキャッシュ**：プロセス内のキャッシュやRedisなどの分散キャッシュ。
  ボリュームテストでDBアクセスを含めた処理時間を測る場合は、無効にするか毎回クリアする。
  本番で常にヒットする設計の機能は、キャッシュが載った状態で測る。
- **DBのバッファキャッシュ**：`shared_buffers` など。
  本番では常に温まった状態であり、マネージドサービスでは無効化もクリアも難しいため、有効のままにする。

入口のキャッシュの設定は[入口とAPIの機能配置](../web-api/edge-responsibilities.md)に従う。

## オートスケール

オートスケールが動くと、どの構成で測った結果かが曖昧になる。
構成を固定して性能を評価するテストでは無効にし（または最小ノード数と最大ノード数を同じにし）、本番と同じ状態での安定性やオートスケールそのものを確かめるテストでは有効にする。

|                | ボリューム | ラッシュ | ロングラン | ストレス |
| :------------- | :--------- | :------- | :--------- | :------- |
| オートスケール | 無効       | 無効     | 有効       | 有効     |

## スタブ

外部システムをテストの範囲に含めない場合は、スタブで置き換える。

- スタブは、テスト対象とは独立したプロセスまたはサーバーとして動かす。
  接続待ちとネットワークI/Oを含めて、実際に近い負荷を再現できるためである。
- 工数や環境の制約で独立したプロセスにできず、対象機能への影響が小さい場合に限り、プログラム内でスタブのオブジェクトへ差し替えてよい。
- どちらの方式でも、設定可能な遅延を含む正常応答を、十分なスループットで返せるようにする。

外部連携の timeout と retry は、スタブに置き換えても[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)の値のまま動かす。

## メトリクスの収集

[性能テストのメトリクスと監視](metrics-and-monitoring.md)で定めたメトリクスを一か所で見られるダッシュボードを用意する。
ダッシュボードは本番の運用監視と共通にし、既にあればそれを基に性能テスト用のメトリクスを足す。
運用監視の基盤を並行して構築している場合は、担当者とスケジュールと分担を調整する。

- 性能テストの期間は、原因の特定にかかる工数を減らすことを優先し、クラウドの詳細モニタリングなど、標準より細かいメトリクスを集める設定を有効にする。
  本番で有効にするかは費用との兼ね合いで別に決める。
- PostgreSQLの `pg_stat_statements` と `auto_explain` は、[PostgreSQLのサーバー設定と拡張機能](../database/postgresql-server-configuration.md)に従い有効にしておく。
- 外部 client または native library を追加した後のテストでは、[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)に従いJFRを有効にして、仮想スレッドのpinningとHikariCPの接続待ち時間を確かめる。

## 負荷ツールの試運転

環境ができたら、テストの前に負荷ツールで疎通し、負荷ツール自体が計画した最大の負荷を安定して生成できるかを確かめる。

- 疎通にはヘルスチェックのような単純なAPIを使う。
- 到達レートを指定する方式で、目標のRPSの3倍程度まで段階的に上げる（例：50、100、150 RPSを各30秒保つ）。

次をすべて満たせば、負荷ツールは十分な負荷を生成できる。

- 目標のRPSに達しており、生成できずに落としたリクエストがない。
- 仮想ユーザー数に余裕がある。
- 負荷ツールを動かすマシンのCPU、メモリ、ファイル記述子に余裕がある。

単純なAPIでも目標の負荷に耐えられない場合は、アプリケーションより前にインフラかネットワークのボトルネックを疑い、原因を特定してから本番のテストへ進む。

## クラウド事業者への申請

- 負荷がサービスの上限（ロードバランサーの容量、同時実行数、APIのスロットリングなど）に達すると見込まれる場合は、実施の1週間から2週間前までに上限の緩和を申請する。
- 大量のトラフィックで意図的に過負荷にする、DDoSに相当するテストを行う場合は、事業者のテストポリシーを確認し、必要な申請を済ませる。
