# 性能テストのデータ

データ量はシステム諸元に合わせ、作成方法は本番データの安全性、実機能の利用可否、件数から選ぶ。
本番データは、秘匿性の高い情報を除外またはマスクできる仕組みがある場合か、秘匿性の高い情報を含まない場合に限って使う。
件数だけでなく、カーディナリティ、偏り、関連テーブルの件数比を本番に近づける。

データ量の基準は[性能テストの計画](test-planning.md)のシステム諸元の節に従う。

## 作成方法の選び方

次の順に判断する。

1. 本番データを安全に使えるなら、本番データをエクスポートして投入する。
2. 実機能でデータを生成できるなら、実機能を使う。
3. 件数が数万件までなら、`INSERT` で投入する。
4. 増幅の元になるデータがあるなら、手続き型SQLで増幅する。
5. どれにも当たらなければ、ファイルを作って一括で取り込む。

### 本番データ

本番データは再現度が最も高いが、個人情報や秘匿情報を含みうる。
次のどちらかに当たる場合に限って使う。

- 秘匿性の高い情報を除外またはマスクしてエクスポートし、安全に扱える仕組みがある。
- もともと秘匿性の高いデータを含まない。

本番データは開発用の可観測性の基盤へ投入しない（[可観測性データの規約](../observability/conventions.md)）。

### 実機能

定時処理がオンライン処理の参照するデータを作る場合や、オンライン処理の実行で履歴が作られる場合は、まず実機能を使えないかを検討する。
時間がかかりすぎる、データを柔軟に作れないなどの制約がある場合は、投入用の機能を作る。

### INSERT

アプリケーションやスクリプトから `INSERT` で投入する。
SQLの解析と通信の負担が大きいため、数万件までの小さなデータか、複雑なロジックでSQLを組み立てて正確に作りたい場合に使う。

### 手続き型SQL

PL/pgSQLや `generate_series` で、DBの中だけで大量の行を生成する。
通信の回数を抑えられるため、ある利用者のデータを主キーを変えながら100万人分に増やすような増幅に向く。

### ファイルの一括取り込み

CSVなどのファイルを用意し、`COPY` で一括で取り込む。
クライアント側のファイルを psql の `\copy` で送る方式は準備が要らないが、通信の帯域に依存し、接続が切れると中断する。
マネージドサービスがオブジェクトストレージからサーバー側で取り込む機能を提供する場合は、大きなファイルではそちらを使う。

取り込みの方法と目安の速度は[大量データの取り込み性能](../integration/interface-bulk-load.md)に従う。

## 大量データを投入するときの事前準備

数百万件以上を投入するときは、性能テスト環境に限り、次の準備で投入を速める。

- 投入の前に主キーを含むインデックスを外し、投入の後に作り直す。
  テストの前に、本番と同じインデックスがそろっていることを確かめる。
- 投入の間だけDBのインスタンスのサイズを上げ、投入後に元に戻す。
  書き込みのIOPSがボトルネックになりやすいためである。
- 投入の後に `ANALYZE` で統計情報を更新する。

物理テーブルには外部キー制約を作らないため（[PostgreSQLの制約とインデックス](../database/postgresql-constraints-and-indexes.md)）、外部キー制約の付け外しは要らない。
VACUUMは[PostgreSQLのサーバー設定と拡張機能](../database/postgresql-server-configuration.md)に従い自動バキュームに任せる。

## データのパターン

件数をそろえても分布が本番と異なると、インデックスが使われない、実行計画が本番と変わるなどで、正しく評価できない。

- **カーディナリティ**：列が取りうる値の種類の数。
  たとえば出身の都道府県なら47種類を作り、一部の地域だけで済ませない。
- **偏り**：特定の値へのデータの集中。
  インデックスやパーティションキーに使う列では特に、本番に近い偏りにする。
  都道府県なら人口の比率に合わせ、全件が一つの値に偏る分布も、すべてが均等な分布も避ける。
  日付を持つ履歴は、特定の日へ集中させない。
- **関連テーブルの件数比**：1対Nや多対多の関係にあるテーブルの件数の比。
  実態と離れると、結合で展開するデータ量やループの回数が変わり、実行計画が変わる。
