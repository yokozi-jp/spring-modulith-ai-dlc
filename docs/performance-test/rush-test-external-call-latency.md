# 外部呼び出しの遅延のラッシュテスト計画

決済代行の応答が遅いとき、決済の Listener が持つ接続の数と、注文の確定の応答時間を、到着率 λ を段階的に上げて測る。
測るのは、[基盤の品質特性シナリオ](../nfr/quality-attribute-scenarios.md#外部呼び出しの遅延)の2つの測定値である。
計画の書き方は[性能テストの計画](test-planning.md)、テスト種別の完了基準は[ラッシュテスト](rush-test.md)に従う。

## 目的

[ラッシュテスト](rush-test.md)の目的のうち、性能指標値の評価とキャパシティプランニングを選ぶ。

- **性能指標値の評価**：次の2つが、λ の段階ごとに成り立つかを確かめる。
  - (a) Listener が同時に持つ接続の数が C 以下で、C が P − R 以下である。
  - (b) λ が C / L 以下のとき、要求のスレッドが executor の空きを待たない。
- **キャパシティプランニング**：本番の接続プールの大きさ P と、Listener の同時実行の上限 C を決める入力にする。[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)に従い、本番の P はこのテストの結果と DB の接続予算から決める。

## 範囲

対象は、注文の確定 API（`POST /api/v1/orders/{orderId}/confirm`）から、注文の確定のイベントを受けた決済の Listener が決済代行を呼ぶまでである。
画面は含めない。
バックエンドは1インスタンスにする。

決済代行は、[性能テスト環境の準備](test-environment.md#スタブ)に従い、独立したプロセスの WireMock のスタブで置き換える。
スタブは遅延を設定できる。
外部呼び出しの timeout と retry は、スタブに置き換えても本番の値（応答の timeout 2秒、試行1回）のまま動かす。

再投入のジョブは無効にする。
有効にすると、最初の配信が executor の空きを待つ間に `wait-age` を過ぎた出版を重ねて再投入し、λ の段階の測定に混ざるためである。
再投入のジョブを有効にした状態は、このテストの範囲に含めない。

## 環境と構成

[性能テストの計画](test-planning.md#テスト環境)に従い、本番と同等の構成を占有した環境で行う。
DB の時間の上限は、アプリケーションの設定のまま使う。

構成は、一度に一つの構成要素だけを変える。

| 構成 | P   | C   | 狙い                                                                             |
| ---- | --- | --- | -------------------------------------------------------------------------------- |
| A    | 10  | 2   | 既定値で、測定値 (a) と (b) が成り立つかを確かめる。                             |
| B    | 10  | 5   | C だけを P / 2 まで上げ、待ちなしで捌ける上限が (P / 2) / L に動くかを確かめる。 |

## 負荷諸元

スタブの遅延を1.5秒にし、応答の timeout（2秒）より短くして、呼び出しを成功させる。
L_test は、負荷をかける前に Listener を1件ずつ流して測った、Listener 全体の処理時間にする。
処理時間は、スタブの遅延に DB の読み書きとコミットが加わるため、1.5秒より長くなる。
既定の L（3秒）の内訳のうち、接続の確立の1秒は、スタブの遅延では再現できない。
このテストが確かめるのは、L = 3秒での上限（0.67件/秒）そのものではなく、`λ × L ≤ C` の式が L_test で成り立つかである。
成り立てば、利用先は式に自分の L を入れて上限を求める。

λ は、構成ごとの C / L_test を基準にし、次の5段階で上げる。
到着率は一定に保つ。到着が偏ると、上限の手前でも待ちが出うるためである。

| 段階 | λ                    | 狙い                 |
| ---- | -------------------- | -------------------- |
| 1    | C / L_test の 0.5 倍 | 余裕のある状態       |
| 2    | C / L_test の 0.7 倍 | 上限の手前           |
| 3    | C / L_test の 1.1 倍 | 上限の直後           |
| 4    | C / L_test の 1.5 倍 | 待ちが増える状態     |
| 5    | C / L_test の 2.0 倍 | 待ちが増え続ける状態 |

各段階は10分続け、立ち上げの最初の2分を判定から除く。
段階の長さは計画の値であり、定常に達するまでの時間を見て調整する。

[負荷ツールとテストスクリプト](test-scripts.md)に従い、到達レート（RPS）を指定できる負荷ツールで、注文の確定の API を毎秒 λ 件の一定の率で呼ぶ。
事前処理で、段階の長さと λ から必要な数の注文を作る。
本体は注文の確定だけを計測する。
注文の確定を含む更新系の API は `Idempotency-Key` を要るので、リクエストごとに新しい値を付ける。

## 測定項目

| 項目                              | 取り方                                                                                                                                                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Listener が同時に持つ接続の数     | PostgreSQL の `pg_stat_activity` で、アプリケーションのロールの接続のうち、`state` が `idle in transaction` で `xact_start` から1秒を超えたものを、1秒ごとに数える。要求のトランザクションも文の合間に同じ状態になりうるため、1秒を超えたものだけを数える。 |
| 接続プールの使用中の数と待ち      | `hikaricp.connections.active` と `hikaricp.connections.pending`。同梱の Grafana のダッシュボードで見る。                                                                                                                                                    |
| 注文の確定の応答時間              | `http.server.request.duration` の p95。                                                                                                                                                                                                                     |
| executor の空きを待つスレッドの数 | 段階ごとに数回、`jcmd <pid> Thread.dump_to_file -format=json` で仮想スレッドを含むスレッドダンプを取り、`ConcurrencyThrottleSupport.onLimitReached` で `WAITING` のスレッドを数える。                                                                       |
| エラー                            | HTTP の 5xx の件数と、バックエンドの ERROR のログの件数。                                                                                                                                                                                                   |

指標の見方は[性能テストのメトリクスと監視](metrics-and-monitoring.md)に従う。

## 完了基準

- **段階1と2（λ ≤ C / L_test）**：
  - Listener が同時に持つ接続の数の最大が C 以下である。
  - 注文の確定の応答時間の p95 が、コア機能の更新系の目標値500ミリ秒以下である（[性能テストの目標値](performance-targets.md)）。
  - executor の空きを待つスレッドが0である。
  - エラーが0件である。
- **段階3から5（λ > C / L_test）**：判定の対象にしない。
  Listener が同時に持つ接続の数が C を超えないことと、executor の空きを待つスレッドが現れ始める λ と応答時間の悪化を記録する。
  待ちが現れ始める λ が C / L_test の近くになければ、`λ × L ≤ C` の式を直す。
- **全段階**：Listener が同時に持つ接続の数の最大が、P − R 以下である。

構成 B は、段階1と2の基準を、C / L_test を B の値にして同じに適用する。

## 結果の使い方

利用先は、自分の L、P、C、R で段階の λ を計算し直し、同じ手順で流す。
結果は[性能テストのレポーティング](reporting.md)に従って報告し、品質特性シナリオの限界に書いた本番の P の置き換えに使う。

## 未決の事項

- 負荷ツールは未選定である。選ぶときは、[負荷ツールとテストスクリプト](test-scripts.md#負荷ツールの選び方)に従って ADR に記録する。
- 本番と同等の占有環境は、まだない。構成 A と B は、その環境で流す。
