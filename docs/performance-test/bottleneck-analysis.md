# ボトルネックの特定

計測データだけを根拠にし、最も大きなボトルネックから一つずつ解消する。
現状値と目標の差を数値で押さえ、レイヤー、レイヤー内の箇所の順に絞り込み、原因と対策の仮説を立てる。
一度に一つの変更だけを加え、修正、計測、評価を繰り返す。

## 守る方針

- **計測データで判断する**：「このクエリが遅そう」という印象で手を打たない。
  性能の問題は直感と実測が大きく離れることが多いため、メトリクス、ログ、トレース、プロファイルを根拠にする。
- **最大のボトルネックから解消する**：全体の性能は、その時点で最も大きいボトルネックで決まる。
  他の箇所をいくら最適化しても、全体はほとんど改善しない。
- **一度に一つの仮説だけを検証する**：スレッド数とインデックスを同時に変えると、どちらが効いたか、どちらが悪化させたかを切り分けられない。

## 手順

1. **現状値を定義する**：目標と現状の差を数値で押さえる（例：p95の目標500ミリ秒に対して1,200ミリ秒）。
2. **レイヤーを特定する**：分散トレーシングや個別のログで一つのリクエストの処理時間を分解し、入口、アプリケーション、DB、外部サービスのどこで時間がかかっているかを把握する。
3. **レイヤー内の箇所を絞り込む**：アプリケーションならメソッドのトレースやプロファイル、DBならスロークエリのログ、`pg_stat_statements`、実行計画、外部サービスなら応答時間と呼び出し回数を確かめる。
4. **仮説を立てる**：絞り込んだ箇所について、原因と対策を合わせて文章にする。
5. **一つ変えて測る**：仮説の対策を一つだけ適用し、同じスクリプトで再計測し、効果と副作用を評価する。
   効果がなければ変更を戻し、手順2へ戻る。

対策の候補は[性能チューニングの打ち手](tuning.md)から選ぶ。
集めるデータは[性能テストのメトリクスと監視](metrics-and-monitoring.md)に従う。
