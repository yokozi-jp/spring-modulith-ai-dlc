# 性能テストのレポーティング

報告書にはテストの概要と、テスト種別ごとの結果、限界性能と増強の手順、残存リスクを書く。
処理時間はパーセンタイルを含む統計値を目標値と並べて表にし、時系列の挙動はグラフに注釈を添えて示す。
エラーは内訳を示し、設計上許容するものと異常とを切り分ける。

## 報告書の構成

1. テストの概要（計画書から抜粋した目的、範囲、テスト種別、性能要件と目標値）
2. ボリュームテストの結果
3. ラッシュテストの結果
4. ロングランテストの結果
5. ストレステストの結果
6. 限界性能、将来の負荷の増加に対する増強の手順、残存するリスク（未解消のチューニング項目、想定外の挙動など）

## 共通の書き方

- 処理時間は min、avg、p50、目標に応じたパーセンタイル（p80、p90、p95など）、max を、目標値と判定とともに表にする。
- リソース使用率は、構成要素ごとにスペック、台数、メトリクス、目標の範囲、min、avg、max、判定を表にする。
- 表に加えて、時系列のグラフ（監視ツールのダッシュボードのキャプチャでよい）を載せる。
  瞬間的なスパイクや、負荷の立ち上げへの追従は、表から読み取れないためである。
- グラフで目を引く箇所（突発的なスパイク、想定外の落ち込み、徐々に上がる傾向）には、原因や解釈を注釈で書く（例：「12時30分ごろのCPUのスパイクは日次の定時処理の起動と一致」）。
- エラー率が0%でない場合は、HTTPステータスごとの件数、割合、原因、対応方針を表にする。
  リトライで成功する一時的な競合や、レート制限による意図した拒否のような設計上許容するものと、本番で問題になる異常とを分け、異常は0%にする。

## ボリュームテスト

- **オンライン処理**：機能ごとに処理時間の統計値を表にする。
- **定時処理**：機能ごとに目標の処理時間、実測の処理時間、データ件数、件数あたりのスループット、データサイズ、サイズあたりのスループット、判定を表にする。
  試行は1回のため統計値は要らない。

## ラッシュテスト

- **シナリオ全体**：シナリオと負荷の状態ごとに、目標のRPS、実測のRPS、エラー率、判定を表にする。
- **機能単位**：シナリオの中の各機能について、呼び出しの割合、実測のRPS、エラー率、処理時間の統計値を表にする。
- **リソース**：負荷の状態ごとに、構成要素のリソース使用率を表にする。
- **構成の比較**：比較した構成ごとに、スペック、台数、性能要件の達成、CPUとメモリの min、avg、max、月額費用、評価（不足、最適、過剰）を表にし、採用した構成の根拠を書く。
  各構成の機能単位の詳細は、シナリオの表と同じ形式で別にまとめる。

[ボリュームテスト](volume-test.md)より大きく劣化した機能があれば、ロック待ち、接続プール待ちなど同時アクセスによる競合を疑って追加で分析する。
特定の機能にエラーが偏る場合は、原因を確かめて対策する。

## ロングランテスト

形式はラッシュテストに準じ、加えて時系列の推移を示す。

- **区間ごとの推移**：1時間ごとなどの区間で、実測のRPS、エラー率、判定を表にする。
- **開始区間と終了区間の比較**：機能ごとの平均処理時間と、構成要素ごとのリソース使用率について、開始区間と終了区間の値と差を示す。
  各区間が目標を満たすことに加えて、差が許容範囲に収まることを確かめる。
- **エラーの推移**：エラー率と特定のエラー種別の件数が、時間とともに悪化していないかを示す。
  接続プールの枯渇やリークによるタイムアウトのように、長時間の稼働で初めて現れるエラーを拾うためである。
- **ランタイムのメモリ**：ヒープとMetaspaceの統計値に加えて、GCによるのこぎり状の波形が分かるヒープの時系列グラフを必ず載せる。
  GCの直後の底を結んだ線が右肩上がりなら、メモリリークの強い兆候として優先して分析する。
  ランタイムのメモリはGCの時機で大きく揺れるため、開始区間と終了区間の比較では判定しない。
- **GCの推移**：区間ごとに、Minor GCとFull GCの回数と平均時間を表にする。
  Full GCの頻発はメモリリークの兆候として重く見る。

開始区間と終了区間は、テストの先頭と末尾ではなく、負荷が安定してかかっている区間から選ぶ。
開始直後はランプアップやJITコンパイルとキャッシュの温まりの途中であり、終了直前はランプダウンで件数が減って平均がぶれるためである。
24時間のテストなら、開始区間を1時間目から2時間目、終了区間を22時間目から23時間目のように両端を避ける。

## ストレステスト

合否の判定ではなく、現在の構成でどこまで耐えられるかと、どの構成要素をどの順に増強するかの見通しを示す。

- **限界性能**：段階ごとに、投入したRPS、実測のRPS、エラー率、処理時間、構成要素ごとのCPUとメモリの使用率を表にし、限界の段階とボトルネックの構成要素を書く。
  余裕のある構成要素を増強しても限界が上がらないことも書く。
- **オートスケール**：閾値に対する実測値、新しいノードの起動時間、ヘルスチェックの完了からロードバランサーへの組み込みまでの時間、スケール後のトラフィックの分散、性能の向上、エラー率を書く。

確認の観点は[ストレステスト](stress-test.md)に従う。
