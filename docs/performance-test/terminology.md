# 性能テストの種別と用語

性能テストは、ボリューム、ラッシュ、ストレス、スパイク、ロングランの5種別に分けて呼ぶ。
負荷の状態はシステムごとにパターンを定義し、関係者と合意する。
「負荷」「処理時間」「同時XX数」は解釈が揺れるため、使うたびに何を指すかを明示する。

## 性能テストの種別

**性能テスト**：性能に関するテスト全体の総称。
次の5種別に分ける。

- **ボリュームテスト**：大量のデータ（DBの大量レコード、大きなファイル）を与え、同時アクセスなしで、仕様の上限のデータ量を処理できるかを確かめる。
- **ラッシュテスト**：通常時とピーク時に想定する同時アクセスをかけ、処理時間とスループットが目標値を満たすかを確かめる。
  負荷テストと呼ぶこともある。
- **ストレステスト**：想定を超える同時アクセスやデータ量をかけ、限界性能と、そのときの振る舞いを確かめる。
- **スパイクテスト**：突発的で大規模なアクセスの増加をかけ、正常に動作し、その後に定常状態へ戻るかを確かめる。
- **ロングランテスト**：一定の負荷を数時間から数日かけ続け、メモリリークや接続とスレッドの枯渇がなく安定して動くかを確かめる。
  耐久テストと呼ぶこともある。

各種別の進め方と完了基準は、[ボリュームテスト](volume-test.md)、[ラッシュテスト](rush-test.md)、[ロングランテスト](long-run-test.md)、[ストレステスト](stress-test.md)に従う。
スパイクテストは、スパイク性のあるシステムに限り、ストレステストと合わせて実施する。

## 負荷の状態

負荷の状態は、負荷の大きさと予測可能性の組で定義する。

- **通常時**：日常的に発生する平均的な負荷。
  想定内とする。
- **ピーク時**：月初の朝など、定期的に訪れる最大の負荷。
  想定内とする。
- **スパイク時**：セールの開始直後など、ごく短時間に急増する負荷。
  予測できるものを想定内、SNSでの拡散のように予測できないものを想定外とする。
- **縮退時**：ノードの障害などで、処理能力の一部を失った状態。

状態ごとに合格基準と対応方針が変わるため、どの状態を想定内とするかを、時間帯と量（例：平日10時から17時、平均500リクエスト/秒）を添えて計画書に定義する。
通常時やピーク時が一つのパターンで表せない場合は、パターンを分けて定義する。

## 負荷

**負荷**：システムの処理リソースを消費する要因。
次のどれを指すかを、性能テストの文書では必ず明示する。

- **動的負荷の頻度**：アクセス数やリクエスト数。
- **動的負荷の規模**：1回あたりのペイロードやファイルのサイズ。
- **静的負荷**：実行の有無にかかわらず存在する負荷。
  主にDBに蓄積されたデータ量。

## 処理時間

**処理時間**：ある処理の開始から終了までの時間。
同じ語でも人とツールで計測区間が異なるため、計画書とレポートでは「どの地点からどの地点までか」を定義してから使う。

- **サーバーサイドレイテンシ**：サーバーがリクエストを受け取ってからレスポンスを返すまでの時間。
- **クライアントレイテンシ**：ブラウザで計測する、ネットワーク遅延を含めた時間。
- **レスポンスタイム**：リクエストを送ってからレスポンスが返るまでの時間。
- **ターンアラウンドタイム**：一連の処理の開始から完了までの時間。
  画面であれば描画の完了まで、定時処理であれば起動の依頼からプロセスの終了までを含む。

## スループット

**スループット**：単位時間あたりの処理量。
計測の対象に応じて単位を選ぶ。

- **リクエストスループット**：1秒あたりのリクエスト数（RPS）。
- **TPS**：複数のリクエストを束ねた業務処理の単位を明確に指す場合だけ使う。
- **メッセージスループット**：非同期処理で1秒あたりに送信または処理できるメッセージ数。
  送信側と受信側のどちらの値かを明示する。
- **定時処理のスループット**：1時間あたりの処理件数やデータサイズ。

「性能が2倍になった」と書くときは、処理時間とスループットのどちらが改善したかを明示する。

## 同時XX数

- **同時利用ユーザー数**：ある期間にシステムを利用しているユニークユーザー数。
  期間と、利用とみなす状態（例：1分間にログインして画面を開いている）を定義する。
- **同時接続数**：ある瞬間にサーバーが維持しているコネクション数。
  Webサーバー、DBなど、何への接続かを定義する。
- **同時処理数**：ある瞬間に実行中の処理数。

同時処理数とスループットは別の量であり、リトルの法則で次の関係にある。

```text
同時処理数 = スループット × 処理時間
```

たとえば同時処理数が4で、各リクエストが2秒かかるなら、スループットは2 RPSになる。
