# レビューで人が確認する範囲

ツールで検出できる指摘はCIの検査へ寄せ、レビューコメントにしない。
人のレビューは、規約にあるがツールで検出できない点、要求を満たしているか、文脈に依存する点に絞る。
レビューで見つけた未記載の方針は、docsの規約か検査へ追加する。

## 観点の振り分け

レビュー観点は、規約に書かれているかと、ツールで検出できるかで次のように振り分ける。

- **規約にあり、ツールで検出できる**：レビュアーは確認せず、CIの結果だけを見る。
- **規約にあり、ツールで検出できない**：レビュイーとレビュアーの両方が、規約に沿っているかを確認する。
- **規約になく、規約に書ける**：レビュアーが指摘し、同じ方針を規約へ追加する。
- **機能要件**：レビュイーとレビュアーの両方が、Issueや仕様を満たしているかを確認する。
- **文脈に依存し規約にできない**：個別の命名や、類似の実装がない箇所は、レビュアーが個別に確認する。

レビューで照らす規約は`docs/`の各領域の文書であり、入口は[ドキュメント](../index.md)から辿る。

## CIに寄せる指摘

整形、未使用コード、重複コード、不適切な層への依存、秘密情報の混入のように検査ツールで検出できる問題は、レビューコメントで扱わない。
検査ツールで検出できる指摘を繰り返しているときは、該当する検査をTaskfileとCIへ追加する。
既存の検査の内容と実行場所は[Lintとテストのリファレンス](../tooling/lint-and-test.md)を参照する。

## 未記載の方針を規約へ戻す

機能上は問題ないが他の実装と方針が揃っていない変更には、既存の方針へ合わせるよう指摘する。
その方針がdocsにない場合は、レビュアーが規約へ追加する。
検査ツールのルールとして表せる方針は、規約の文章より検査の追加を優先する。
規約を追加するPull Requestには、指摘を受けたレビュイーをレビュアーに含める。

文書の追加は[docs文書の作成と変更](../knowledge/documentation-authoring.md)に従う。
戻しにくい設計上の方針は、[ADRの運用ルール](../adr/conventions.md)に従ってADRを起こす。

## 生成コードの差分

Gitで管理する生成コード（[jOOQの生成コード](../database/jooq-codegen.md)など）は、`.gitattributes`で`linguist-generated=true`を指定し、Pull Requestの差分で既定では折りたたむ。
生成コードは生成元（changesetやOpenAPI契約）の変更として確認し、生成物を行ごとに確認しない。

## Pull Requestテンプレートのチェックリスト

[Pull Requestテンプレート](../../.github/PULL_REQUEST_TEMPLATE.md)のチェックリストは、レビュー依頼前のセルフチェックに使う。
項目は「関連文書も更新したか」のように確認できる具体的な行動にし、必要最小限に保つ。
CIで検査できる項目はチェックリストへ加えず、検査へ移す。
確認されなくなった項目は削除する。
