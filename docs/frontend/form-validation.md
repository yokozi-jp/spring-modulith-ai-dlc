# フォームの入力検証

入力検証はクライアントとサーバーの両方で行い、サーバーの検証を省かない。
クライアントの検証はTanStack FormとZodで実装し、表示している入力条件と同じ条件だけを検証する。
エラーは入力欄の近くに次の行動が分かる文言で表示し、エラーを理由に送信buttonを無効にしない。

## クライアントとサーバーの役割

- サーバーは、クライアントと同じかそれ以上の検証を必ず行う。クライアントの検証は利用者が迂回できるためである。
- クライアントの検証は、利用者へ即時に知らせるために行う。
- 表示している入力条件より緩い検証も厳しい検証もしない。
- 条件が複数ある場合（64文字以下かつ英数字混在など）は、すべての条件を検証する。
- インライン検証を行うフォームでは、送信時の検証とサーバーの検証でエラーがなるべく出ないように作る。

フォームの状態と検証のライブラリは[ADR-023](../adr/ADR-023-adopt-tanstack-form-and-zod.md)で決めている。

## 検証条件の同期

- クライアントとサーバーの検証条件は、OpenAPI契約を正本にして揃える。
- OrvalがOpenAPIから生成するrequestのZod schemaで入力条件を表せる場合は、それを送信時の検証に使い、同じschemaを手書きしない（[OrvalとAPI境界](api-client-orval.md)）。
- 生成schemaで表せない項目単位の条件と、生成のためにOpenAPI拡張（`x-`）の多用などの個別対応が要る条件は、featureの `schemas.ts` にZodで書く。
- 手書きした条件がOpenAPIの制約と一致することは、レビューとテストで確認する。

## インライン検証

**インライン検証**：送信の前に、入力中またはfocusを外したときに行う検証。

- インライン検証を導入するフォームでは、全項目に導入する。一部の項目だけに導入すると、インラインのエラーを解消した後に送信時のエラーが出るためである。
- 初期表示ではエラーを出さない。
- 必須の検証はfocusを外したときに行い、一度も入力していない項目には出さない。
- 桁数の検証と、IDやパスワードのように正しい値が利用者に自明でない入力の検証は、入力中に行う。
- 氏名、住所、電話番号、メールアドレスのように正しい値が利用者に自明な入力は、focusを外したときに検証する。
- 数値や文字種は、inputの `type` で入力を制御し、入力中に検証しない。
- どのエラーも、有効な値になった時点で、focusを外すのを待たずに消す。
- TanStack Formでは、入力中の検証を `onChange`、focusを外したときの検証を `onBlur`、送信時の検証を `onSubmit` のvalidatorに割り当てる。

インライン検証の度合いは、次の二つの型から選ぶ。

- **UX重視**：入力中とfocusを外したときの両方でインライン検証を行う。
- **バランス型**：入力中の検証を行わず、focusを外したときにインライン検証を行う。

どちらの型でも、送信時の検証とサーバーの検証を行う。

## サーバーへの問い合わせを伴う検証

- 重複の確認のようにAPIを使う検証は、入力中ではなくfocusを外したときに非同期で行う（TanStack Formの `onBlurAsync`）。
- メールアドレスの登録有無を返すAPIは、第三者が登録済みのアドレスを確かめられるため、バックエンドで厳しいrate limitをかける。
- 確認用の再入力欄を設ける場合は、確認欄で入力中に完全一致だけを検証し、大文字と小文字の同一視などの正規化をしない。
- 通常の操作でエラーが起きない連動項目（選んだ支払方法に応じて表示する欄など）には、項目間の検証を追加しない。

## 送信buttonとHTMLの制約属性

- 入力エラーを理由に送信buttonを `disabled` にしない。`disabled` のbuttonはkeyboardのfocusが届かず、押せない理由も利用者に伝わらないためである。
- 検証ロジックはZodで実装し、`form` 要素に `noValidate` を付けてブラウザ標準の制約検証を止める。
- inputには、入力条件に合わせて `type`（`email`、`tel`、`number`、`date` など）と、`required`、`minLength`、`maxLength`、`min`、`max`、`pattern` を付ける。
- エラーのある入力欄には `aria-invalid="true"` を付け、`aria-errormessage` でエラー文言の要素を参照する。

## エラーメッセージ

- 何をすればよいかが分かる具体的な文言にする（「パスワードは8文字以上にしてください」）。「エラーが発生しました」で済ませない。
- 短く書き、利用者を責めず、入力し直しを促す表現にする。
- 文言はmessage catalogに置き、schema libraryの既定の文言をそのまま表示しない（[フロントエンドの国際化](i18n.md)）。
- エラーは入力欄の直下または横に表示する。
- scrollが必要な長いフォームでは、フォームの上部にエラーの一覧を併せて表示してよい。
- サーバーが返すProblem Detailsの文言の扱いは[フロントエンドの国際化](i18n.md)に従う。
