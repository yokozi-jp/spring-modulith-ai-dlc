# 非機能要件定義の進め方

非機能要件の定義では、重要ドライバを見極め、曖昧な期待を検証できる数値に変え、関係者と合意する。
フェーズの解像度に合わせて方針、数値、検証の順に具体化し、アーキテクチャを左右する要件ほど早く方針を決める。
目標値は、優先度、根拠、測り方、検証するテストと組にして確定する。

## 用語

- **非機能要件**：機能がどの程度の品質で提供されるかを定める要件。個々の機能に一対一で対応せずシステム全体を横断し、実現できるかどうかではなく度合いを問う。
- **アーキテクチャドライバ**：アーキテクチャを方向づける要因。非機能要件、主要機能要件、制約、その他の関心事（チームのスキル、技術の採用実績、プロジェクト規模など）からなる。
- **主要機能要件**：インフラ構成やコストに波及し、システムの構造を左右する機能要件。
- **制約**：要件を実現するうえでの前提条件。予算、スケジュール、体制、社内規程、コンプライアンスのビジネス制約と、実行環境、言語、フレームワーク、セキュリティポリシーの技術制約に分かれる。
- **重要ドライバ**：満たせなければシステムの存在意義が失われる非機能要件。「あったほうがよい」要件は含めない。

類似する用語と非機能のフレームワークは[非機能要件のフレームワークと用語](frameworks.md)にまとめている。
適用範囲と合意相手は[非機能要件の適用範囲と合意相手](scope-and-stakeholders.md)に従う。

## 判断の原則

- 要件を項目ごとに個別に判断せず、全体として成り立つかを見る。
- 要件の水準を上げるときは、代わりに諦めるもの（別の品質、コスト、スケジュール）を併記する。
- 根拠を説明できない水準は過剰品質を疑う。「念のため」の冗長化や暗号化を積み上げない。
- 要件を一覧にして終わらせず、重要ドライバを特定する。業務上の致命的な失敗シナリオから逆算すると見つけやすい。
- 要件を決めるときは、それが求める設計、コスト、期間、テストまで見通す。
- 「24時間365日止めない」「無停止で更新する」のような要求は、そのまま受け入れない。犠牲になるコスト、スケジュール、運用負荷を示し、必要性を確かめる。

## フェーズごとに決める粒度

| フェーズ                   | 粒度 | 決めること                                                  |
| -------------------------- | ---- | ----------------------------------------------------------- |
| 提案からグラウンドデザイン | 方針 | 重要ドライバ、アーキテクチャの骨格、大枠の予算と体制        |
| 要件定義                   | 数値 | 開発とテストの基準になる定量目標と、関係者の合意            |
| 基本設計以降               | 検証 | PoC、負荷テスト、セキュリティ診断による実現性の確認と再調整 |

- 非機能要件の決定を基本設計まで先送りしない。
- 確度の低い要件は幅を持たせるか低めに置き、検証していない高い目標値（稼働率99.99％など）を確定として約束しない。目標値は上げるより下げるほうが合意しにくい。
- 合意した値を覆すときは、事業前提の変化や実測との乖離といった理由を添えて説明する。
- 基本設計以降に新しい非機能要件が出たら、要件定義の詰めが不足していたものとして扱い、合意相手と再調整する。
- 重要ドライバは会議で同期的に合意し、それ以外の項目は書面や非同期のレビューで確認する。
- 反復型の開発でも、性能、可用性、セキュリティ、拡張性の重要ドライバは方針を早期に決める。数値目標は幅を持たせて置き、反復のなかで具体化する。

## 手順

次の順に進める。
後段の検討や検証で問題が見つかったら、前段へ戻って見直す。

1. 提案からグラウンドデザインの段階で、重要ドライバに関係する事業上の関心事と大枠の予算と体制を押さえ、意思決定層を巻き込む。
2. 要件定義の入口で、この手順そのものを関係者と合意する。
3. ビジネスコンテキストを確かめる。
4. 制約を洗い出す。
5. 重要ドライバを特定する。
6. 出発点にするフレームワークを選ぶ。
7. ベースラインを仮置きする。
8. 優先度を付ける。
9. 要求を定量化する。
10. トレードオフを評価する。
11. 関係者と合意して確定する。
12. 確定した要件を文書にして設計へ引き渡す。

### ビジネスコンテキスト

非機能要件に着手する前に、次の観点を関係者の共通認識にする。
判断の根拠がないまま決めた要件は、妥当性を問われたときに説明できない。

- **ビジネスゴール**：新規事業で顧客を増やす攻めか、既存業務のコストを削る守りか。投資の姿勢が変わる。
- **クリティカル度**：停止が売上と信用の毀損に直結する基幹業務か、多少の停止を許容できる業務か。
- **ユーザー像と利用規模**：社内数百名の業務利用か、不特定多数の利用者か。精緻な数値は定量化で決める。
- **コストとスケジュール**：予算と納期にどれだけ余裕があるか。
- **新規構築か刷新か**：刷新なら現行の実績値と障害履歴を使い、既知の課題の解消を焦点にする。新規なら構築コストと見込み効果から水準を起こす。

### 制約

変更できない制約を早く洗い出す。
後から発覚すると手戻りの大きい技術と規程の制約を優先する。

- 採用する技術がすでに決まっていないかを確かめる。このリポジトリの技術選定は [ADR](../adr/index.md) に記録している。既存の技術から外れる選択には理由が要るため、[ADR の運用ルール](../adr/conventions.md)に従って ADR を起こす。
- ベンダーロックインの回避、一般提供版に限った採用、マネージドサービスの優先、サポート終了への許容度のような、明文化されていない方針を確かめる。ロックインの回避は絶対の要求にせず、マネージドサービスの保守性やセキュリティの便益と比べて範囲を決める。
- 組織の規定（クラウド構築ガイドライン、全社セキュリティポリシー、システム運用基準）があれば、準拠を前提にしてこのシステム固有の要件を上乗せする。規定がなければ、クラウド事業者のベストプラクティスや業界標準を拠り所にする。

### 重要ドライバ

- 「このシステムのコンセプトは何か」を一文で決める。性能と拡張性の優先、可用性の優先、運用と拡張のしやすさの優先、セキュリティの優先、コストの抑制などがある。
- コンセプトは、要件が競合したときにどちらへ寄せるかの指針にする。
- コンセプトを、アーキテクチャの分岐が決まる粒度まで具体化する。

具体化の例を次に示す。

- **性能の優先**：同期の即時応答が必須か、非同期の結果整合を許すか。
- **可用性の優先**：どの範囲の障害まで無停止で耐えるか。複数のアベイラビリティゾーンで足りるか、複数リージョンまで要るか。
- **セキュリティの優先**：テナントの分離を論理分離で足りるとするか、DB やインスタンスの物理分離まで求めるか。DB の分離方式は[PostgreSQLのマルチテナント](../database/postgresql-multitenancy.md)に従う。

重要ドライバは会議で重点的に議論し、それ以外の項目はベースラインと書面の確認に委ねる。

### フレームワークとベースライン

- フレームワークは検討の抜けを点検するために使う。項目を上から順に埋める台帳にしない。選び方は[非機能要件のフレームワークと用語](frameworks.md)に従う。
- 項目ごとの議論の前に、既存または類似システムの非機能要件か、フレームワークの標準モデルをベースラインとして仮置きする。
- 標準モデルは粒度が粗いため、そのまま当てはめず、システムの性質に合わせて調整する。

### 優先度

洗い出した要件と制約を次の三つに分け、関係者と認識を合わせる。

- **Must**：満たさなければプロジェクトが成立しない要件。予算の上限、法規制の遵守など。
- **Should**：強く求めるが、交渉や代替案の余地がある要件。目標とするレスポンスタイムなど。
- **Want**：余裕があれば実現する要件。将来の拡張に向けたリソースの確保など。

### 定量化

定量化の土台として、次の基礎数値を事業側から引き出す。
現行システムがあれば実績値を使い、新規構築なら事業計画から見込む。

- **規模**：利用者数、拠点数、データ量。性能と拡張性の目標の土台になる。
- **地理的範囲**：国内の一拠点か、海外を含むか。ネットワークのレイテンシに効く。
- **時間的範囲**：平日日中だけか、24時間365日か。担保する稼働時間に効く。
- **ピーク特性**：セールや決算期に通常の何倍になるか。ピーク時の性能目標に効く。

数値を引き出すときは次のように進める。

- 質問の目的（要件に落とし、性能検証で担保するため）を示す。
- 相手から数値が出なければ、事業規模と成長率から仮説の数値を示し、実態と合うかを確かめる。
- 事業の数値から技術の数値を導く計算式を共有する。たとえば、ピーク時の同時接続1,000名が10秒に1回操作するなら100 TPS になる。
- その水準である理由と、満たせないときに利用者や業務に起きることを説明する。

目標値は、検証するテストと対にして置く。
対応は[非機能要件と検証するテストの対応](verification-mapping.md)で確かめ、検証するテストを描けない目標値は定義が曖昧なものとして扱う。

### トレードオフの評価

定量化した要件を全体として突き合わせ、コストとスケジュールのなかで成り立つかを評価する。

1. 競合する要件を一覧にし、横断で見る。
2. 競合した要件は、重要ドライバとコンセプトに照らしてどちらを立てるかを決める。
3. コストとスケジュールに収まらなければ、Should と Want から緩める。Must は緩めない。
4. それでも成り立たなければ、優先度か目標値に戻って水準を調整する。

### 確定の条件と記録

目標値は、次の三つを満たしたときに確定とする。

1. 業務要求に照らして、その水準である理由を説明できる。
2. その値を達成する設計を合理的に描ける。
3. 未達のときに原因を追い、改善できる。

- 目標値と一緒に、その値の測り方（稼働率の計算式など）を合意する。測り方が曖昧だと、同じ実績で達成と未達の判断が食い違う。
- 合意した値は、根拠（重要ドライバ、基礎数値、トレードオフの結果）と一緒に記録する。
- 複数リージョンの要否のように後戻りしにくい判断は、[ADR の運用ルール](../adr/conventions.md)に従って ADR に記録する。

### 設計への引き渡し

- 要件には達成する水準までを書き、実現手段は設計に委ねる。
- 設計や検証で実現が難しいと分かったら、要件へ戻して再調整する。
