# 高可用性要件と稼働率の扱い

稼働率を議論するときは、要求値、要件、設計値、実績値のどれを指すかを明示する。
要求値は停止の痛みと期待損失から引き出し、設計値と照らして実現できる水準を要件として合意する。
停止は利用者と業務への影響で数え、実績値で要件と構成を見直す。

一般レベルで足りるかの判断と、稼働率の計算条件は[可用性要件の定め方](availability-requirements.md)に従う。

## 稼働率の四つの視点

- **要求値**：事業の文脈から導いた、止まりにくさへの期待。主な関心者は事業責任者と業務主管部署。
- **要件**：目標値の合理性と、未達時の改善責任を合意したもの。主な関心者はプロジェクト責任者。
- **設計値**：要件を実現する構成が理論上出せる上限。主な関心者はアーキテクト。
- **実績値**：運用で記録した実際の値。主な関心者は運用部門。

要求値を要件として約束し、設計値で裏づけ、実績値で検証する順に扱う。

## 要求値

要求値はシステムの内側ではなく、事業の状況で決まる。
事業の状況を踏まえずに置いた数値は、根拠のない数字合わせになる。

- **事業の局面**：拡大期は投資を積極化しやすく、縮小期は目標が下がりやすく、探索期は最小限から始める。
- **システムのライフサイクル**：新規構築時は投資を得やすく、運用保守期や刷新前ほど予算が厳しくなる。
- **停止の影響度**：競合への顧客流出や売上への影響が大きいほど高い稼働率を求める。利用頻度の低い社内システムでは、コストとの釣り合いで水準を下げてよい。

事業側とは、技術用語ではなく停止の痛みで認識を合わせる。
稼働率だけでは止まる時期と長さを表せないため、次の痛みごとに許容できる止まり方を具体化する。

- **頻度の痛み**：頻繁に止まる。
- **長さの痛み**：一度止まると長い。
- **時期の痛み**：繁忙期や月末に止まる。
- **検知の痛み**：止まったことに気づかない。
- **回復の痛み**：直ったと思っても使えない。

可用性に投じる金額の目安は、停止による期待損失（1回あたりの損失額 × 発生頻度）で見積もる。
損失には停止中の売上の減少に加え、評判の低下による顧客の離反も織り込む。
備えのコストが、それによって避けられる期待損失を上回る投資はしない。

## 要件

- 要件の確定条件は[非機能要件定義の進め方](definition-process.md)の「確定の条件と記録」に従う。
- 要件は要求値だけでは確定できない。設計値と照らし合わせ、実現できる水準として確定する。
- 書き方は[可用性要件の定め方](availability-requirements.md)の「要件の書き方」に従う。

## 設計値

設計値は要件定義の成果物ではないが、要件の実現性を判断するために見積もる。

- 直列の構成では、全体の稼働率は各要素の稼働率の積になり、最も低い要素で頭打ちになる。たとえば99.9％、99.9％、99.5％の三要素を直列につなぐと約99.3％になる。
- 冗長化（並列化）で稼働率を引き上げられる。99.9％の要素を2台並列にすると、両方が同時に止まる確率は0.001の2乗になり、約99.9999％になる。
- 並列化できない単一の依存先があると、そこが全体の上限になる。オンプレミスでは共有ストレージがこの依存先になりやすい。
- 99.999％のような値は金融や通信の水準であり、一般の業務システムの要件に置かない。

### クラウドとオンプレミスの公表値

- クラウドが公開する SLA の値は、設計値ではなく商用上の下限とみなす。その値で毎月どれだけ止まるかを時系列に描き、業務の期待に足りるかを確かめる。運用が始まったら実績値で見直す。
- オンプレミスの製品の公表値は、故障率の予測と冗長設計から導いた設計値とみなしてよい。
- SLA はサービスが応答するかを示し、業務を再開できるまでの復旧処理の時間を含まない。復旧のシナリオまで見通して RTO に織り込む。

### 障害の種類ごとの対策

障害の原因ごとに対策の型を分けて見積もる。

- **機器の故障**：公開されている故障率から見積もり、冗長構成と機器の更改時期を計画する。
- **負荷の急増によるミドルウェアの不調**：流量制御と、その制御が働いたときの対応を一緒に設計する。外部連携の容量制御は [ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md) に従う。
- **特定の条件で起きる不具合**：外形監視と、切り替えの高速化で抑える。

設計値が要求値に届かないときにとれる手は、次の二つである。

- 別の耐障害機構（別のリージョン、別のクラウド、オンプレミスの併用）を加える。
- 業務側で吸収する。復旧までの時間を前提に、代替の運用や業務の調整を用意する。

冗長機構そのものが切り替えに失敗する可能性も織り込む。

## 実績値と停止の数え方

停止は、部品やジョブが失敗したかではなく、利用者や業務に影響が出たかで数える。
たとえば夜間の一括処理が途中で失敗しても、決められた時間枠内に回復して後続の業務に影響がなければ、稼働率を下げる停止に数えない。

稼働率は、運用が記録した障害の検知から復旧までの時刻を積み上げて算定する。
停止の判定基準は次から選び、目標値と一緒に合意する。

- **ヘルスチェックの応答**：外形的に応答が返るかで判定する。サービスは応答しているのに業務が回っていない状態を取りこぼす。
- **実際のリクエストの成功率**：成功率が閾値を下回った時間帯を、利用できない時間として集計する。

API の外形監視、ヘルスチェック、エラーバジェットの扱いは[APIの失敗のログレベルと監視](../web-api/logging-and-monitoring.md)に従う。

実績値は要求値、要件、設計値と突き合わせ、乖離があれば構成か要件を見直す。
実績値は、次期システムの要求水準を決めるベースラインとして残す。

## 要求水準の見直し

要求値は固定せず、次の二つの機会に見直す。

- **定期の点検**：年1回や、予算と計画の節目に、現在の要求水準が妥当かを確かめる。
- **変化のきっかけ**：利用者数や取引量が想定を大きく超えた、事業の局面が変わった、重大な障害や実績値の未達が出た、といったときに臨時で見直す。

利用が伸びると停止の影響を受ける利用者と取引が増え、同じ稼働率でも以前は許容できた停止が許容できなくなることがある。
