# 基盤の品質特性シナリオ

このリポジトリの業務機能（注文、決済）はサンプルなので、業務の目標値は置かない。
基盤が守る性質を、**品質特性シナリオ**（刺激、環境、応答、応答の測定値の4項目で書く目標）3件にする。
数値はパラメータにし、既定値は今の設定から導いた値である。

## 利用先が値を入れる前提

既定値は、今の設定から導いた値であり、業務の根拠はない。
利用先は、次の順で自分の値に置き換える。

1. 自分の外部システムの最悪時間 L、到着率 λ、許容する停止の長さ T_out を決める。
2. 接続プールの大きさ P と同時実行の上限 C を、[接続の予算](#接続の予算)の式で決める。
3. 再投入の方針の待ち時間の和を、[許容する停止の長さ](#許容する停止の長さ)の式で求め、T_out 以上にする。
4. 確かめるテストを、置き換えた値で流す。

目標値を決める手順は[非機能要件定義の進め方](definition-process.md)に従い、検証するテストとの対応は[非機能要件と検証するテストの対応](verification-mapping.md)に従う。

## 外部呼び出しの遅延

決済の Listener は、外部システム（決済代行）を呼ぶ間もトランザクションを開き、DB の接続を持つ（[ADR-050](../adr/ADR-050-define-backend-class-roles-and-naming.md)）。
外部システムが遅いと、Listener が接続を長く持つ。

| 項目         | 内容                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------- |
| 刺激         | 外部システムを呼ぶ Listener が、毎回最悪時間 L かかる。到着率は1インスタンスあたり λ 件/秒である。                |
| 環境         | 平常の運用。1インスタンス。                                                                                       |
| 応答         | Listener が持つ接続は C 本までで、通常の要求のために R 本が残る。                                                 |
| 応答の測定値 | (a) Listener が同時に持つ接続の数 ≤ C ≤ P − R。(b) λ ≤ C / L のとき、要求のスレッドが executor の空きを待たない。 |

### 接続の予算

Listener は接続を、外部システムの応答を待つ間も持ち続ける。
平均して λ × L 件の Listener が同時に動くので、次の2つの式が成り立つ範囲に収める。

- `λ × L ≤ C`：Listener の同時実行の上限 C に収まり、要求のスレッドが executor の空きを待たない。
- `C ≤ P − R`：Listener が持つ接続の上限 C が、プールから通常の要求の分 R を引いた本数に収まる。

既定値の C / L は 2 / 3 ≒ 0.67 件/秒/インスタンスで、これが待ちなしで捌ける上限である。
C を P / 2 まで上げても、上限は (P / 2) / L ≒ 1.67 件/秒/インスタンスである。
λ がこの上限を超えると、コミットの後に Listener を投入する要求のスレッドが、接続を持ったまま空きを待つ（`application.yaml` の `ponytail:` の注記、[非同期処理の流量制御と性能](../integration/async-flow-control.md)）。
決済代行の呼び出しをトランザクションの外へ出しても、この上限は変わらない。
上限の原因は接続ではなく、Listener のスレッドの枠だからである。
外へ出すと変わるのは、C を P / 2 の制約なしに上げられるようになる点だけである。

L は、トランザクションの中で呼ぶ外部システムの最悪時間の計算（[外部システムのClient](../backend/class-roles/external-client.md)）と同じ値であり、`idle_in_transaction_session_timeout` より短くする（[DB接続情報とロール分離](../database/connections.md#接続ごとの時間の上限)）。

## 外部システムの停止と回復

| 項目         | 内容                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 刺激         | 外部システムが T_out の間、すべての呼び出しを失敗させ、その後回復する。                          |
| 環境         | 再投入のジョブが有効。                                                                           |
| 応答         | 出版は失われず、人の操作なしに再投入されて完了する。                                             |
| 応答の測定値 | T_out ≤ 再投入の待ち時間の和のとき、全出版が回復の後、次の待ち時間 + `interval` 以内に完了する。 |

### 許容する停止の長さ

n 回目の再投入の前に、最後の試行から `min(wait-age × multiplier^(n-1), max-wait)` だけ待つ（[ADR-079](../adr/ADR-079-resubmit-failed-event-publications-periodically-with-shedlock.md)）。
再投入は `abandon-after-attempts` 回目まで行う。
既定の方針の待ち時間は次のとおりである。

| n   | 待ち時間 | 最初の失敗からの合計 |
| --- | -------- | -------------------- |
| 1   | 1分      | 1分                  |
| 2   | 2分      | 3分                  |
| 3   | 4分      | 7分                  |
| 4   | 8分      | 15分                 |
| 5   | 16分     | 31分                 |

`max-wait` の1時間は、既定の5回では効かない。
許容する停止の長さは、この和の31分である。
定期のジョブは待ち時間を過ぎた後の最初の実行で再投入するので、実際の再投入は最大で `interval`（30秒）遅れる。
この遅れの分の余裕は数えない。

出版が回復の直前に失敗したとき、次の再投入までの待ちが最も長くなる。
最悪は4回目の失敗の直後に回復した場合で、最後の待ち16分に `interval` の30秒を足した約16.5分で完了する。

T_out が和を超えた出版は、上限の回数目の再投入で失敗して `ABANDONED` になり、ERROR のログで人の対応を求める（[イベント出版の再投入のログイベント](../observability/runbook-event-publication-resubmission.md)）。

## 同じイベントの二重の配信

| 項目         | 内容                                                                                |
| ------------ | ----------------------------------------------------------------------------------- |
| 刺激         | 同じイベントが同じ Listener に2回届く（再投入、インスタンスの停止、ロックの競合）。 |
| 環境         | 任意。                                                                              |
| 応答         | 2回目が業務の行を変えない。                                                         |
| 応答の測定値 | すべての Listener で、2回目の後の行が1回目の後と一致する（差が0件）。               |

## 限界

- λ と T_out の既定値は、現在の設定から導いた値で、業務の根拠はない。利用先が置き換える。
- 本番の P は、負荷試験で決まっていない。接続の予算の境目の数値は、P が決まった後に置き換える。
- 許容する停止の長さは、`last_resubmission_date` を基準にした待ち時間で、ジョブの実行の揺れ（`interval` の30秒）を含めて概算した。性能テストと結合テストで確かめる。
- 要求のスレッドの待ちに上限をつけたキューを足すと、接続の予算の測定値 (b) の測り方が変わる。
