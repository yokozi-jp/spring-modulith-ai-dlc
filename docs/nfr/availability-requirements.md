# 可用性要件の定め方

可用性要件は、運用スケジュール、RTO と RPO、稼働率の三つを基本項目にして定める。
稼働率は、分母、停止の数え方、計画停止の扱いを目標値と一緒に合意する。
標準構成で業務要求を満たせるなら一般レベルで確定し、判断基準に当てはまるときだけ高可用性要件へ進む。
要件は水準で書き、機能や実現手段で書かない。

## 可用性の項目

- **継続性**：どの時間帯に、どれだけの割合で使え、障害からどれだけ速く戻すか。この文書で定める。
- **耐障害性**：冗長化と単一障害点の排除で、止まりにくくする。[耐障害性の要件と設計の分担](fault-tolerance.md)に従う。
- **災害対策**：広域障害からの復旧と事業継続。[災害対策と事業継続の要件](disaster-recovery.md)に従う。

定義項目と値の例は[可用性の定義項目チェックリスト](availability-checklist.md)にまとめている。

## 継続性の基本項目

- **運用スケジュール**：稼働が必要な時間帯。平日9時から17時、24時間365日など。
- **RTO**：目標復旧時間。障害からどれだけの時間で復旧するか。
- **RPO**：目標復旧時点。どの時点までのデータを戻すか。
- **稼働率**：運用スケジュールのうち、サービスを提供できる時間の割合。

これらは次のように決める。

- 運用スケジュールを最初に決める。とくに計画停止の枠を取れるかを確かめる。24時間365日を求めると、無停止の更新と冗長構成の切り替えが前提になり、難度と費用が大きく上がる。
- このリポジトリでは、DB の切り戻しにアプリケーションの書き込み停止が要る（[DBのデプロイと切り戻し](../database/runbook-deploy-and-rollback.md)）。無停止の更新を要件にする場合も、切り戻し時の書き込み停止を稼働率でどう数えるかを計算条件に含める。
- 稼働率と RTO を両方定める。稼働率は一定期間の停止の累計に、RTO は一回の停止の長さに上限をかける。稼働率だけでは、繁忙日に許容時間をまとめて使い切る止まり方を防げない。
- 平均故障間隔（MTBF）や故障率を独立した要件にしない。結果として止まらなかったか（稼働率）と、壊れたときにどれだけ早く戻せるか（RTO と RPO）で定める。
- 可用性と耐久性を別の要件として定める。可用性はサービスを使い続けられるかで、冗長化とフェイルオーバーで確保する。耐久性は預けたデータを失わないかで、バックアップ、レプリケーション、複数拠点での保管で確保する。冗長化はデータの保全を保証しない。

## 稼働率の計算条件

稼働率は次の式で求める。

```text
稼働率（％）＝ 実際に稼働できた時間 ÷ 稼働を求める時間 × 100
```

- 分母の稼働を求める時間は、運用スケジュールで決める。
- 停止時間には、障害そのものの継続時間に加え、原因の調査、切り戻し、データの復旧、業務再開の確認までの復旧処理の時間を含める。
- 事前に告知した計画停止は、運用スケジュールの外として停止時間に含めない。
- 大規模災害や外部要因による停止を除くか、月間と年間のどちらで集計するかを明記する。
- 何を停止として数えるかは[高可用性要件と稼働率の扱い](availability-high.md)の判定基準から選び、目標値と一緒に合意する。

たとえば600分の稼働を求め、障害が10分続いて復旧処理に60分かかった場合、停止時間は70分で、稼働率は (600 − 70) ÷ 600 × 100 ＝ 88.3％ になる。

### 稼働率の水準

24時間365日の運用での目安を示す。
「9」が一つ増えるごとに停止の許容は約10分の1になり、コストと構成の難度が大きく上がる。

| 稼働率    | 年間の停止許容時間 |
| --------- | ------------------ |
| 99％      | 約3.6日            |
| 99.9％    | 約8.7時間          |
| 99.99％   | 約52分             |
| 99.999％  | 約5分              |
| 99.9999％ | 約32秒             |

- 一般的な業務システムは99.5％から99.9％に収まることが多い。
- 99.99％以上は、金融や通信のように可用性が重要ドライバになる領域の水準である。
- 事業側へ水準を示すときは、年間の停止時間や「30分の停止が年に何回までか」に換算する。99.99％は年1回の30分停止で維持でき、年2回では維持できない。

## 一般レベルで確定するか

多くのシステムは、次の三つの手順で一般レベルの可用性要件を確定する。

1. ベースラインから要求レベルを置く。停止の影響が社内にとどまる業務なら、IPA 非機能要求グレードの社会的影響が「限定される」モデルにあたり、稼働率99.5％から99.9％を目安にする。
2. 標準構成で満たす。冗長化（複数のアベイラビリティゾーンや機器の二重化）、単一障害点の排除、バックアップとリストアを整える。特別に作り込まず、標準の構成から外さない。
3. 実績で妥当性を確かめる。現行システムがあれば稼働実績と障害履歴から、実際に何回止まり業務がどれだけ困ったかを確かめる。新規なら類似システムの水準を拠り所にする。

一般レベルの合意は、「業務への影響は限定的なので、標準構成で稼働率○％程度を目標にする」と確認する程度でよい。

次のいずれかに当てはまるときは、一般レベルで止めず[高可用性要件と稼働率の扱い](availability-high.md)へ進む。
費用、合意形成、設計と構築の負担は増える。

- 決済、認証基盤、社会インフラ、基幹業務のように、ミッションクリティカル性が高い。
- 「24時間365日絶対に止めない」のように、事業側の期待が技術や予算の面で現実的な水準から大きく離れている。
- 同種のシステムで、重大な障害、訴訟、信用の失墜を起こしたことがある。
- 前例のない新規事業のように、妥当なベースラインがない。
- 重要インフラ、金融、医療などの法令やガイダンスによる要求がある。
- SLA の未達に違約金や契約解除の条項がある。

迷うときは、止まったときの痛みの大きさで判断する。

## データ保全の要件

データを失わないための備えは、ミッションクリティカルかどうかに関わらず定める。
要件として決めるのは次の二つである。

- **許容するデータ損失**：障害時にどの時点まで戻せればよいか（RPO）。
- **データ保全の範囲**：リージョンや拠点の全損に備え、別のリージョンや拠点へバックアップするか。

運用と設計の項目は要件と分けて扱う。

- バックアップの取得頻度、世代管理、ジョブの監視、リストアの訓練は運用保守性の要件で、取得方式と保管先は設計で扱う。DB は[PostgreSQLのバックアップと災害対策](../database/postgresql-backup-and-recovery.md)に従う。
- バックアップからのリストアでは間に合わない RTO や、無停止の切り替えが要る場合は、[災害対策と事業継続の要件](disaster-recovery.md)で扱う。

## 要件の書き方

- 定性的な期待は数値にする。「止まりにくいこと」ではテストで合否を判定できない（例：稼働率99.9％以上、年間の停止時間8.7時間以内）。
- 停止の影響が異なる機能（決済と管理画面など）は、水準を分けるかを検討する。
- 可用性を機能として書かない。悪い例は「障害時に自動で切り替わる機能を追加する」で、良い例は「フェイルオーバーの切り替えは5分以内」である。
- 実現手段を書かない。悪い例は「Kubernetes の Replica 数を3にする」「DB を同期レプリケーションでフェイルオーバーさせる」で、良い例は「RTO 5分以内、RPO 1分以内」である。構成は設計で決める。
