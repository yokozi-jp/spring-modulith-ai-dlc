# 耐障害性の要件と設計の分担

要件では、どの範囲の障害に耐え、どのリスクを受容するか、切り替え時間、自動か手動か、縮退の範囲を合意し、具体的な構成は設計に委ねる。
単一障害点を許容しない方針を置き、認証基盤、DNS、共有ストレージを意識して洗い出す。
依存先が止まったら、明確な理由がない限り縮退せずに止める。

稼働率と RTO の定め方は[可用性要件の定め方](availability-requirements.md)に従う。

## 要件で決めることと設計に委ねること

| 項目                         | 要件で決めること                                                             | 設計に委ねること             |
| ---------------------------- | ---------------------------------------------------------------------------- | ---------------------------- |
| 稼働率                       | 目標水準                                                                     | 到達させる構成全般           |
| RTO と切り替え時間           | 許容する最大時間                                                             | フェイルオーバーの方式       |
| RPO                          | 許容するデータ損失                                                           | レプリケーションの方式       |
| フェイルオーバーの自動と手動 | どちらにするかの方針                                                         | 検知の閾値と切り替えの仕組み |
| 縮退運用のレベル             | どこまで機能を落として続けてよいか                                           | 縮退の実装                   |
| 障害耐性の範囲               | どこまでの障害に耐えるか（単一 AZ の障害は継続、リージョン全損は対象外など） | AZ とリージョンの構成        |
| 単一障害点                   | 許容しない方針                                                               | 各層での特定と冗長化         |

- 障害耐性の範囲は、稼働率の目標から推測させず、要件定義で明示的に合意する。範囲外とした障害の損失を事業が受け入れる判断であり、構成の土台を決めて後戻りが高くつくためである。
- どの AZ を使うか、retry を何回にするかのような構成は要件に書かない。外部連携の timeout と retry は [ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md) に従う。

## 単一障害点

- 単一障害点を許容しない方針を要件に置き、各層の単一障害点を設計で洗い出す。
- 認証基盤、DNS、共有ストレージは単一障害点になりやすく、見落とされやすい。
- このリポジトリでは、OIDC の IdP と、セッションを保持する Redis も洗い出しの対象にする（[ADR-007](../adr/ADR-007-session-based-auth-with-oidc-pkce.md)）。
- DB の構成は[PostgreSQLのバックアップと災害対策](../database/postgresql-backup-and-recovery.md)に従う。

## フェイルオーバー

- 切り替えている間は利用者が使えず停止時間に含まれるため、切り替え時間を要件で定める。
- RTO が厳しいほど自動に寄せる。手動では検知、判断、操作に人手が入り、RTO を圧迫する。
- 誤った切り替えを防ぐために承認を挟むかは、運用とガバナンスの判断で決める。

## 依存先が止まったときの振る舞い

外部 API、DB、認証基盤などの依存先が止まったときの振る舞いを要件で決める。
選択肢は次の二つである。

- **止める**：依存先が使えないと判断したら、その機能全体を止める。動くか止まるかの二状態になり、テストと運用が単純になる。
- **縮退して続ける**：一部の機能だけ続ける（更新は止めて参照は続けるなど）。正常、縮退、復帰の状態とその組み合わせをテストする必要があり、古いデータの参照や、片側だけ更新された不整合を招きやすい。

どちらにするかは次のように決める。

- 明確な理由がなければ止める。
- 縮退を選ぶなら、落とす機能、落とす条件、戻し方を設計とテストの対象にする。成り行きで参照だけを生かす縮退にしない。
- 依存先の障害を検知して呼び出しを止める circuit breaker の既定値は [ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md) に従う。

## 半死状態への備え

- **半死**：完全には止まらず、応答が極端に遅い、または一部の要求にしか応答しない状態。単純な死活監視では切り替えや切り離しが起きず、遅れが積み重なると業務が回らなくなる。

半死への備えは、要件と設計で受け持つ範囲を分ける。

- 要件では、業務への影響で稼働率を数える方針だけを定める。応答時間やエラー率の閾値は要件に含めない。数え方は[高可用性要件と稼働率の扱い](availability-high.md)に従う。
- 設計では、処理の成否まで確かめるヘルスチェック、閾値による監視、circuit breaker による切り離しで半死を検知して切り離す。
- どこまで作り込むかは、業務が許容できない劣化を起点に、コストと比べて決める。
