# 災害対策と事業継続の要件

復旧レベルは RTO と RPO から、バックアップとリストア、パイロットライト、ウォームスタンバイ、マルチサイトのいずれかを選ぶ。
待機サイトは、データを置ける場所を先に確かめ、そのうえで同時被災の回避、レイテンシ、コストで選ぶ。
システムの復旧順序と冗長の水準は、事業継続計画（BCP）の業務の優先順位と継続体制に揃える。

データを失わないための備えは前提とし、[可用性要件の定め方](availability-requirements.md)の「データ保全の要件」に従う。
DB の緊急事態ごとの対策とバックアップは[PostgreSQLのバックアップと災害対策](../database/postgresql-backup-and-recovery.md)に従う。

## 復旧レベル

速く戻せる方式ほど待機環境を厚く持つため、コストが上がる。
許容できる RTO と RPO を満たす、最も軽い方式を選ぶ。

| 方式                   | 概要                                                                                | RTO と RPO の目安              | コスト   |
| ---------------------- | ----------------------------------------------------------------------------------- | ------------------------------ | -------- |
| バックアップとリストア | 待機環境を持たず、被災後にバックアップから環境を作って復旧する                      | どちらも数時間以上             | 低       |
| パイロットライト       | データを常時複製し、DB などの中核だけを用意する。被災時にアプリケーションを起動する | RTO は数十分、RPO は数分       | 低から中 |
| ウォームスタンバイ     | 縮小した待機環境を常時動かし、被災時に本番の規模へ拡張する                          | RTO は数分、RPO は数秒から数分 | 中から高 |
| マルチサイト           | 複数のリージョンで本番を常時動かし、同時に処理する                                  | どちらもほぼゼロ               | 高       |

## 待機サイトの置き場所

- **データ主権と法規制**：最初に、国外にデータを置いてよいかを確かめる。個人情報の保護やデータの国外移転の規制で、置ける場所が絞られる。扱うデータによっては、準拠法が国内法か、国内の裁判所で係争できるかを契約時に確かめる。制約の洗い出しは[非機能要件定義の進め方](definition-process.md)に従う。
- **同時被災を避ける距離**：本番と待機サイトが近いと、同じ地震や広域停電で共倒れになる。十分に離れたリージョンを選ぶ。
- **レイテンシとコスト**：離れるほど、平常時のデータ複製の遅延、データ転送費、二重運用のコストが増える。

## 事業継続計画との整合

- 被災時に戻す業務の優先順位（Critical、High、Medium など）を事業の重要度で決め、システムの復旧順序をそれに従わせる。
- 業務を回す代替拠点、要員、業務手順の継続まで含めて備える。システムが戻っても、業務を回す人と場所がなければ事業は再開できない。
- システムの冗長の水準だけを突出させない。複数リージョンのような高価な冗長は、業務側の継続体制と整合する場合に限って採る。

災害の検知と DR の発動基準、本番の復旧後の切り戻し、DR 訓練の頻度は運用の要件で定める。
定義項目と値の例は[可用性の定義項目チェックリスト](availability-checklist.md)の「災害対策と事業継続」に示す。
