# 非機能要件のフレームワークと用語

フレームワークは非機能要件の抜けを点検するために使い、項目を上から順に埋める台帳にしない。
組織で使われているフレームワークがあれば流用し、なければドメインの標準を基準に置いて、足りない観点を補う。
優先順位はフレームワークではなく、システム固有の重要ドライバで決める。

重要ドライバとベースラインの扱いは[非機能要件定義の進め方](definition-process.md)に従う。

## 類似する用語

docs では「非機能要件」と呼ぶ。
同じ対象を指す次の用語は、出自と範囲が少しずつ異なる。

- **非機能**：機能以外の特性をまとめて指す、伝統的な呼び方。
- **品質特性**：ISO/IEC 25010 の品質モデルに基づく呼び方。明示的なニーズと暗黙のニーズを満たす製品の能力を指す。
- **アーキテクチャ特性**：Mark Richards と Neal Ford の『ソフトウェアアーキテクチャの基礎』による呼び方。ドメインに依存しない設計上の考慮事項のうち、設計の構造に影響し、アプリケーションの成功に欠かせないものを指す。
- **イリティ**：Availability、Reliability、Maintainability のように「-ility」で終わる特性の総称。

## 選び方

1. 組織（発注者または自社）で慣習的に使われているフレームワークがあれば、それを流用する。
2. ドメインで標準とされるフレームワークがあれば、それを基準に置く。国内の業務システムなら IPA 非機能要求グレードか ISO/IEC 25010、政府情報システムならデジタル社会推進標準ガイドラインが該当する。
3. システムの性質から、足りない観点を補う。IPA 非機能要求グレードはシステム基盤に特化しており、ユーザビリティ、アクセシビリティ、テスタビリティ、オブザーバビリティを含まない。これらが重要なら ISO/IEC 25010 から取り込むか、独自の項目として加える。

## IPA 非機能要求グレード

- 情報処理推進機構（IPA）が、システム基盤への発注者の要求を見える化するために策定した。
- 6の大項目（可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境・エコロジー）の下に、35の中項目、118の小項目、238のメトリクスを階層で整理し、要求レベルを段階で示す。
- 社会的影響の大きさに応じた3つのモデルシステム（ほとんどない、限定される、極めて大きい）を、ベースラインとして選べる。
- IPA による更新と保守は終了している。クラウドや現在の開発手法と合わない前提とメトリクスは、プロジェクトに合わせて変える。

## JUAS 非機能要求仕様定義ガイドライン

- 日本情報システム・ユーザー協会（JUAS）が2008年に発行した。
- 発注者の視点と検証できることを重視し、230の項目について、確認すべき項目、確認のプロセス、検証方法、必要な文書を整理している。
- 10の大分類は、ISO/IEC 25010 の前身である ISO/IEC 9126 の品質特性を下敷きにしている。
- クラウドの普及や近年のセキュリティインシデントを反映していない。

## ISO/IEC 25010

- システムとソフトウェアの品質モデルを定める国際規格で、SQuaRE シリーズの中核にあたる。
- 2023年の改訂で、製品品質モデルは9つの品質特性（機能適合性、性能効率性、互換性、相互作用性、信頼性、セキュリティ、保守性、柔軟性、安全性）になった。各特性は副特性に分かれる。
- 2011年版の使用性は相互作用性に、移植性は柔軟性（移植性はその副特性）に再編され、安全性が加わった。

## デジタル社会推進標準ガイドライン

- デジタル庁が定める、政府情報システムの整備と管理の共通ルール。
- 要件定義書に書く非機能要件として、次を定めている。
  ユーザビリティ及びアクセシビリティ、システム方式、規模、性能、信頼性、拡張性、上位互換性、中立性、継続性、情報セキュリティ、情報システム稼働環境、データマネジメント、テスト、移行、引継ぎ、教育、運用、保守。
