# 帳票の定義と分類

人が利用する前提で、レイアウトが固定され、出力後に内容が変わらず、視認性を保つ文書を帳票とする。
帳票は、対外、対内、法定の業務分類と、単票、鑑と明細、リスト、ラベルの表現形式の二軸で分類する。
表形式のデータ出力、印刷用 CSS を当てた画面、SVG による描画は帳票として扱わない。

## 帳票の定義

次の3条件をすべて満たす出力物を**帳票**とする。

- 人が利用する前提の文書である。
- レイアウトが固定され、出力した時点から内容が変わらない。
- 人が読み取れる視認性を保っている。

受け取った側が OCR などで自動で取り込む出力物も、帳票として扱う。
AI エージェントが内容を参照する出力物も、人の確認や承認を含むなら帳票として扱う。
人が確認せず AI エージェントだけで処理が完結する出力は帳票ではなく、[システム間連携の方式選択](../integration/interface-integration-patterns.md)に従う。

## 対象の媒体

帳票の媒体は紙、PDF、Excel とする。
Excel は、罫線などのレイアウト、印刷範囲、改ページを持つものだけを帳票とする。

## 帳票として扱わない出力

- **データ出力**：一覧や明細の表をそのまま CSV や Excel にする出力。二次利用の素材であり、レイアウトに意味を持たない。
- **印刷用の画面**：印刷用 CSS を当て、ブラウザの印刷機能で出す HTML。ブラウザの種類や余白、フォントの設定でレイアウトが変わるため、画面の一種として扱う。
- **SVG による描画**：座標を指定して描く SVG の帳票。改ページ制御の実装と保守の知見が少ないため扱わない。

レイアウトを組んで視認性を高めた Excel は、データ出力ではなく Excel 帳票として扱う。

## 業務分類

帳票は、誰に何のために出すかで分類する。
分類は、デザイン、セキュリティ、保存義務の要件を決める基準にする。

| 区分 | 分類           | 例                                                       | 優先する要件                 |
| ---- | -------------- | -------------------------------------------------------- | ---------------------------- |
| 対外 | 証憑           | 見積書、注文書、納品書、請求書、領収書、契約書           | デザインと証憑としての正確性 |
| 対外 | 顧客レポート   | 利用明細書、残高証明書、運用レポート                     | デザインと正確性             |
| 対内 | 伝票           | 入金伝票、出金伝票、振替伝票、仕入伝票、売上伝票         | 網羅性と作業効率             |
| 対内 | 帳簿           | 仕訳帳、総勘定元帳                                       | 網羅性                       |
| 対内 | 現場指示と管理 | ピッキングリスト、生産指示書、現品票、在庫一覧表、棚卸表 | 作業効率                     |
| 法定 | 税務と労務     | 源泉徴収票、給与支払報告書、社会保険の届出書             | 様式と保存期間の厳格な準拠   |
| 法定 | 業法上の義務   | 製造記録、法定点検記録簿                                 | 様式と保存期間の厳格な準拠   |

区分ごとに次の方針をとる。

- 対内帳票は取引先との合意が要らないため、画面、BI、タブレットなどへの置き換えを先に検討する。
- 対外帳票は取引先との関係と税務上の証憑に関わるため、一方的に廃止しない。
- 対外帳票は、PDF の配信への移行と、データ連携への移行を長期で検討する。
- 法定帳票は法改正で様式が変わるため、自前で開発する前にパッケージや SaaS の利用を検討する。
- 仕訳帳や総勘定元帳などの帳簿は帳票として作らず、訂正と削除の履歴を持つ DB として設計し、監査で必要なときだけ CSV などで出力する。

見積書から領収書までのように、元データ（商品、数量、単価）が同じで状態と件名だけが変わる帳票群がある。
こうした帳票群は帳票ごとにデータを持たず、共通の元データと状態から生成する。

## 表現形式

| 形式     | データ構造 | 実装上の要件                                                                                     | 例                                       |
| -------- | ---------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| 単票     | 1対1       | 1件のデータを固定のレイアウトに配置し、明細の増減を考慮しない                                    | 配送伝票、会員申込書、源泉徴収票、入館証 |
| 鑑と明細 | 1対N       | 固定のヘッダーと可変の明細で構成し、明細がページ枠を超えたときの改ページと合計欄の表示を制御する | 請求書、納品書、見積書、注文書           |
| リスト   | N          | 一覧を連続して出力し、グループヘッダーと集計行を含むことが多い                                   | 在庫一覧表、チェックリスト               |
| ラベル   | N          | 特殊なサイズや連続用紙に小さな単票を繰り返して出力し、バーコードを含むことが多い                 | 配送ラベル、商品タグ                     |

鑑と明細は実装が最も難しいため、改ページの条件と合計欄を出すページを設計の初期に確定する。
リストは、画面での絞り込みとチェックボックスによる消し込み、または表計算ソフトでの集計への置き換えを先に検討する。

## 印字する日時と言語

帳票は出力した時点で内容が固定されるため、印字する日時の表示タイムゾーンと文言の言語は出力時に決まる。
帳票の生成処理でも、日時の保存と取得は[日時とタイムゾーンの規約](../datetime/timezone-conventions.md)に従い、`ZoneId.systemDefault()` に依存しない。
帳票を生成する側で表示タイムゾーンと言語をどう決めるかは未決定であり、最初の帳票を実装するときに ADR を起こす。
