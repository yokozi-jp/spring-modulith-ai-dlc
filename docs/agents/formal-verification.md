# 形式検証スキルの使い方

## 要約

- 形式検証スキル（`.agents/skills/formal-verify-*`）は、TLA+ のモデル、設定、変異をスキルごとに持ち、`tooling/formal-verify/` の共通の道具で検査する。
- 変更がスキルの「変更がこの検証に関わるか」のファイルに触れたら、`check.sh` と `mutants.py` を流す。
- 違反は本物の不具合かモデルの誤りかに切り分け、本物の不具合は不変条件やモデルを緩めずに既知の発見として残す。
- 同期コミットは、モデルがそのコミットのコードを写すと確かめてから進める。

## スキルの中身

各スキルのディレクトリは次のファイルを持つ。

- **`SKILL.md`**：約束（不変条件）、設定と期待する結果、切り分けの手がかり、関わるファイル、コードとの対応表、変異、範囲と前提、既知の発見、同期の記録。
- **`model/<モジュール>.tla`**：モデル。
  `model/` に置く `.tla` は一つだけにし、`check.sh` はそれを検査する。
- **`model/<設定>.cfg`**：TLC の設定。
  1 行目を `\* expect: pass` か `\* expect: <TLC が報告すべき不変条件>` にする。
- **`model/mutants.toml`**：コードの退行を写す変異。
  書き方は「変異を書く」にある。

## 検査を実行する

リポジトリのルートで、スキルのディレクトリを渡して実行する。

```bash
tooling/formal-verify/check.sh .agents/skills/<スキル名>
tooling/formal-verify/check.sh .agents/skills/<スキル名> <設定>...
tooling/formal-verify/mutants.py .agents/skills/<スキル名>
```

`check.sh` は、渡した設定か `model/*.cfg` のすべてを TLC で検査し、結果が 1 行目の `expect:` と一致すれば `OK`、違えば `FAIL` を出す。
すべて一致すれば 0 で終わる。
TLC の出力は `FAIL` の設定の分だけ `~/.cache/formal-verify-tla/runs/` に残し、その場所を出す。
TLC と Java の版は `check.sh` の先頭で固定している。
初回は TLC を取得して SHA-256 で確かめ、Java を mise で入れるため、ネットワークが要る。
Kiro Web では先に `source docs/local-env-setup/kiro-web.sh` を実行する。

TLC は最初に見つけた違反で止まる。
そのため、違反を期待する設定は、その不変条件が破れることだけを示し、同じ設定に並べたほかの不変条件が成り立つかは示さない。

`mutants.py` は、`model/mutants.toml` の変異ごとに、まず変異を入れないモデルで対照の検査をし、次に変異を入れたモデルで変異の不変条件を一つずつ検査する。
すべての対照が通り、すべての不変条件が `caught` なら 0 で終わる。
出力の行の先頭の語は次のとおり。

- **`control`**：変異を入れないモデルが、変異の設定とすべての不変条件で成り立つ。
- **`caught`**：変異を入れたモデルで、TLC がその不変条件の違反を報告した。
- **`VACUOUS`**：変異を入れないモデルが、すでに変異の設定で成り立たない。
  変異がなくても出る違反なので、変異は何も示さない。
- **`MISSED`**：変異を入れても、TLC がその不変条件の違反を報告しない。
  不変条件か設定が、守るはずの退行を捕まえていない。
- **`FAIL`**：変異の `old` がモデルにちょうど一度は現れないか、設定の定数を書き換えられない。

`VACUOUS` と `MISSED` の行の下には、`check.sh` の出力が続く。
モデル、設定、変異のどれかを変えたら、`check.sh` と `mutants.py` の両方を流す。

## 結果を読む

TLC の結果は `/statechart` スキルで読む。
違反の経路は、スキルの対応表でコードの場所に置き換えて読む。

## 違反を切り分ける

`check.sh` が `FAIL` を出したら、本物の不具合かモデルの誤りかを次の順に切り分ける。

1. 経路の各ステップを、スキルの対応表でコードの場所に置き換える。
2. 各ステップがコードで一つの不可分な操作（一つの SQL の文、コミットまで他から見えないトランザクション、メモリの中の一つの判断）か、その順序がコードで起こりうるかを確かめる。
   スキルの「切り分けの手がかり」に、そのモデルで確かめる箇所がある。
3. 起こりえないなら、モデルのどの行がコードと違うかを直し、`check.sh` と `mutants.py` を流し直す。
4. 起こりうるなら本物の不具合である。
   不変条件やモデルを緩めて通さない。
   経路をコードの言葉の短い手順にして利用者に報告し、製品のコードは利用者が頼んだときだけ直す。
5. 本物の不具合をすぐに直さないなら、「既知の発見を残す」に従って残す。

## 既知の発見を残す

既知の発見は、今のコードで破れる約束である。
破れる不変条件ごとに、次のように残す。

1. その不変条件の違反を期待する設定を足す。
   1 行目を `\* expect: <不変条件>` にし、次の行に既知の発見であることと、どの設定と同じ値かを書く。
2. 同じ値の設定でほかの約束を検査し続けるなら、その設定からは破れる不変条件だけを外し、`\* expect: pass` のまま残す。
3. スキルの「既知の発見」に、経路をコードの言葉の番号つきの短い手順で書き、破れたときの害と、まれである理由を添える。
4. 発見が直ったら、足した設定を消し、外した不変条件を元の設定に戻し、「既知の発見」から消す。

## 意図した変更でモデルを直す

1. 変えたコードをスキルの対応表で引き、対応するアクションをコードの新しい振る舞いに合わせて書き換える。
   新しい不可分な操作はアクションにし、`Next` と対応表に足す。
2. 新しい約束は不変条件にし、それを破る変異を `mutants.toml` とスキルの変異の表に足す。
3. `check.sh` と `mutants.py` を流し、違反が出たら「違反を切り分ける」に従う。
4. スキルの設定の表、範囲と前提、既知の発見を結果に合わせる。
5. 「同期コミットを進める」に従う。

## 同期コミットを進める

スキルの「同期の記録」は、モデルがコードを写すと最後に確かめたコミットと、そのとき読んだライブラリの版とクラスを持つ。
「変更がこの検証に関わるか」のコマンドが差分を出したら、モデルを読み直すまで検査の結果を信じない。

1. 差分の各箇所を読み、対応表のアクションとモデルの行がその振る舞いを写すかを確かめる。
2. ライブラリの版が変わったら、同期の記録にあるクラスを新しい版のソースで読み直す。
3. 違いがあれば「意図した変更でモデルを直す」に従う。
4. 確かめたコミットの完全なハッシュを、同期の記録と、関わるかのコマンドに書く。
   確かめていないコミットへ進めない。
5. スキルを直したら、[スキルの取得元と更新](skill-sources.md)の「このリポジトリで書くスキルを記録する」に従って `skills-lock.json` の `computedHash` を直す。

読み直しの作業は `/maintain-formal-verification-skill` で行ってよい。

## 変異を書く

`model/mutants.toml` には、変異ごとに `[[mutant]]` を一つ書く。
次は `tooling/formal-verify/fixtures/counter/model/mutants.toml` の変異である。

```toml
[[mutant]]
name = "off-by-one"
change = "the guard lets the counter pass Limit"
config = "holds"
invariants = ["AtMostLimit"]

[[mutant.edits]]
old = '''Next == n < Limit'''
new = '''Next == n <= Limit'''
```

- **`name`、`change`**：変異の名前と、それが写すコードの退行。
- **`config`**：元にする `model/` の設定の名前。
- **`overrides`**：設定の定数の書き換え。
  省いてよい。
- **`invariants`**：変異が破るべき不変条件。
  対照はこれらをまとめて検査し、変異はそれぞれを一つずつ検査する。
- **`edits`**：モデルの書き換え。
  適用の順に、`old` がその時点のモデルにちょうど一度だけ現れる必要がある。
  TLA+ の `\` と `'` をそのまま書けるよう、TOML のリテラル文字列（`'''`）で書く。
- **`control_overrides`**：対照だけに使う定数の書き換え。
  退行が起動時の検査（モデルの `ASSUME`）を緩めるもので、変異を入れないモデルが `overrides` の値を拒むときだけ書き、検査が受け付ける値にする。

`VACUOUS` が出たら、`overrides` が退行と関係のない違反を起こしていないかを見る。
変異は、設定の値ではなく、写したコードの退行で約束を破るものにする。

## 共通の道具を変える

`tooling/formal-verify/` を変えたら、`task formal-verify-test` を実行する。
ケースは `tooling/formal-verify/test.sh` にある。
