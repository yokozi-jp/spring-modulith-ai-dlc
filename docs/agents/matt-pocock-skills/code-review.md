# 規約と仕様を分離して確認する code-review リファレンス

この文書は実行用の `SKILL.md` ではなく、固定した上流版の日本語リファレンスである。
プロジェクトでの運用は [Matt Pocock スキル運用](workflow.md) を優先する。

## 二軸レビューの概要

`code-review` は、利用者が指定した固定点と `HEAD` の差分を二つの軸でレビューする。
Standards 軸はリポジトリの明文化されたコーディング規約への適合を確認し、Spec 軸は元の課題または仕様への適合を確認する。
二つの軸は互いのコンテキストを混ぜないよう、並列の sub agent で実行し、最後に並べて報告する。

## 使う場面

ブランチ、プルリクエスト、作業途中の変更、特定の固定点以降の変更をレビューするときに使う。

## レビューの入力と前提

コミット SHA、ブランチ名、タグ、`main`、`HEAD~5` など、比較の固定点が必要である。
利用者が固定点を指定しなかった場合は質問する。

課題管理システムは事前に提供されている必要がある。
`docs/agents/issue-tracker.md` がない場合は、利用者に `/setup-matt-pocock-skills` の実行を案内する。

## 二軸レビューの手順

### 固定点と差分の確定

利用者が示した値を固定点とする。
差分コマンドを `git diff <fixed-point>...HEAD` として一度だけ確定し、merge base に対する三点差分を使う。
`git log <fixed-point>..HEAD --oneline` でコミット一覧も記録する。

先へ進む前に、`git rev-parse <fixed-point>` で固定点を解決できることを確認する。
差分が空でないことも確認する。
不正な参照または空の差分は、二つの sub agent を起動する前に失敗として扱う。

### 仕様の探索

最初に、コミットメッセージ内の課題参照を探し、`docs/agents/issue-tracker.md` の手順で取得する。
次に、利用者が引数として渡したパスを探す。
その次に、ブランチ名または機能名に対応する仕様を `docs/`、`specs/`、`.scratch/` から探す。

見つからない場合は、仕様の場所を利用者へ質問する。
利用者が仕様はないと答えた場合は Spec sub agent を省略し、最終報告に仕様がないことを記す。

### 規約と smell baseline の収集

`CODING_STANDARDS.md` や `CONTRIBUTING.md` など、コードの書き方を定めるリポジトリ内文書を探す。
これらに加え、リポジトリに文書がない場合も次の Fowler code smell baseline を Standards 軸へ必ず渡す。

- **Mysterious Name**：役割または保持内容を表さない関数名、変数名、型名であり、名前を変え、正直な名前が付かないなら設計を見直す。
- **Duplicated Code**：複数の差分箇所またはファイルに同じ形のロジックがあり、共通部分を抽出して双方から呼ぶ。
- **Feature Envy**：自身よりほかのオブジェクトのデータへ多くアクセスするメソッドであり、そのデータを持つ側へ移す。
- **Data Clumps**：同じ少数のフィールドまたは引数が繰り返し一緒に移動しており、一つの型へまとめる。
- **Primitive Obsession**：固有の型に値するドメイン概念をプリミティブ値または文字列で表しており、小さな型を与える。
- **Repeated Switches**：同じ型に対する同じ `switch` または `if` の連鎖が変更内で繰り返されており、polymorphism または両方で共有する一つの map に置き換える。
- **Shotgun Surgery**：一つの論理変更が多数のファイルへ散在した編集を要求しており、一緒に変わるものを一つのモジュールへ集める。
- **Divergent Change**：一つのファイルまたはモジュールが複数の無関係な理由で編集されており、変更理由ごとに分ける。
- **Speculative Generality**：仕様にない必要性のために抽象化、引数、hook を追加しており、実際の必要が生じるまで削除またはインライン化する。
- **Message Chains**：呼び出し元が依存すべきでない長い `a.b().c().d()` の走査であり、最初のオブジェクト上の一つのメソッドへ隠す。
- **Middle Man**：ほとんどを委譲するだけのクラスまたは関数であり、取り除いて実際の対象を直接呼ぶ。
- **Refused Bequest**：継承内容の大半を無視または上書きする subclass または implementer であり、継承をやめて composition を使う。

明文化されたリポジトリ規約は baseline より優先する。
リポジトリ規約が baseline なら指摘する形を明示的に認めている場合は、その smell を抑制する。
baseline の smell は常に判断を要する heuristic として名前を付け、規約違反として断定しない。
ツールがすでに強制する事項は報告しない。

### 二つの sub agent の並列実行

Standards sub agent には、完全な差分コマンド、コミット一覧、規約文書の一覧、smell baseline の全文を渡す。
規約違反は該当するファイルまたは差分箇所ごとにすべて報告させ、規約文書と規則を引用させる。
smell は名前を示して差分箇所を引用させる。
明文化された規約違反は強い指摘にできるが、baseline の smell は常に判断を要し、リポジトリ規約が baseline より優先することを区別させる。
ツールが強制する事項は省かせ、報告を400語未満にする。

Spec sub agent には、完全な差分コマンド、コミット一覧、仕様のパスまたは取得した内容を渡す。
仕様で求めたが未実装または部分実装の要件、求められていない差分内の振る舞い、実装済みに見えるが誤っている実装を報告させる。
各指摘では仕様の該当行を引用させ、報告を400語未満にする。

仕様がない場合は Spec sub agent を起動しない。

### 二軸の集約

二つの報告を `## Standards` と `## Spec` の見出しの下へ、そのまま、または軽く整えて掲載する。
二軸を意図的に分けているため、指摘を統合したり、軸をまたいで順位を付け直したりしてはならない。

最後に、軸ごとの指摘数と、存在する場合は各軸内で最も重大な問題を一行で示す。
二軸をまたぐ単一の最悪項目を選んではならない。

## 二軸を分ける理由

すべての規約に従っていても、求められたものと違う実装は Standards 合格、Spec 不合格になり得る。
仕様どおりでも、プロジェクトの規約を破る実装は Spec 合格、Standards 不合格になり得る。
二軸を分けて報告することで、一方が他方を隠すことを防ぐ。

## 完了条件と成果物

`## Standards` と `## Spec` の下に各報告を分け、軸ごとの指摘数と各軸内の最重大項目を一行で示せば完了である。
仕様がない場合は Spec 報告を省略した理由を記す。
成果物は Standards 報告、Spec 報告、軸ごとの一行要約である。

## 関連スキル

`docs/agents/issue-tracker.md` がない場合は、`setup-matt-pocock-skills` の実行を案内する。
原文には、ほかの関連スキルの指定はない。

## レビューするときの注意点

不正な固定点または空の差分を sub agent へ渡してはならない。
規約が baseline と競合するときは規約を優先し、smell を強い違反として扱わない。
二軸の指摘を統合または再順位付けしてはならない。
