# 振る舞いをテスト駆動で実装する TDD リファレンス

この文書は実行用の `SKILL.md` ではなく、固定した上流版の日本語リファレンスである。
プロジェクトでの運用は [Matt Pocock スキル運用](workflow.md) を優先する。

## 保守できるテストの概要

TDD は、失敗するテストを先に作り、そのテストを通す最小実装を作る反復である。
このスキルは、残す価値のあるテストの条件、テストを置くシーム、避けるパターン、反復の規則を定める。
各節は反復後ではなく、反復前と反復中の毎回に適用する。

## 使う場面

機能または不具合修正をテストから作るとき、red と green の反復を求められたとき、統合テストを作るときに使う。

## テスト開始前の入力と前提

コードベースを調査する場合は、`GLOSSARY.md` が存在すれば読み、テスト名とインターフェースの語彙をプロジェクトのドメイン言語に合わせる。
対象領域の ADR を尊重する。

テストを書く前に、対象とするシームを書き出して利用者の確認を得なければならない。
未確認のシームにはテストを書いてはならない。
利用者には、公開インターフェースが何か、どのシームをテストするかを確認する。

## 良いテストの条件

テストは実装詳細ではなく、公開インターフェースを通じて振る舞いを検証する。
内部実装を全面的に変更しても、振る舞いが同じならテストは維持できる必要がある。

良いテストは仕様として読める名前を持ち、利用者または呼び出し元が必要とする能力を明示する。
公開 API だけを使い、内部リファクタリングに耐え、どのように実装したかではなく何ができるかを記述する。
一つのテストは、一つの論理的な assertion に絞る。

期待値は、既知の正しいリテラル、計算済みの例、仕様など、実装とは独立した根拠から得る。
たとえば合計計算では、実装と同じ集計処理で期待値を作らず、既知の合計値を使う。

## テストを置くシーム

**シーム**は、内部へ立ち入らずに振る舞いを観測する公開境界である。
テストは内部ではなくシームに置く。
すべてをテストすることはできないため、事前にシームへ合意し、重要な経路と複雑なロジックへ労力を集中する。

インターフェースの深さ、シームの位置、公開内容が未決の場合は、Skill ツールで `codebase-design` を呼び出して語彙を参照する。
これはモジュール、インターフェース、深さ、シーム、アダプター、leverage、locality の共有語彙を参照する用途であり、セッションとして実行するものではない。

## red から green へ進む手順

最初に、対象のシームで失敗するテストを一つ書く。
そのテストが失敗することを確認してから、通すために必要な最小限のコードだけを書く。
将来のテストを先読みせず、推測に基づく機能を追加しない。

一回の反復では、一つのシーム、一つのテスト、一つの最小実装だけを扱う。
一つのテストと一つの実装を終えてから、直前の反復で得た知見を次の tracer bullet に反映する。

リファクタリングは red から green への反復に含めない。
リファクタリングは `code-review` の段階で行う。

## モックを使える境界

モックはシステム境界だけで使う。
対象は外部 API、時刻、乱数であり、データベースとファイルシステムは場合によって対象になる。
データベースにはテスト用データベースを優先する。

自作のクラスやモジュール、内部 collaborator、制御下にあるものをモックしてはならない。

外部依存は内部で生成せず、dependency injection で渡す。
外部操作ごとに固有の関数を持つ SDK 形式のインターフェースを、条件分岐を持つ汎用 fetcher より優先する。

SDK 形式では、各モックが一つの具体的な形を返せる。
テスト設定の条件分岐が不要になり、テスト対象の endpoint が明確になり、endpoint ごとの型安全性を得られる。

## 避けるテスト

内部 collaborator のモック、private method のテスト、呼び出し回数や順序への assertion は、実装に結合したテストになる。
インターフェースを使わずデータベースを直接照会するなど、別経路で結果を検証してはならない。
振る舞いが変わっていないリファクタリングで壊れることと、名前が実現方法を記述していることは、実装結合の兆候である。

実装と同じ方法で期待値を再計算する tautological test を書いてはならない。
このテストは構造上常に実装と一致し、誤りを検出できない。

全テストを先に書いてから全実装を書く水平分割をしてはならない。
一括作成したテストは想像上の振る舞いや構造を検証しやすく、実装を理解する前にテスト構造を固定する。

## 完了条件と成果物

スキル全体に独立した完了条件は指定されていない。
各反復は、先に失敗を確認した一つのテストが最小実装で通れば完了する。
成果物は、公開インターフェースを通じて外部の振る舞いを表すテストと、そのテストを通す最小実装である。

## 関連スキル

インターフェースの形またはシームの位置が未決の場合は、`codebase-design` の語彙を参照する。
リファクタリングは、`code-review` の段階で扱う。

## TDD を行うときの注意点

テストは合意済みのシームだけに置く。
内部構造ではなく観測可能な振る舞いを検証し、期待値を実装から独立させる。
一回の反復を超える実装や、反復中のリファクタリングを行わない。
