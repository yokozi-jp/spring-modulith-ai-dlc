# Ask Matt のスキル選択リファレンス

この文書は実行用の `SKILL.md` ではなく、固定した上流版の日本語リファレンスである。
プロジェクトでの運用は [Matt Pocock スキル運用](../../matt-pocock-skills.md) を優先する。

## 概要

`ask-matt` は、状況に合うスキルまたはフローを選ぶルーターである。
フローとは複数のスキルを通る経路であり、多くの作業は一つのメインフローを進む。
二つの入口がメインフローへ合流し、それ以外は単独スキルまたは下層の語彙として使う。

## 使う場面

使うスキルやフローを思い出せないときに使う。
最初のエンジニアリングフローの前には、前提として `/setup-matt-pocock-skills` を実行し、Issue tracker、triage label、文書配置を設定する。
カスタムの Issue tracker も使える。

## 入力と前提

入力形式の指定はない。
作業の種類、作業ディレクトリの有無、対話だけで決められるか、複数セッションが必要かを判断材料にする。

## 手順

1. 作業ディレクトリ内で作業している場合は、最初に `/grill-with-docs` を使う。
このスキルは `/grilling` を使って対話し、学んだ内容を `GLOSSARY.md` と ADR に残す。
作業ディレクトリがない場合は、同じ `/grilling` を使うが記録を残さない `/grill-me` を使う。

2. すべての疑問を対話で決められるか判定する。
状態、業務ロジック、実際に見る必要がある UI など、実行可能な答えが必要ならプロトタイプへ迂回する。
元の作業から `/handoff` を作り、そのファイルを使って新しいセッションを開く。
`/prototype` で使い捨てコードを作り、疑問へ答える。
学んだ内容を `/handoff` で元のアイデアの作業へ戻し、元のスレッドから参照する。
プロトタイプは別ディレクトリに置くため、往復には `/handoff` を使う。

3. 複数セッションの実装か判定する。
複数セッションなら、`/to-spec` でスレッドを仕様に変え、`/to-tickets` でブロック関係を明記した tracer bullet のチケットへ分割する。

チケットは二つの方法のいずれかで進める。
`/implement` をチケットごとに実行する場合は、チケット間で `/clear` してコンテキストを空にする。
ローカル tracker では `.scratch/<feature>/issues/` 配下の一ファイルを一チケットとし、ブロッカーから手作業で進める。
実 tracker ではブロック関係をネイティブリンクにし、ブロッカーが完了したチケットを選ぶ。
各チケットは自己完結しているため、直前のチケットのコンテキストを保持しない。

`/implement-spec` を使う場合は、仕様全体を一回で進める。
このスキルはチケットをタスクグラフとして読み、準備できた frontier の implementer subagent を並列実行し、一つの integration branch に統合する。
実装を個別に操作するより、全体をオーケストレーションしたい場合に使う。

複数セッションでなければ、現在のコンテキストで `/implement` を実行する。

どちらの方法でも、実装は `/tdd` で red と green の小単位を進め、最後に `/code-review` で Standards と Spec の二軸を確認する。
`/implement` はチケットごとに両方を実行する。
`/implement-spec` の各 implementer は `/tdd` を使い、integration branch 全体へ一回の `/code-review` を実行する。
仕様全体が不要で、具体的な振る舞いをテストファーストで作るだけなら `/tdd` を単独で使う。
固定点に対して branch または PR をレビューするだけなら `/code-review` を単独で使う。

PR を作るときは、モデルが `/pr` を呼び、変更を示す最小の図、動作の前後証拠、一方向または双方向のドアの判断を本文へ入れる。

1. 実装後は `/retro` でループを閉じる。
特に作業が想定どおり進まなかった場合に、コードではなくエージェント環境への改善を提案する。
対象にはナビゲーション、機械的検査、`/code-review` が強制する coding standards、steering、tooling が含まれる。
機械的な誤りは決定的な検査にし、判断が必要な事項は coding standards にする。

## コンテキストの維持

`/grill-with-docs` から `/to-tickets` までは、圧縮も消去もせず、一つの切れ目のないコンテキストで進める。
その後の各 `/implement` は、チケットを入力として新しいコンテキストで始める。
`/retro` は対象セッションを消去する前に同じセッションで実行する。
消去後に実行する場合は、そのセッションのログを渡す。

この原則の上限は、最新モデルでおよそ十五万 token とされる smart zone である。
`/to-tickets` の前に上限へ近づいた場合は、推論が劣化したまま進めず、最寄りの工程境界で `/compact` して続ける。

## 作業が発生したときの入口

外部から来た不具合報告や機能要求には `/triage` を使い、agent ready な Issue にする。
`/to-tickets` が作ったチケットはすでに agent ready であるため、triage してはならない。

一見して解けない不具合、断続的な flake、二つの正常な状態の間で入った regression には `/diagnosing-bugs` を使う。
このスキルは、対象不具合で失敗する一つのコマンドによる短い feedback loop を得るまで推測せず、その後 regression test とともに修正する。
不具合を固定できる seam がないことが真因なら、事後分析から `/improve-codebase-architecture` へ渡す。

一セッションに収まらず、目的地までの道筋が見えない新規プロジェクトまたは巨大機能には `/wayfinder` を使う。
このフローは Issue tracker 上に decision ticket の共有地図を作り、一つずつ解決し、成果物ではなく判断を生み出す。
一セッションで保持できるアイデアには使わず、明確に範囲が定まった機能にも使わない。
地図が明確になったら実装せず、`/to-spec`、`/to-tickets`、`/implement` の順でメインフローへ合流する。
地図から直接 `/implement` へ進むとリンクされた詳細が失われるため、作業が本当に小さいと判明した場合に限る。

## コードベースの保守

`/improve-codebase-architecture` は、エージェントが扱いやすいコードベースを保つ時間があるときに使う。
このスキルは深くできる候補を提示し、選んだ候補を `/grill-with-docs` へ渡すアイデアにする。
候補の調査にはこのスキルを使い、選んだ候補の設計には `/codebase-design` を使う。

## 下層の語彙

`/domain-modeling` は、曖昧または多義的なドメイン用語を整理し、後戻りしにくい判断を ADR に記録する単一の語彙源である。
`/grill-with-docs` は、この規律で `GLOSSARY.md` を用語集として保つ。

`/codebase-design` は、module、interface、depth、seam、adapter、leverage、locality という deep module の語彙源である。
`/tdd` と `/improve-codebase-architecture` はこの語彙を使う。
言葉自体が問題なら直接使い、それ以外は上位のスキルから呼ばせる。

## 工程境界の選択

工程とは、対話、実装、QA など、一つのセッション内の作業のまとまりである。
次の五問を工程境界で上から順に判定し、最初の「はい」に対応する方法を選ぶ。
工程の途中では判定せず、続行するか、残作業を subagent へ分ける。

1. 次の工程が現在の工程を一次資料として必要とするか、次の工程が smart zone 内に収まるなら、そのまま続行する。
続行は情報を失わず、切替コストもないため最初に判定する。

2. 現在の探索、判断、行き止まりが次の工程に不要なら `/clear` を使う。
関連するコンテキストを消すと理由を失い、差分を読み直しても戻せない。
古いセッションは再開可能である。

3. 新しい harness、新しいディレクトリまたは repository、同僚への移動、工程途中で見つけた横作業の分岐なら `/handoff` を使う。
`/handoff` が提供するのは、どこへでも運べる Markdown ファイルである。
何も移動しない場合は使わない。

4. キーボードから離れても進められるほど範囲が明確なら、subagent へ送り、現在のセッションを保持する。
自動レビューが標準例である。

5. それ以外は、次の工程に必要な指示を付けて `/compact` を使う。
`/compact` は既定の着地点だが、最初に選んではならない。
続行以外の方法は、一次資料を情報量の少ない二次資料へ変える。

## 単独で使うスキル

`/grill-me` は、作業ディレクトリがなく、ローカルへ何も保存せずに計画、設計、文章などを対話で磨く場合に使う。
作業ディレクトリがある場合は、同じ対話と記録を提供する `/grill-with-docs` を使う。

`/grilling` は対話の基本処理であり、round、frontier、事実の調査と利用者による判断を扱う。
wrapper のない対話が必要な場合だけ直接使う。

`/prototype` は一つの設計上の疑問へ答える小さな使い捨てプログラムである。
コードの書き方は使い捨てにするが、結果は実装へ戻し、prototype 自体は main から分けた `prototype/<name>` branch に一次資料として残して実装 Issue から参照する。

`/research` は、一次資料の調査を background agent へ委ね、引用元を示した Markdown を repository に残す。
調査中も別作業を続け、完成した文書は `/grill-with-docs` へ渡す。

`/to-questionnaire` は、利用者やコードベースではなく別の人物が持つ知識が不足している場合に、非同期で回答できる質問票を作る。
返答は `/grill-with-docs` または `/to-spec` の材料にする。

`/wizard` は、基盤の provision、資格情報または CI secret の設定、第三者 dashboard の操作、一回限りの migration または cutover など、人間だけが実行できる作業に使う。
URL を開き、値を受け取り、`.env` と GitHub secrets へ書く対話型 Bash script を生成する。
エージェント自身ができる作業には使わない。

`/wait-what` は、直前の説明が伝わらなかったときに会話の途中で使う。
不足していたコンテキストを補い、`GLOSSARY.md` の語彙を使った平易な英語で説明し直す。

`/teach` は、現在のディレクトリを状態保存用 workspace として、複数セッションで概念を学ぶために使う。

`/writing-for-agents` は、skill、`AGENTS.md`、参照先 docs など、エージェントが読む文書を書くためのリファレンスである。

## 成果物

このスキル自体が作るファイルや永続的な成果物は、原文に記載がない。
選んだフローによって、仕様、チケット、コード、レビュー、調査文書などが作られる。

## 関連スキル

関連スキルは各節に示した `/setup-matt-pocock-skills`、メインフロー、入口、保守、語彙、工程境界、単独利用の各スキルである。

## 注意点

`ask-matt` 自体はモデルから自動起動しない設定である。
メインフローの最初の三段階は、`/to-tickets` が終わるまで同じコンテキストを維持する。
工程途中の `/compact` は作業の筋を失わせるため、工程境界でのみ選ぶ。
