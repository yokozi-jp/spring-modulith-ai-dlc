# ADR-012: プロパティベーステストとミューテーションテストを採用する

## Status

Proposed

## Date

2026-09-14

## Context

既存のテストはJUnit Jupiterの具体例、Springのスライステスト、実PostgreSQLを使う統合テスト、ArchUnitによる構造検査で構成されている。
JaCoCoは実行経路を測れるが、入力空間の境界をどこまで検証したかと、テストが振る舞いの変化を検出できるかは測れない。

現在の手書きプロダクションコードはアプリケーション設定が中心であり、業務値オブジェクトや純粋な業務計算はまだ存在しない。
この段階で全入力を対象とするテストや高いミューテーションスコアを必須にすると、設定コード向けのテストを量産し、将来の業務リスクと対応しない品質指標になる。
一方、テスト基盤を先に用意すれば、最初の業務ロジックから不変条件とテスト検出力を確認できる。

プロパティベーステストの候補にはjqwikとQuickTheoriesがある。
jqwikはJUnit Platformの独自TestEngineを使うため、JUnit Jupiterへ統一した既存規約とSpringのテストスライスをそのまま共用できない。
これは設計上の非互換だが、この開発環境でjqwikを採用できない決定的な理由は別にある。
jqwikのメンテナは2026年5月公開の1.10.0に、コーディングエージェントを標的とするプロンプトインジェクションを意図的に仕込んだ。
その内容は、エージェントに対しjqwikのテストとコードをすべて削除するよう指示するもので、ANSIエスケープで人間の端末表示からは隠され、CIログやエージェントが取り込む標準出力にだけ残る。
このリポジトリはAI-DLC、すなわちエージェント駆動を前提とするため、jqwikを実行することはテストとコードを破壊されるサプライチェーン上の危険を負う。
安全のためインジェクション導入前のバージョンへ固定すれば、将来のJDK対応やバグ修正を取り込めなくなり、後述するQuickTheoriesの停滞と同じ制約を、より悪い天井のもとで負う。
QuickTheoriesはJUnit Jupiterのテストメソッド内で動作し、生成、反例探索、縮小を既存スライステストへ追加できる。
QuickTheoriesの最新版0.26は2019年公開が最後で、実質的に更新が止まっている。
ただしテスト専用スコープで推移的依存を持たず、内部でバイトコード操作も行わないため、新しいJDKで壊れる要素が構造的に少ない。
実際、Java 25.0.2で`JacksonConfigTest`のプロパティテストがパスすることを確認済みである。
残る停滞リスクは、将来のJDK更新でQuickTheoriesが動作しなくなった時点で本ADRを再評価する形で管理する。

PITはテストを繰り返し実行するため、通常の単体テストやJaCoCoより実行コストが高い。
現時点では対象コードも少ないため、通常のpush前検証やpull requestの必須ジョブへ組み込まず、明示実行と手動CIで結果を蓄積する必要がある。

## Decision

プロパティベーステストにはQuickTheories 0.26を使い、JUnit Jupiterのテストメソッド内で実行する。
プロパティは任意入力を試すこと自体ではなく、往復則、冪等性、順序不変性、境界保存など対象コードの不変条件として記述する。
固定例で仕様を読みやすく示すテストは残し、境界の組合せが広い契約だけをプロパティへ置き換える。
失敗時にはQuickTheoriesが出力するseedと最小反例を使って再現する。

ミューテーションテストにはGradle PIT Plugin 1.19.0、PIT 1.22.1、PIT JUnit 5 Plugin 1.2.2を使う。
PIT 1.22.1はGradleプラグイン1.19.0の既定版であり、Java 25のクラスファイルに対応するASMを含む。
GradleプラグインによるJUnit Platform Launcherの自動追加は無効にし、Spring Boot BOMがJUnit 6.0.3へ揃えたLauncherを通常テストとPITで共用する。
変異対象は`com.example.demo`以下の手書き業務コードとする。
jOOQ生成コード、起動クラス、Springの設定と外部ライブラリを接続する配線クラスは除外する。
業務コードがまだ存在しない間は、変異対象がない実行を失敗にしない。

`task mutation-test`をローカルの共通入口とし、使い捨てのPostgreSQLとRedis、確定済みマイグレーションを使ってPITを実行する。
通常の`task verify`とpull requestの必須CIには含めない。
GitHub Actionsでは手動実行だけを提供し、HTMLとXMLのレポートを成果物として保存する。

導入時はミューテーションスコアの閾値を設定しない。
業務ロジックと対応テストが追加され、安定した基準値を取得した後に、対象パッケージごとの閾値と定期実行頻度を別途決める。

## Consequences

### Positive

- 日時のシリアライズなど入力範囲が広い契約を、固定例だけに依存せず検証できる。
- 既存のJUnit JupiterとSpringテストスライスを維持したままプロパティを追加できる。
- JaCoCoの網羅率とは別に、テストが振る舞いの変化を検出できるかを確認できる。
- 高コストなPITを通常の開発ループから分離し、必要なときだけ実行できる。
- 生成コードを除外するため、修正できない変異で指標が汚染されない。

### Negative

- QuickTheories 0.26は安定しているが、2019年公開が最後で実質的に更新が止まっている。テスト専用かつ推移的依存ゼロで現行JDKでの動作を確認済みだが、将来のJDKで動かなくなれば再評価が要る。
- プロパティの入力範囲と不変条件を誤ると、多数の例を実行しても業務上の欠陥を検出できない。
- PITは手動実行でも通常テストより時間がかかり、DBを使うテスト群の起動コストも負担する。
- 閾値を設定するまでは、ミューテーションの生存をCIが自動では拒否しない。

### Neutral

- 具体例テストとプロパティベーステストは目的が異なるため、両方を使い分ける。
- 業務モジュール追加後も`com.example.demo`以下の手書きコードは自動的にPIT対象へ入る。
- スコア閾値と定期実行への移行は、実測した所要時間と基準値を根拠に判断する。

## Alternatives Considered

### Alternative 1: jqwikを使う

- Description：JUnit Platform向けの専用TestEngineでプロパティを実行する。
- Pros：Java向けプロパティベーステストとして機能が多く、ジェネレータと縮小を宣言的に書ける。活発に保守されている。
- Cons：既存のJupiter統一規約とSpringスライスをそのまま共用できない。さらに決定的な問題として、メンテナが1.10.0にコーディングエージェント向けのプロンプトインジェクション（テストとコードの削除指示）を意図的に仕込んでおり、エージェント駆動のこのリポジトリでは実行自体が危険である。安全なバージョンへ固定すると保守の恩恵を受けられず、停滞したQuickTheoriesより悪い制約になる。

### Alternative 2: JUnitのパラメータ化テストだけを使う

- Description：境界値を開発者が列挙し、追加依存を持たない。
- Pros：既存のテスト基盤だけで完結し、実行結果が決定的で読みやすい。
- Cons：入力生成と反例の縮小がなく、開発者が想定しなかった組合せを探索できない。

### Alternative 3: PITをpull requestの必須ゲートにする

- Description：すべての変更でPITを実行し、スコア閾値を下回る変更を拒否する。
- Pros：テスト検出力の低下を変更ごとに自動検出できる。
- Cons：対象となる業務ロジックがまだなく、実行時間と閾値の基準値もないため、現段階ではコストに見合う判定にならない。

### Alternative 4: 業務ロジックが増えるまで導入しない

- Description：最初の業務モジュール追加時に両ツールを導入する。
- Pros：実在する業務不変条件と変異対象に合わせて初期設定できる。
- Cons：最初の実装時に基盤整備も必要になり、通常テストだけで設計が固定される可能性がある。
