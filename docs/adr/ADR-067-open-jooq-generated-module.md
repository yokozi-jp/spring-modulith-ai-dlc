# ADR-067: jOOQ の生成物を Spring Modulith の OPEN のモジュールにする

## Status

Proposed

## Date

2026-10-06

## Context

jOOQ の生成物は `backend/src/generated/jooq` の `com.example.demo.jooq` に置く（[jOOQコード生成物の管理](../database/jooq-codegen.md)）。
このパッケージはベースパッケージの直下にあるため、Spring Modulith は `jooq` をアプリケーションのモジュールとして扱う。
Spring Modulith は、モジュールのルートのパッケージの型だけを公開し、サブパッケージの型を内部の型として扱う。

main は今 `modulith` のスキーマだけを生成し、生成型はルートの `com.example.demo.jooq.Tables` とサブパッケージの `com.example.demo.jooq.tables` にある。
本番コードから生成型を使うクラスがまだないため、main ではモジュールの検査が失敗していない。

確認用のサンプル機能（[issue #122](https://github.com/yokozi-jp/spring-modulith-ai-dlc/issues/122) の `product` と `order`）を作るブランチで、生成の対象のスキーマを `modulith`、`product`、`order` の 3 つにした。
jooq-codegen 3.21 は、スキーマが 2 つ以上のとき、スキーマの定義とその下の `Tables`、テーブル、Record を `com.example.demo.jooq.<スキーマ名>` のサブパッケージに生成する。
ルートに残るのは `DefaultCatalog` だけで、ルートの `Tables` はなくなる。

この状態で `JooqProductRepository` が `com.example.demo.jooq.product.Tables.M_PRODUCT` を使うと、`ApplicationModules.verify()`（`ApplicationModuleArchitectureTest`）が「Module 'product' depends on non-exposed type com.example.demo.jooq.product.tables.MProduct within module 'jooq'」で失敗した。
最初の業務スキーマを足す変更でこの失敗が起きないよう、業務スキーマを足す前に main へ入れる。

生成先は `clean = true` で毎回消されるため、生成先に手書きのファイルを置いても次の生成で消える。
また `ProductionCodeOnlyTest` は、`com.example.demo.jooq` の本番のクラスのソースが `src/generated/jooq` にあることを求める。

## Decision

`com.example.demo.jooq` を Spring Modulith の OPEN のモジュールにし、すべての生成型を公開する。

- `backend/gradle/database.gradle` の `jooqCodegen` の `doLast` で、生成のたびに `src/generated/jooq/com/example/demo/jooq/package-info.java` を書く。
  中身は固定の文字列で、先頭に「This file is generated by backend/gradle/database.gradle (jooqCodegen)」のコメントを置き、`@ApplicationModule(type = ApplicationModule.Type.OPEN)` と `@NullUnmarked` を付ける。
- 生成物は null の契約を満たさないため、`@NullMarked` ではなく `@NullUnmarked` にする。
  Error Prone の `RequireExplicitNullMarking` は、明示した `@NullUnmarked` で満たす。
- `ProductionCodeOnlyTest` は、生成コードの基準の型をルートに残る `DefaultCatalog` にする。
- 機能モジュールの Repository は、スキーマごとの `Tables`（`com.example.demo.jooq.ordering.Tables.T_ORDER` など）のテーブルと列を使う。

## Consequences

### Positive

- 機能モジュールを足しても、生成型の公開の設定を足さずに済む。
- `package-info.java` が生成の手順の一部になり、再生成で消えず、手で書き直す必要がない。
- `ApplicationModules.verify()` は、機能モジュールの間の依存の検査を保つ。

### Negative

- Spring Modulith は、どの機能モジュールがどのスキーマのテーブルを使うかを検査しない。
  他モジュールのテーブルを直接読む誤りは、Spring Modulith ではなく、jOOQ の Repository の規約とレビューで防ぐ（[jOOQ の Repository](../backend/class-roles/jooq-repository.md) の「依存してはいけない型」）。
- `database.gradle` が Spring Modulith と JSpecify の注釈の名前を文字列で持つ。
  注釈のパッケージが変わると、生成物のコンパイルで気付く。

### Neutral

- [jOOQコード生成物の管理](../database/jooq-codegen.md)、[jOOQ の Repository](../backend/class-roles/jooq-repository.md)、[バックエンドのアーキテクチャテスト](../backend/architecture-tests.md) は、この ADR と同じ変更で、生成物のモジュールとスキーマごとの `Tables` に合わせて直した。

## Alternatives Considered

### 選択肢1: 生成型のパッケージごとに `@NamedInterface` を付ける

- **Description**：`com.example.demo.jooq.<スキーマ名>` と、その `tables`、`tables.records` に `@NamedInterface` を付け、使うモジュールに名前付きインタフェースとして公開する。
- **Pros**：公開する生成型を、スキーマの単位で選べる。
- **Cons**：スキーマを足すたびに、生成先の 3 つのパッケージに `package-info.java` を書く手順が要る。機能モジュールの側にも `allowedDependencies` を書かないと、スキーマを使うモジュールを絞れず、手間に見合う検査にならない。

### 選択肢2: スキーマを 1 つに保つ

- **Description**：業務テーブルを 1 つのスキーマにまとめ、ルートの `Tables` を保つ。
- **Pros**：生成のパッケージが変わらない。
- **Cons**：[ADR-011](ADR-011-use-module-owned-database-schemas.md) のモジュールごとのスキーマに反する。また、ルートの `Tables` の型もルートの外のテーブルのクラスを返すため、内部の型への依存の失敗は解消しない。

### 選択肢3: 生成先をベースパッケージの外にする

- **Description**：生成のパッケージを `com.example.jooq` のようにベースパッケージの外にし、Spring Modulith のモジュールにしない。
- **Pros**：Spring Modulith の検査の対象から外れ、注釈が要らない。
- **Cons**：ArchUnit の規則、`ProductionCodeOnly`、`CleanGeneratedTablesExtension` が `com.example.demo.jooq` の生成物を前提にしており、変更が広い。生成物がアプリケーションの一部であることがパッケージから読めなくなる。
