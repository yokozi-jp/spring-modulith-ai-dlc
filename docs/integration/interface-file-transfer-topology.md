# ファイル連携の構成とストレージの所有

組織内のファイル連携はハブ経由を原則とし、ハブには業務知識に依存しない汎用の処理だけを持たせる。
ファイルは配信側が書き込み、集信側が取りに行く。
直接連携では、配信側が所有するオブジェクトストレージを使う。

## 用語

- **ハブ**：システム間のファイル連携を仲介する中央の連携基盤。
- **スポーク**：ハブへ接続する個々のシステム。
- **直接連携**：ハブを介さず、システム同士が1対1でファイルを受け渡す構成。

配信側と集信側の定義は[システム間連携の方式選択](interface-integration-patterns.md)に従う。

## 構成の選択

- 組織内の連携ではハブを使う。
  既存のハブがあればそれを使い、なければ導入を検討する。
- 他社との連携は直接連携にする。
- ハブを導入できない組織内の連携は直接連携にする。
  将来ハブへ移せるよう、標準形式のファイルにし、この領域の規約（ストレージの所有、バケットの分け方、取り込み完了の示し方）を守る。

## ハブの責務

- ハブには、業務知識に依存しない汎用の処理だけを持たせる。
  - 形式の変換（CSV から Parquet など）
  - 文字コードの変換
  - 圧縮と展開
  - 機微なデータのマスキング
- 業務固有のロジックはスポークに持たせる。
- ハブを通すファイルは標準形式にそろえる。
  日付の形式、項目の物理名、データ型を組織のデータモデルに合わせ、ファイル形式は[連携ファイルの形式と CSV の書き方](interface-file-format.md)に従う。
- 連携先ごとに項目や鮮度を変えた個別のファイルを作らない。
  各集信側が受け入れる標準レイアウトを一つ決め、連携先と合意する。
  標準レイアウトを合意できない場合、ハブを使っても配信するファイルの数は減らない。

## ファイルを置く向き

- 配信側のスポークがハブへファイルを書き込み、ハブは配信側から取りに行かない。
- 集信側のスポークがハブからファイルを取りに行き、ハブは集信側へ書き込まない。
- 直接連携でも、配信側が書き込み、集信側が取りに行く。
- データ基盤への配信は、スポークが基盤へ書き込む。
  スポークを改修できない場合に限り、基盤がスケジュール起動で取りに行ってよい。

この向きにすると、スポークへのインバウンド通信を作らずに済む。

## オブジェクトストレージの所有

- ハブ経由の連携では、ハブが提供するオブジェクトストレージを使う。
- 直接連携では、配信側が所有するオブジェクトストレージを使い、集信側には読み取りに必要な権限だけを与える。
- 集信側が所有するストレージへ配信側が書き込む構成は採用しない。
  下流のリプレイスに上流が巻き込まれ、集信側が増えるたびに配信側が同じファイルを複数の場所へ送ることになるため。
- 配信側のストレージの費用、監視、監査、改廃、バックアップは、所有する配信側が責任を持つ。
- ストレージの所有は、連携が必要と分かった時点で連携先と調整する。
  構築後に所有を変えることはできないものとして扱う。
- 集信側がファイルの到着イベントを使う場合は、配信側のストレージのイベントを通知サービスやキュー経由で集信側へ渡す。
