# 連携用オブジェクトストレージのバケットとキー

集信用と配信用のバケットを分け、配信用のバケットは連携先ごとに分ける。
キーは連携先を含まない Hive 形式の日付階層にし、ファイル名にミリ秒までの UTC のタイムスタンプを付ける。
取り込みの完了は、集信側がオブジェクトタグで示す。

## 用語

- **個別バケット方式**：配信用のバケットを連携先ごとに分ける方式。
- **同報配信**：同じファイルを複数の連携先へ配信すること。
- **Hive 形式**：`dt=2026-10-01` のように `キー=値` の階層でパーティションを表すパスの形式。

ストレージをどのシステムが所有するかは[ファイル連携の構成とストレージの所有](interface-file-transfer-topology.md)に従う。

## バケットの分け方

- 集信用と配信用のバケットを分ける。
- 配信用のバケットは個別バケット方式にする。
- 配信用のバケット名は `{env}-{system}-outbound-{連携先}` の形にする（例：`stg-sales-outbound-crm`）。
- 連携先ごとのバケット作成は IaC のモジュールで定型化し、作成の手間を理由に共有バケットへ寄せない。
- 一つのバケットを複数の連携先で共有し、プレフィックスごとに権限を分ける方式は採用しない。
  設定ミスの影響がバケット全体へ及び、バケットポリシーのサイズ上限にも当たりやすいため。

## 同じファイルを複数の連携先へ渡す

- 連携先を名前に含むバケットやパスへ、別の連携先の読み取り権限を与えない。
- 同じファイルを複数の連携先へ渡すときは、各連携先のバケットへコピーして同報配信する。
- ハブがある場合、同報配信はハブが担う。

## オブジェクトキー

- キーに連携先を含めない。
  連携先はバケットで表す。
- データ種別の階層の下に、Hive 形式の日付の階層を置く。
  `dt=2026-10-01/` または `year=2026/month=10/day=01/` の形にし、`20261001/` のような値だけの階層にしない。
- 日付の階層は少なくとも日単位にし、月や週に丸めない。
- 時単位の階層を加えるかは、連携の頻度と1パーティションあたりのファイル数で決め、一覧取得がページングなしで済む数に収める。
- 業務日付を管理している場合、日付の階層には業務日付を使う。
- ファイル名にはミリ秒までのタイムスタンプを付け、名前の順が生成の順になるようにする。
  タイムスタンプは UTC で書き、末尾に `Z` を付ける（[日時とタイムゾーンの規約](../datetime/timezone-conventions.md)）。
- 随時連携のファイル名には、UUID v7 などの一意な値も付ける。
  一意な値を付ける場合、タイムスタンプは秒までにしてよい。
- 再送などで同じデータを置き直すときも、既存のオブジェクトを上書きせず、別の名前で置く。

キーの例を示す。

```text
stg-sales-outbound-crm/
  m_customer/dt=2026-10-01/m_customer_delta_20261001T063012123Z_0192a4b2-7c1e-7d3a-9f00-2b1c3d4e5f60.csv
```

## 取り込み完了の示し方

- 集信側は、取り込んだオブジェクトにタグを付けて完了を示す。
  オブジェクトの移動、リネーム、完了ファイルの配置は使わない。
- 集信側には、読み取りとタグ付けに必要な権限だけを与える。
- タグには処理状態と処理日時を持たせる。
  - `processing-status`：`unprocessed`、`processing`、`processed`、`error` のいずれか
  - `processed-timestamp`：`Z` 付きの RFC 3339 の日時（例：`2026-10-01T06:30:00Z`）
- 集信側のリプレイスで新旧のシステムが並行稼働する場合は、`v1-processing-status` のように版の接頭辞を付け、新旧の状態を分ける。
- 完了の示し方は、少なくともシステム内で一つに統一する。
- 集信側が完了状態を自分の DB だけで持つ方式は、ストレージから状態が見えないため採用しない。
- タグを付けられない転送先（FTP サーバーなど）では、移動またはリネームで完了を示す。
