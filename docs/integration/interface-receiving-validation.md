# 連携ファイルの検証と取り込み範囲

配信側は出力したファイルを実行時に検証せず、集信側がスキーマレベルと業務ロジックレベルの二段階で検証する。
スキーマレベルの検証はアプリケーションで行い、違反した行番号と項目名を出力する。
エラーのレコードが1件でもあればファイル全体を取り込まないことを原則とする。

## 用語

- **スキーマレベルの検証**：型、桁、必須、区分値、形式、範囲など、単項目の検証。
- **業務ロジックレベルの検証**：項目間の相関、レコード間の整合、マスタなど他のテーブルとの整合の検証。
- **受信ワークテーブル**：連携ファイルをそのままのレイアウトで格納するテーブル。

## 検証の分担

- 配信側は、出力したファイルを実行時に検証しない。
  出力の正しさはテストで確かめる。
- 集信側は、受け取ったファイルを必ず検証する。

## 集信時の検証

- スキーマレベルの検証は、DB の制約違反に任せずアプリケーションで行う。
- 違反ごとに、ファイル、行番号、項目名、違反した規則を出力する。
- 違反した値そのものはログに出さない。
  ログに出せる値は[可観測性データの規約](../observability/conventions.md)に従う。
- 業務ロジックレベルの検証は、スキーマレベルの検証を通ったデータを受信ワークテーブルへコミットした後、後続のジョブで SQL を使って行う。

## 受信ワークテーブル

- 受信ワークテーブルの列は、ファイルの項目定義に合わせた型と桁にし、管理用の列を加える。
- すべての列を可変長の文字列型で受け、後続のジョブで型の変換と検証を行ってもよい。
  この場合は、スキーマレベルと業務ロジックレベルの検証を同じトランザクションで行う。
- 受信ワークテーブルは、その連携を担当するモジュールが所有するスキーマに置く（[ADR-011](../adr/ADR-011-use-module-owned-database-schemas.md)）。
- 大きなファイルを受信ワークテーブルへ書き込む方法は[大量データの取り込み性能](interface-bulk-load.md)に従う。

## エラー時に取り込む範囲

- 原則として、エラーのレコードが1件でもあれば、ファイル全体を取り込まない。
- データの整合性よりデータの鮮度を優先する業務に限り、エラーのレコードを除いて取り込むことを検討する。
  除いたレコードは、後で直して取り込めるよう記録して追跡する。
