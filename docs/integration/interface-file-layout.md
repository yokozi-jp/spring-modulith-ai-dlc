# 連携ファイルのレイアウト

連携ファイルはデータ種別ごとに正規化した単一のレイアウトにし、親子のデータは別のファイルに分ける。
定時とマイクロバッチの連携では、0件でもヘッダー行だけの空ファイルを配信する。
調査のために、元テーブルの主キーとシステム共通項目を必ず含める。

## 用語

- **空ファイル**：ヘッダー行だけを持ち、データ行を持たないファイル。0バイトのファイルではない。
- **スナップショット属性**：注文時の単価のように、取引が成立した時点の値を固定して記録する項目。
- **マルチレイアウト**：一つのファイルに複数のレコード種別を混在させ、先頭の項目などで種別を区別する形式。

連携の頻度の分類は[ファイル連携の頻度と起動方式](interface-file-scheduling.md)に従う。

## 空ファイル

- 定時連携とマイクロバッチ連携では、抽出結果が0件でも空ファイルを配信する。
- イベント駆動の連携では、空ファイルを配信しない。
- 相手が空ファイルを配信できない場合は、集信側が未着を検知できず、停止の検知を相手の監視に任せることを連携先と合意する。

## 正規化

- データ種別ごとにファイルを分け、マスタの値をトランザクションのファイルへ横持ちしない。
- 連携先が限られ、将来の拡張がなく、参照用途に限る場合だけ、非正規化したファイルを例外として認める。
- スナップショット属性は、マスタの横持ちではないため、トランザクションのファイルに含める。

## 親子関係のあるデータ

- ヘッダーと明細は別のファイルにする（例：`orders` と `order_details`）。
- 明細にヘッダーの項目を横持ちしない。
- マルチレイアウトは、レガシーシステムや業界標準の形式に合わせる場合だけ使う。
- 別のファイルにしたヘッダーと明細の整合は、[連携データの整合性と冪等性](interface-data-consistency.md)に従って保つ。

## 取り消しの表し方

- 業務で登録の取り消しが起きるデータは、キャンセル区分やマイナス伝票などで取り消しを連携できるレイアウトにする。
- 取り消しを認めない期限を業務で決める場合は、その期限を連携仕様に書く。

## バイナリ

- 数KBから数MBの小さなバイナリ（アイコンなど）は、Base64 で項目に埋め込む。
- それより大きな画像、動画、オフィス文書、PDF は、配信側のオブジェクトストレージに置き、連携ファイルにはその参照を書く。
- 参照にはオブジェクトのバージョンを含め、ファイルを作った後の更新で別の版を取り込ませない。
- 機微な情報を含むバイナリは、版を指定した署名付き URL で渡すことを検討する。
  有効期限は集信側の最大の取り込み遅延に合わせ、再送するときは URL を再発行する。
  署名付き URL の使い方は[機密情報を含む連携ファイル](interface-file-security.md)に従う。

## ソート順

- 配信側は、特定のキーでソートしてファイルを出力する。
- 連携仕様にはソート条件を書き、集信側がレコードの並び順に依存してはならないことも書く。
- 集信側は、処理の順序が必要なら自分でソートする。
- ファイルをまたぐ順序は配信側が守り、前のファイルに入るべき古いレコードを後のファイルに入れない。

## 調査用の項目

- 元テーブルの主キーを含める。
- 作成日時、更新日時、更新トランザクション ID、更新番号などのシステム共通項目を、元テーブルにあれば含める。
- これらの項目は、集信側が使わなくても含める。
