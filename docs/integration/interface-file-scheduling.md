# ファイル連携の頻度と起動方式

連携の頻度はバッチ、サイクルバッチ、マイクロバッチの順に検討し、1件ごとのイベント駆動連携は採用しない。
定時連携の集信は門限後の定時起動、随時連携の集信はポーリングを原則とする。
ファイル作成イベントで集信を起動する場合は、同じイベントが複数回届く前提で冪等に取り込む。

## 用語

- **バッチ連携**：1日1回など、決めた時刻に大量のデータをまとめて連携する方式。
- **サイクルバッチ連携**：1時間ごとなど、短い間隔で定期的に連携する方式。
- **マイクロバッチ連携**：業務イベントを数十秒から数分ごとにまとめて連携する方式。
- **イベント駆動連携**：業務イベント1件ごとに連携する方式。
- **定時連携**：バッチ連携とサイクルバッチ連携の総称。
- **随時連携**：マイクロバッチ連携とイベント駆動連携の総称。
- **変更データキャプチャ（CDC）**：DB の変更ログから追加、更新、削除を取り出す仕組み。

## 連携の頻度

- 業務上どの程度の遅延が許されるかを、業務とシステムの両面から確認してから頻度を決める。
- バッチ、サイクルバッチ、マイクロバッチの順に検討し、要件を満たす最も低い頻度を選ぶ。
- バッチ連携で鮮度が足りない場合は、まず1日に複数回の起動か、時単位や分単位のサイクルバッチを検討する。
- マイクロバッチ連携は、データ鮮度が数分以内に求められる場合に使う。
- イベント駆動連携は採用しない。
  低い遅延が必要なら、マイクロバッチの間隔を短くする。
- アプリケーションの更新処理から同期的に連携データを配信する方式と、DB のトリガーで配信する方式は使わない。

## 配信処理

- 配信の最大遅延時刻を定め、集信側の門限チェックに使う（[連携ファイルの門限チェック](interface-arrival-deadline.md)）。
- 0件でも空ファイルを配信する（[連携ファイルのレイアウト](interface-file-layout.md)）。
- 大きくなりうるファイルは、全件をメモリに載せずストリーミングで書き込む。
- 前回の配信ジョブが終わる前に、次の配信ジョブを起動しない（[ジョブとファイルの順序制御](interface-job-ordering.md)）。
- 小さなファイルが大量にできて調査や分析で扱いにくくなる場合は、一定の粒度にまとめる処理を加える。

## マイクロバッチの差分抽出

- 間隔が数分以内のマイクロバッチでは、更新日時の列による差分抽出を使わず、CDC を使う。
- バッチ連携の差分抽出と、間隔を2時間程度まで延ばせるマイクロバッチでは、更新日時の列による抽出を使ってよい。
- 更新日時の列による抽出を使う場合は、物理削除を検知する方法を別に設計する。
- CDC は、自前で運用する CDC 基盤より、マネージドなサービスを優先する。

全件連携と差分連携の使い分けは[全件連携と差分連携](interface-full-and-delta.md)に従う。

## 集信処理の起動

- 定時連携の集信は、門限後の決めた時刻にスケジュールで起動し、ファイル作成イベントでは起動しない。
- 随時連携の集信は、数分の遅延が許されるならポーリングで起動する。
- 数秒単位の低い遅延が必要な随時連携に限り、ファイル作成イベントで起動する。
- ファイル作成イベントで起動する集信は、イベントの重複を前提に冪等にする（[連携データの整合性と冪等性](interface-data-consistency.md)）。
