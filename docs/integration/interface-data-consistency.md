# 連携データの整合性と冪等性

複数の配信ファイル間の整合は配信側が保ち、静止点、作成日時での絞り込み、行ロック、スナップショットの順に方式を検討する。
集信側は、関連するファイルを受信ワークテーブルまで到着順に書き込み、待ち合わせをワークフローエンジンで制御する。
集信は、同じファイルやレコードを再び受けても結果が変わらないよう冪等にする。

## 用語

- **静止点**：連携の対象テーブルを更新する処理が動いていない時間帯。
- **配信ワークテーブル**：配信ファイルの元にするデータを一時的に格納するテーブル。

受信ワークテーブルの定義は[連携ファイルの検証と取り込み範囲](interface-receiving-validation.md)に従う。

## 配信ファイル間の整合

- 親子関係のあるデータなど、複数のファイル間の整合は配信側が保つ。
  集信側に不整合の無視を求めない。
- 次の順に方式を検討する。
  1. オンライン処理や他のバッチと競合しない静止点で作成する。
  2. 追記だけのテーブルなら、作成日時で抽出の対象を絞り込む。
  3. 作成の前に、関係するテーブルを結合した `SELECT ... FOR UPDATE` で行ロックを取る。
  4. 1本の `INSERT ... SELECT` で配信ワークテーブルへコピーし、そこから各ファイルを作る。
  5. ヘッダーと明細を一つのファイルにまとめる。
- 4では、SQL で調査できるよう実テーブルの配信ワークテーブルを使う。
  小さなシステムでは一時テーブルでもよい。
- 4のコピーを複数のクエリに分けない。
- 5は、[連携ファイルのレイアウト](interface-file-layout.md)の例外の条件に当たる場合だけ使う。

## 集信ファイルの待ち合わせ

- 次の場合、集信側は関連するファイルがそろうまで後続の処理を待つ。
  - ヘッダーと明細のような親子のファイル
  - 複数のシステムから関連するデータを集める場合
  - マスタを更新してからトランザクションを取り込む必要がある場合
- 各ファイルは、到着した順に受信ワークテーブルまで書き込む。
- すべての受信ワークテーブルへの書き込みが終わった時点で後続を起動する制御は、ワークフローエンジンで行う。

## 冪等性

- 配信ワークテーブルを使う場合は、処理済みを示すステータス列を持たせ、処理済みのレコードを抽出から除く。
- 集信は、同じファイルやレコードを再び受けても結果が変わらないようにする。
  `MERGE` で反映するか、アプリケーションで重複を除く。
- キューやストレージのイベントを使う随時連携では、同じファイルが複数回届く前提にする。
- 定時起動の集信は `INSERT` で反映してもよい。
  ただし、運用をそろえるため、すべての集信を `MERGE` で反映することを優先する。
