# 非同期化の判断基準

処理は同期を既定とし、応答性、負荷の平準化、障害分離のいずれかを同期のままでは満たせない場合だけ非同期にする。
コンシューマーからさらに非同期処理を呼び出す連鎖は、代替手段で解決できず、前段と後段で処理の粒度が変わる場合に限る。
非同期にした理由は、[非同期処理の設計文書](async-design-documents.md)の設計意図として残す。

プロデューサー、コンシューマー、キューなどの用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## 非同期にする条件

次の三つの条件を順に確認し、どれかに当てはまる場合だけ非同期化を検討する。
どれにも当てはまらなければ、同期のまま実装する。

1. **応答性**：処理時間が長く、呼び出し元が応答を待てない。ただし、呼ばれる頻度が業務上限られ、運用上の工夫で待ち時間を許容できるなら同期のままにする。
2. **負荷の平準化**：突発的に大量の呼び出しが起こり得る。ただし、バーストの規模と時期を予測でき、事前のリソース増強で対応できるなら同期のままにする。
3. **障害分離**：外部システムや別のデータストアへの依存を本処理から切り離せる。ただし、依存先の障害で本処理が失敗してよく、失敗したデータを手作業で回復する運用費用が見合うなら同期のままにする。

応答性の例として、ファイル生成の要求は受付応答を即時に返し、生成を裏側で行い、完了を通知する。
障害分離の例として、DB とオブジェクトストレージの両方へ書く処理で片側だけにデータが残る状態を許容できないなら、後段の書き込みを非同期にして再試行で結果整合させる。

## 同期のまま残す処理の点検

同期処理の単純さを理由に、優先度の異なる処理を一つの同期処理へまとめない。
最優先の処理と重い付随処理が同じリソースを奪い合うと、ピーク時に付随処理の遅延が積み重なり、最優先の処理までタイムアウトする。

同期と非同期の判断には、非機能要件で想定するピーク時のアクセス数から求めたスループットを使う。
重い付随処理が要件を満たすかを机上で見積もり、[非同期処理のテスト](async-testing.md)の負荷テストで実測して確かめる。

## 非同期の連鎖

コンシューマーから別の非同期処理を呼び出す連鎖は、同期から非同期を呼び出す場合と同じく最小限にする。
連鎖が増えるほど、処理の追跡と障害の切り分けが難しくなる。

連鎖を検討する目的ごとに、先に次の代替を試す。

- **流量制御**：キューを分けて緩衝にせず、コンシューマーの同時実行数の上限で制御する（[非同期処理の流量制御と性能](async-flow-control.md)）。
- **データ整合性**：外部 API の成功を記録するためだけに非同期を分けず、同じコンシューマー内で外部 API を呼び出してから自 DB をコミットする。
- **並列化による性能改善**：言語機能による並列化で足りるなら、プログラム内で並列化する。
- **リカバリ単位の分割**：元のタスクを細かく分割できるなら、プロデューサー側で分割して発行する。

代替で解決できず、前段と後段で処理の粒度が変わる場合だけ連鎖を許容する。

- **集約**：後段の粒度が大きくなる。例として、在庫引当ごとにピッキング指示を出さず、一定数たまった時点でまとめて指示する。この場合も、先に別プロセスのポーリングで集約できないかを検討する。
- **分散**：後段の粒度が細かくなる。例として、締め処理の後の決済を利用者ごとのタスクに分け、一件の失敗や遅延が全体の完了を遅らせないようにする。
