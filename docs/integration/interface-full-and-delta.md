# 全件連携と差分連携

全件連携を第一の選択肢にし、性能やデータ鮮度の要件で全件連携が難しい場合だけ差分連携にする。
差分連携には整合性を確認する仕組みを組み込み、定期的な全件の洗い替え、チェックサムの比較の順に検討する。

## 用語

- **全件連携**：毎回すべての対象データを連携し、集信側で洗い替える方式。
- **差分連携**：前回の連携以降に追加、更新、削除されたデータだけを連携する方式。

## 方式の選択

- 原則として全件連携を使う。
- 巨大なマスタで性能要件を満たせない場合と、数分間隔など高い頻度の連携が必要な場合だけ差分連携を使う。
- 差分連携を使う場合は、次節の整合性の確認を組み込む。

## 差分連携の整合性

- 差分連携で整合性を守る必要があるかを、要件から判断する。
  傾向だけ分かればよいレポート用途などでは、確認を省いてよい。
- 整合性を守る必要がある場合は、まず定期的な全件の洗い替えを検討する。
- 次の場合は、洗い替えの代わりにチェックサムの比較を使う。
  - 洗い替えの間隔を短くできない。
  - 洗い替えで生じた差分を知る必要がある。
  - 集信側の後続処理（発注指示の配信など）が済んでおり、洗い替えできない。
- チェックサムは配信ファイルから計算せず、配信元の DB から直接抽出したデータで計算する。
- チェックサムの不一致の原因を調べるため、配信側が全件ファイルを出力できるよう調整しておく。
- チェックサムの比較、全件の比較、洗い替えを重ねる確認は、費用に見合う場合だけ行い、できる限り一つの方式に絞る。
