# メッセージングの設計

非同期処理は Spring Modulith のアプリケーションイベントとイベント出版レジストリで実装し、外部ブローカーの導入は ADR で決める。
一つの業務処理に一つのキューと一つのコンシューマーを対応させ、配信保証は at-least-once を前提にコンシューマーを冪等にする。
業務データの更新とメッセージの発行は、同じトランザクションでレジストリへ記録する。

## 用語

- **非同期処理**：呼び出し元が完了を待たずに応答し、別の実行単位で続きを行う処理。
- **メッセージ**：プロデューサーからコンシューマーへ渡すデータ。モジュール間ではモジュールルートに置くイベント型が該当する。
- **プロデューサー**：メッセージを発行する側。
- **コンシューマー**：メッセージを受け取って処理する側。現在は `@ApplicationModuleListener` を付けた非同期のイベントリスナーが該当する。
- **キュー**：メッセージを保持してコンシューマーへ渡す仕組み。現在は Spring Modulith のイベント出版レジストリがこの役割を担い、外部ブローカーを導入した後はブローカーのキューとトピックを指す。
- **DLQ**：処理できなかったメッセージを退避する場所。扱いは[非同期処理の失敗時の再試行と回復](async-failure-recovery.md)に従う。

## 実行基盤

非同期処理は、Spring Modulith のアプリケーションイベントと `@ApplicationModuleListener` で実装する。
イベントの発行は `modulith` スキーマのイベント出版レジストリに記録され、外部ブローカーへの externalization は無効にしている（[ADR-001](../adr/ADR-001-adopt-spring-modulith-modular-monolith.md)）。
リスナーの置き場所は[バックエンドの層の責務](../backend/layers.md)の `infrastructure.messaging` に従う。

外部ブローカーの導入、製品の選定、externalization の有効化は、後戻りしにくいため ADR を起こして決める。
製品は運用負担の小さいマネージドサービスを第一候補にする。
オンプレミスやマルチクラウドへの構築、ベンダーロックインの回避、既存ブローカーの移行といった制約がある場合だけ、標準プロトコル互換の製品やセルフホストを検討する。
AMQP や MQTT などのプロトコルは製品の選定に従属するため、単独の設計論点にしない。

PostgreSQL の `LISTEN` と `NOTIFY`、Redis の Pub/Sub を、業務処理の非同期実行に直接使わない。
どちらもメッセージを永続化しないため、コンシューマーの停止中に発行されたメッセージを失う。
これらを内部で使い、配信の品質を保証するフレームワークを介する場合は対象外とする。
Redis Streams のように永続化するデータ構造を使う場合は、外部ブローカーと同じく ADR で選定する。

## キューとコンシューマーの分割

一つの業務処理に、一つのキューと一つのコンシューマーを対応させる。

- 一つのキューで、異なる業務処理のメッセージを混ぜない。片方の障害や遅延がもう片方へ波及し、失敗した業務を切り分けにくくなる。
- 一つのコンシューマーで、複数の業務処理を順に実行しない。業務処理ごとにリスナーを分ける。
- キューごとに扱うメッセージのスキーマを一つに定め、重複排除とステータス管理に使う一意な項目を決める。

複数のプロデューサーが同じスキーマのメッセージを一つのキューへ送ってよい。
その場合は、[順序保証と冪等性](async-ordering-and-idempotency.md)の順序制御と重複排除を特に確認する。

同じメッセージを複数の業務処理で消費するファンアウトでは、プロデューサーから複数のキューへ直接送らず、トピックを経由させる。
Spring Modulith では一回のイベント発行が購読する全リスナーへ配られ、レジストリはリスナーごとに完了を記録する。

構成は次の二つから選ぶ。

- **1対1**：重い処理の切り出しなど、他の業務処理が同じメッセージを使う見込みが小さい場合に使う。例は帳票の生成や外部サービスへのデータ連携である。
- **1対N**：同じメッセージを複数の業務処理で消費する場合や、後から購読者を追加する拡張性を重視する場合に使う。例は注文確定イベントに在庫引当と分析基盤への通知を購読させる構成である。

## 配信保証

配信保証は次の三段階で表す。

- **At most once**：メッセージを0回か1回届ける。欠損があり得る。
- **At least once**：メッセージを少なくとも1回届ける。コンシューマーが重複して起動され得る。
- **Exactly once**：基盤の受け渡しを1回にする。プロデューサーの二重送信までは排除しない。

At most once を使わない。
At least once を既定とし、Exactly once を選べる基盤でもコンシューマーは冪等にする。
リカバリでの再実行によって、配信保証にかかわらず同じメッセージが重複して処理され得るためである。
Spring Modulith のレジストリも、未完了のイベント出版を再投入すると同じリスナーへ同じイベントを再び届ける。

## DB 更新とメッセージ発行の整合

業務データの更新とメッセージの発行は、同じトランザクションでイベント出版レジストリへ記録する。
この方式は**トランザクションアウトボックス**に当たり、コミットされた更新に対応するメッセージだけが後続へ渡る。

- **ファントムメッセージ**：コミット前に送ったメッセージ。コミットが失敗すると、コンシューマーは存在しないデータを処理する。
- **メッセージロスト**：コミット後の送信が失敗し、後続処理が起動しないこと。

どちらも避けるため、次を守る。

- イベントは、[バックエンドの層の責務](../backend/layers.md)が定めるトランザクション境界の内側で `ApplicationEventPublisher` から発行する。
- コミット前に外部ブローカーへ直接送信しない。
- コミット後に、トランザクションの外で別途送信しない。
- 外部ブローカーへ届ける場合も、Spring Modulith の externalization のようにレジストリを経由する方式を使う。
- DB の変更ログから中継する CDC は、仕組みが重いため第一候補にしない。
