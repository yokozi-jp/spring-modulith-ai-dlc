# 非同期処理の流量制御と性能

流量はプロデューサーではなくコンシューマーの同時実行数で制限し、上限は設定値で明示する。
DB を使うコンシューマーの同時実行数は、DB 接続の予算に収める。
性能の改善はファンアウトとコンシューマーのスケーリングで行い、どちらでも依存先の保護をスケーリングより優先する。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## コンシューマーの同時実行数

拡張性の高い基盤では、プロデューサーの送信に流量の制限を設けない。
コンシューマーには、次の目的で同時実行数の上限を設ける。

- 処理の急増で DB やシステム全体が不安定になることを防ぐ。
- 特定のタスクが資源を占有し、他のタスクが起動できなくなることを防ぐ。

上限は設定値で明示し、ライブラリの既定値に任せない。
流量を守るために後段のキューを増やして緩衝にせず、同時実行数の設定で解決する。
構成要素が増えるほど運用の費用が増えるためである。

Spring Modulith の非同期リスナーは、アプリケーションの task executor で実行される。
仮想スレッドはスレッドの費用を下げるが DB 接続を増やさないため、DB を使うリスナーの同時実行数は HikariCP の接続予算に収め、同期リクエストが使う接続を残す（[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)）。

このリポジトリは `application.yaml` の `spring.task.execution.simple.concurrency-limit` を 2 にする。
仮想スレッドの `SimpleAsyncTaskExecutor` は、この値で同時に動くリスナーの数を制限する。
値は最小の接続の pool（テストの `DB_POOL_MAXIMUM_SIZE` の 4）の半分で、残りの接続を同期リクエストに残す。
`DemoApplicationTest` は、上限が 1 以上で pool の半分以下であることを確かめる。
上限に達すると、コミットの後にリスナーを投入する要求のスレッドは、接続を持ったまま空きを待つ。
`reject-tasks-when-limit-reached` で断ると出版が未完了のまま残るため、断らずに待たせる。
本番の pool の大きさを負荷試験で決めたら、上限を pool から導いた環境変数にする。

失敗したイベント出版の定期の再投入は、advisory lock を持つ間、実行中に接続を 1 本持ち続ける（[ADR-075](../adr/ADR-075-resubmit-failed-event-publications-periodically-with-advisory-lock.md)）。
再投入したリスナーは同じ `concurrency-limit` の中で動き、上限に達するとジョブのスレッドが空きを待つ。
このため、ロックを取ったインスタンスでは、ジョブの 1 本とリスナーの上限の分を除いた接続が同期リクエストに残る。

## 受信方式ごとの流量制御

コンシューマーの受信方式によって、流量の制御方法が変わる。

- **常駐型**：コンシューマーのプロセスがキューを能動的にポーリングして処理する。コンシューマー数と処理スレッド数を1対1にし、プロセス数の増減で流量を調整する。
- **イベント駆動型**：基盤のポーリング担当がメッセージをワーカーへ割り当てる。プッシュ型のように起動されるため、意図しない並列度の上昇による過負荷に注意する。

イベント駆動型では、次の順に流量の制御方法を選ぶ。

1. コンシューマーを実行する基盤で、関数やタスクの単位に同時実行数の上限を設定する。
2. 基盤で上限を設定できない場合だけ、起動時に現在の同時実行数を確かめ、上限ならメッセージをキューへ戻す。

イベント駆動の関数から別の実行基盤のタスクを起動する構成は、関数の同時実行数を絞っても DB へ接続するタスクの総数を直接制御できないため、できる限り使わない。

## ファンアウトとファンイン

一つの重い処理を独立したサブタスクへ分けて並列に実行することを**ファンアウト**、サブタスクの結果を合流させることを**ファンイン**と呼ぶ。

- ファンインが不要なら、一つのイベントを複数のサブタスクが購読するトピックの構成でファンアウトする（[メッセージングの設計](async-messaging-design.md)）。
- ファンインが必要なら、親タスクがステータス管理テーブルに子タスクを登録し、後続の処理がテーブルを問い合わせて全子タスクの完了を判定する（[非同期処理のステータス管理](async-job-status.md)）。
- 分岐、合流、再試行を宣言的に書けるワークフローエンジンを導入する場合は、ADR を起こして決める。

## コンシューマーのスケーリング

キューへ流入するメッセージ量に応じて、コンシューマーの計算資源を増減させる。

- 固定数で運用し、負荷の増減に合わせて手作業で変える方式は、平常時の無駄が大きく、急増時にメッセージが滞留する。
- キューの深さや最古メッセージの滞留時間をトリガーにコンシューマー数を自動で増減させる方式を、固定数より優先する。
- 起動の速いサーバーレスの実行基盤を使える場合は、実行時間とリソースの制限に収まる処理から採用を検討する。

どの方式でも、最大の同時実行数を設定する。
スケールアウトしすぎると DB や外部 API などの依存先に負荷をかけるため、依存先の保護をスケーリングより優先する。
