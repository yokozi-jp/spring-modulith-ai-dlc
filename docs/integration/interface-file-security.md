# 機密情報を含む連携ファイル

連携に不要な機密情報は含めず、集信側が元の値を必要としなければ非識別化する。
機密情報を連携する場合は、ファイルの暗号化、連携先ごとの専用バケット、最小権限、監査、短い保持期間を重ねる。

## 用語

- **非識別化**：マスキング、ハッシュ化、匿名化などで、元の値を特定できない形にすること。
- **トークン化**：元の値を意味のない文字列に置き換え、対応表で元の値と突合できるようにすること。
- **署名付き URL**：特定のオブジェクトへのアクセスを期限付きで許可する URL。

## 含める情報の判断

- 機密情報が業務上必要かを最初に確認し、不要なら連携しない。
- 集信側が元の値を必要としない場合は、非識別化する。
- 元の値との突合が必要な場合は、トークン化を検討する。
- 機密情報を連携する場合は、情報の種類と機密度を分類し、準拠すべき法令や基準（個人情報保護法、マイナンバー法、PCI DSS、顧客や組織のセキュリティポリシーなど）を確認する。
- 想定する脅威（不正アクセス、改ざん、漏えい、運用ミスなど）ごとに影響と発生可能性を評価し、対策の優先順位を決める。

## 機密情報を連携する場合の対策

- ファイル定義書に、機密情報を含むかどうかを必ず書く（[連携の一覧と定義書](interface-documentation.md)）。
- ファイルを暗号化する。
  クラウド事業者やシステム管理者からも平文を見えなくする必要がある場合は、クライアントサイド暗号化を使う。
  サーバーサイド暗号化では、事業者が管理する鍵ではなく、利用者が管理する鍵を使う。
- 機密情報の専用バケットを連携先ごとに作る。
  プレフィックスによる論理的な分離は使わない。
- 専用バケットの権限は最小にし、アクセスの証跡を残し、不正アクセスを検知する監視アラートを設定する。
- 保持期間はできる限り短く（例：3日）し、ライフサイクルポリシーで自動的に削除する。

## 署名付き URL

- 不特定多数のシステムへ提供するハブ経由の連携と、機密性の高いデータを扱う連携では、署名付き URL でアクセスの範囲を絞ることを検討する。
- すべての連携で必須にはしない。
  使うかどうかはシステム全体の方針として決め、一部の連携だけで使い分けない。
- 定時の集信で使う場合は、再取り込みを考えて有効期限を長め（60分から180分など）にする。
- 署名付き URL は閉じたネットワークの外からも使える。
  閉じたネットワークで連携する場合は、外部からのアクセスを禁止するポリシーがあることを確認する。
