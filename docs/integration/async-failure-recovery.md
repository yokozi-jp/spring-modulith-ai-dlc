# 非同期処理の失敗時の再試行と回復

一時的なエラーは再試行し、回復不能なエラーは再試行を打ち切って DLQ へ退避する。
DLQ はソースキューごとに置き、アプリケーションによる即時の退避と基盤の受信回数上限による退避を併用する。
再実行はソースキューへの書き戻しに一本化し、複数のシステムにまたがる不整合は補償トランザクションより先に設計で減らす。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## 再試行

エラーを次の二つに分けて扱う。

- **回復可能なエラー**：外部 API のタイムアウトなど、一時的な障害で、時間をおけば成功が見込めるエラー。
- **回復不能なエラー**：内部ロジックのエラーやメッセージ自体の検証エラーなど、何度再試行しても成功しないエラー。

回復可能なエラーは、回数と間隔を決めて再試行する。

- 外部呼び出しの即時の再試行は、client adapter の一層だけで行う（[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)）。コンシューマーで client adapter を囲む再試行のループを書かない。
- メッセージの再配信の間隔は、基盤が指数バックオフをサポートしていれば使う。指数バックオフに独自の実装が必要な場合は、実装費用に見合う効果がある場合だけ採用する。

回復不能なエラーは、資源の浪費と他の処理への影響を避けるため、再試行を打ち切って DLQ へ退避する。

## Spring Modulith のイベントの失敗

外部ブローカーを導入するまでは、リスナーが失敗したイベント出版がレジストリに `FAILED` の状態で残り、これが DLQ の役割を兼ねる。
失敗した出版の再投入は `FailedEventPublications` を使い、`IncompleteEventPublications` は落ちたまま残った出版の回復に限る。

Spring Modulith 2.1.1 のイベント出版は、次の状態を持つ（[Spring Modulith: Event Publication Lifecycle](https://docs.spring.io/spring-modulith/reference/events.html)）。

- **`PUBLISHED`**：記録され、リスナーの実行を待っている。
- **`PROCESSING`**：リスナーが実行している。
- **`COMPLETED`**：リスナーが成功した。
- **`FAILED`**：リスナーが例外を送出した、または Staleness Monitor が古いと判定した。
- **`RESUBMITTED`**：失敗した出版を再投入し、実行を待っている。

出版は、リスナーを呼んだ回数（completion attempts）も持ち、`PROCESSING` に移るときに増える。
再投入したかどうかは `completion_attempts` で見る。
2.1.1 の JDBC の実装は、作成時の `last_resubmission_date` に `publication_date` と同じ値を入れるためである（[issue #108 の確認結果](https://github.com/yokozi-jp/spring-modulith-ai-dlc/issues/108#issuecomment-6032559650)）。

再投入と回復は次のように扱う。

- 失敗した出版の再投入は、`FailedEventPublications.resubmit(ResubmissionOptions)` を使う。
  `ResubmissionOptions` で、一度に扱う件数、同時に実行する件数、最小の経過時間、条件（イベントの型、`completionAttempts` の上限）を付ける。
  回数の上限を超えた出版は自動で再投入せず、人の確認に回す。
  `resubmit` は再投入した件数を返さないため、件数を記録するときは条件の関数の中で数える。
- Staleness Monitor（`spring.modulith.events.staleness.*`）は、`PUBLISHED`、`PROCESSING`、`RESUBMITTED` のまま設定した時間を過ぎた出版を `FAILED` にする。
  既定ではどの時間も 0 で動かず、main は設定していない。
- `IncompleteEventPublications` は、処理中のものを含めて、完了していない出版をすべて対象にする。
  通常の失敗には使わず、Staleness Monitor を使わない環境で、落ちたまま残った出版を経過時間で絞って回復する場合に限って使う。
- 起動時の自動再配信（`republish-outstanding-events-on-restart`）は使わない（[ADR-001](../adr/ADR-001-adopt-spring-modulith-modular-monolith.md)）。
- 回復不能と判定したエラーは、ステータス管理テーブルを FAILED にして失敗の内容を記録し、リスナーを正常終了させて再投入の対象から外す（[非同期処理のステータス管理](async-job-status.md)）。
  このときイベント出版は `COMPLETED` になり、ステータス管理テーブルの FAILED は出版の `FAILED` とは別の値である。
- 予期しない例外はリスナーから送出し、イベント出版を `FAILED` で残す。

本番で運用者が再投入する入口（コマンド、API、ジョブ）と定期の再投入は [issue #108](https://github.com/yokozi-jp/spring-modulith-ai-dlc/issues/108) で決め、main にはまだない。
`completion-mode: archive` で完了した出版を移す archive の表の保存期間と消し方も決めていない（issue #108）。

## DLQ の構成

DLQ は、ソースキューごとに一つ置く。
全キューで一つの DLQ を共有すると、再実行の際にどのキューから来たメッセージかを判別する処理が必要になる。

## DLQ への退避

処理不能なメッセージが同じグループの後続を止める状態を避けるため、次の二段構えで DLQ へ退避する。
ただし、厳密な順序が必要なキューには適用しない（[順序保証と冪等性](async-ordering-and-idempotency.md)）。

- **アプリケーションによる退避**：コンシューマーが回復不能と判定したエラーは、アプリケーションから即時に DLQ へ送る。
- **基盤による退避**：予期しない例外、メモリ不足、タイムアウトによるクラッシュは、基盤の受信回数の上限（Amazon SQS の `maxReceiveCount` など）を超えた時点で DLQ へ転送させる。

受信回数の上限は、無限の再実行を防ぐ安全網として、アプリケーションが行う最大の再試行回数より大きい値にする。
大きすぎると、上限とメッセージロックのタイムアウトを掛けた時間だけ後続が止まる。

二段構えには次の前提がある。

- アプリケーションによる DLQ への送信とソースキューからの削除は原子的でないため、ステータス管理テーブルで重複実行を防ぐ。
- アプリケーションから DLQ へ送るときは、順序制御のグループ ID とトレースコンテキストなどのメタデータを明示的に引き継ぐ。引き継がないと、再実行で順序と追跡が崩れる。

## DLQ からの再実行

DLQ のメッセージは、ソースキューへ書き戻して再実行する。
コンシューマーに DLQ を直接読ませる方式は、二つの入力の考慮と再実行時の構成変更が必要になるため使わない。

DLQ からソースキューへ転送する再実行専用のジョブを用意し、再実行の操作を統一する。

## 失敗メッセージの保持

原則として、DLQ の保持期間に依存し、保持期間は基盤の最大値にする。
失敗の解決に数週間以上かかり得る機能に限り、失敗を検知した時点でメッセージの内容を DB やオブジェクトストレージへ永続化する。
DLQ を定期的にアーカイブする仕組みは、別のジョブと調査の手間が増えるため第一候補にしない。

## 複数のシステムにまたがる整合性

自社 DB と外部サービスへ順に登録する処理の後段で回復不能なエラーが起きると、不整合が残る。
回復の方式は次の二つである。

- **Saga**：失敗したら、それまでの処理を取り消す補償トランザクションを逆順に実行する。取り消し API が必要で、副作用が残る場合がある。補償トランザクションも非同期の処理として切り出す。
- **手動リカバリ**：失敗したら通知し、不整合を一時的に許容して、運用担当者がデータの修正で回復する。

方式を選ぶ前に、設計で非同期の箇所を減らせないかを検討する。
例として、売上に直結する決済サービスへの登録までを同期で行い、遅れても影響の小さい顧客管理への連携だけを非同期にすれば、失敗しても後から登録し直す一方向の回復で済む。

- 在庫引当のように、失敗を放置すると業務上許容できない損失になる場合だけ Saga を採用する。
- 取り消し API を用意しにくい場合や発生頻度が低い場合は、手動リカバリで様子を見る。送信済みのメールのように取り消せない副作用は、訂正の連絡など別の処理で打ち消す。
- どちらの方式でも、再試行を組み込んで不整合の発生頻度を下げる。
