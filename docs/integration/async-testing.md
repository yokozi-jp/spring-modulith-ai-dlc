# 非同期処理のテスト

非同期処理も通常の機能と同じテスト種別で検証し、冪等性のテストとプロデューサーからコンシューマーまでの結合テストを加える。
負荷テストはキューへの直接投入でコンシューマー単体の性能を測ってから、Web API を経由した通しの試験を行う。
障害と運用のテストでは、DLQ への退避の検知と再実行の手順を確かめる。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。
テスト種別の選び方は[バックエンドのテスト種別](../backend/testing-strategy.md)に従う。

## 冪等性のテスト

コンシューマーの冪等性は、ユニットテストで確かめる。
同じメッセージを二回処理しても、結果が一回の処理と同じであることを検証する。
冪等性を任意の入力に対する不変条件として書く場合は、プロパティベーステストを使ってよい（[ADR-012](../adr/ADR-012-adopt-property-based-and-mutation-testing.md)）。

## 結合テスト

キューを挟むとプロデューサーとコンシューマーの認識違いによる不具合が起きやすいため、プロデューサーからキューを経てコンシューマーまでの結合テストを自動化する。

- Spring Modulith のイベントは、[バックエンドのDBテスト](../backend/testing-database.md)に従い `@ApplicationModuleTest` と `Scenario` で検証する。
- 非同期の完了は固定時間で待たず、[バックエンドのテストコードの書き方](../backend/testing-code-style.md)の条件待機で待つ。
- 外部ブローカーを導入した後は、モックではなく Testcontainers などで起動した実物のキューを使う。
- 結合テストは実行時間が長いため、正常系に絞る。
- 代表的な一つの機能に限り、処理の失敗が規定回数の再試行の後に DLQ へ退避されることも検証する。

## 負荷テスト

非同期処理の負荷テストでは、キューへ投入した後のコンシューマーの処理が非機能要件の性能を満たすかを確かめる。

1. キューへメッセージを直接投入し、コンシューマー単体の性能を測る。
2. 次に、Web API を経由した通しの試験を行う。

直接投入から始めるのは、試験環境の設定誤りでコンシューマーへメッセージが届かない問題を先に切り分けるためである。
また、最初から Web API を経由すると、Web API の性能不足で流量が絞られ、コンシューマーへ十分な負荷がかからないことがある。

本番相当の負荷を15分などの一定時間かけ、次を確かめる。

- コンシューマーが、非機能要件で想定した処理量をさばける。
- DB などの依存先の CPU、I/O、メモリの使用量が想定を下回る。
- 自動のスケールアウトとスケールインを設計に含めた場合は、それらが動作する。
- 通しの試験で、Web API の同期部分のレイテンシが小さく保たれ、非同期に切り出した効果がある。

## 障害と運用のテスト

監視の設定が機能することを障害テストで確かめる。

- ソースキューから DLQ へ退避されたときに、検知と通知が行われる。
- DLQ からソースキューへ書き戻す再実行の手順が、想定どおりに行える。
