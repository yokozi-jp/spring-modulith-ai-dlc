# 非同期処理のテスト

非同期処理も通常の機能と同じテスト種別で検証し、冪等性のテストとプロデューサーからコンシューマーまでの結合テストを加える。
Spring Modulith のリスナーの冪等性は、すべてのリスナーに同じイベントを 2 回届ける全件の結合テストで確かめる。
負荷テストはキューへの直接投入でコンシューマー単体の性能を測ってから、Web API を経由した通しの試験を行う。
障害と運用のテストでは、DLQ への退避の検知と再実行の手順を確かめる。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。
テスト種別の選び方は[バックエンドのテスト種別](../backend/testing-strategy.md)に従う。

## 冪等性のテスト

Spring Modulith のリスナーの冪等性は、全件の結合テスト `ListenerIdempotencyTest` で確かめる。
このテストは、Spring の文脈から `@ApplicationModuleListener` の付いたメソッドを全件集め、リスナーの ID ごとに入力例を求める。
リスナーの ID は、イベント出版の `listener_id` と同じ規則（リスナーのメソッドの完全修飾名と引数の型）で作る。
入力例は、前提の状態を作る準備と、受けるイベントの組である（`ListenerExample`）。
新しいリスナーに入力例を足す手順は、[Listener](../backend/class-roles/listener.md)の「冪等性の入力例」に従う。

テストは、各リスナーに同じ本文のイベントを順に 2 回と同時に 2 回届ける。
順の 2 回では、2 つのテナントに前提の状態を作り、入力例のイベントを `Scenario#publish` と同じくトランザクションの中で出版し、出版の完了を `event_publication` と `event_publication_archive` で待ち、業務の表の中身を両方のテナントで読む。
次に同じ本文のイベントをもう一度出版して完了を待ち、もう一度読んで比べる。
リスナーはイベントの本文だけを受け取り、出版の ID を見ないため、同じ本文の 2 回目の出版は再投入による 2 回目の配信と同じ入力になる。

同時の 2 回では、競合を運に任せず、次の順で必ず起こす。

1. 前提の状態を作り直す。
2. 1 回目を、リスナーのトランザクションのコミットの直前で止める。業務の書き込みとロックは済んでいる。
3. 2 回目を出版し、2 回目が 1 回目のセッションのロックを待つ（`pg_blocking_pids` が 1 回目のセッションを返す）か、コミットの直前に届くか、失敗するまで待つ。
4. 待ちを見つけたらすぐ 1 回目をコミットし、両方の出版の完了を待つ。

2 回目がロックを待つ時間は待ちを見つける間隔ほどで、`lock_timeout`（[ADR-055](../adr/ADR-055-set-db-time-limits-per-connection.md)）より十分に短いため、2 回目は `lock_timeout` で失敗しない。
手順 3 で待つ上限は、2 回目が待ち始めるまでの時間（非同期の配信の開始と CI の負荷を含む）を区切る。
この上限を `lock_timeout` に合わせると、負荷で 2 回目が待ち始める前に上限を過ぎ、偽の失敗になる。
そのため、1 回目を止める上限から余裕を引いた固定値にし、1 回目が止める上限で諦める前に 1 回目を通せるようにする。

業務の表の中身は、所有者の接続で読む。
RLS の外の `tenancy` の表はそのまま読み、ほかの業務の表は `m_tenant` のテナントを 1 つずつ設定して読む。
`modulith` スキーマの表は比べない。
外部システムの呼び出しは、`infrastructure.client` の `*Client` が実装する `domain.model` のインタフェースの呼び出しを、メソッドと引数の組で記録して比べる。

テストは、次のときに失敗し、リスナーの ID と何が悪いかをメッセージに書く。

- 入力例のないリスナーがある。
- リスナーのない入力例がある。
- 1 回目の配信が業務の表の行を 1 行も変えない。
- 順の 2 回目の配信が、業務の表の行を足す、消す、または変える。行数だけでなく行の中身を比べる。
- どちらかの配信が例外で終わり、出版が `FAILED` に残るか、方針で `ABANDONED` になって archive の表へ移る。
- どちらかの出版が、待つ上限までに完了（archive の表の `COMPLETED`）にも失敗にもならない。
- 同時の 2 回の後の業務の表の中身が、1 回だけ届けたときと違う。
- 同時の 2 回の 1 回目がコミットの直前で止まらない（トランザクションの外で動く）、2 回目が 1 回目のロックを待たず、コミットの直前にも届かず、失敗もしない、または 1 回目をコミットさせた後に 2 回目がコミットの直前に届かない。
- 順の 2 回か同時の 2 回の後で、外部システムの呼び出しの組の集合が、1 回だけ届けたときと違う。同じ組を 2 回呼ぶことは許す。

テストで確かめられない範囲と、その範囲の守り方は、[順序保証と冪等性](async-ordering-and-idempotency.md)の「全件の結合テストが確かめる範囲」にある。
CommandHandler の判定を任意の入力に対する不変条件として書く場合は、プロパティベーステストを使ってよい（[ADR-012](../adr/ADR-012-adopt-property-based-and-mutation-testing.md)）。

## 結合テスト

キューを挟むとプロデューサーとコンシューマーの認識違いによる不具合が起きやすいため、プロデューサーからキューを経てコンシューマーまでの結合テストを自動化する。

- Spring Modulith のイベントは、[バックエンドのDBテスト](../backend/testing-database.md)に従い `@ApplicationModuleTest` と `Scenario` で検証する。
- 非同期の完了は固定時間で待たず、[バックエンドのテストコードの書き方](../backend/testing-code-style.md)の条件待機で待つ。
- 外部ブローカーを導入した後は、モックではなく Testcontainers などで起動した実物のキューを使う。
- 結合テストは実行時間が長いため、正常系に絞る。
- 代表的な一つの機能に限り、処理の失敗が規定回数の再試行の後に DLQ へ退避されることも検証する。

## 負荷テスト

非同期処理の負荷テストでは、キューへ投入した後のコンシューマーの処理が非機能要件の性能を満たすかを確かめる。

1. キューへメッセージを直接投入し、コンシューマー単体の性能を測る。
2. 次に、Web API を経由した通しの試験を行う。

直接投入から始めるのは、試験環境の設定誤りでコンシューマーへメッセージが届かない問題を先に切り分けるためである。
また、最初から Web API を経由すると、Web API の性能不足で流量が絞られ、コンシューマーへ十分な負荷がかからないことがある。

本番相当の負荷を15分などの一定時間かけ、次を確かめる。

- コンシューマーが、非機能要件で想定した処理量をさばける。
- DB などの依存先の CPU、I/O、メモリの使用量が想定を下回る。
- 自動のスケールアウトとスケールインを設計に含めた場合は、それらが動作する。
- 通しの試験で、Web API の同期部分のレイテンシが小さく保たれ、非同期に切り出した効果がある。

## 障害と運用のテスト

監視の設定が機能することを障害テストで確かめる。

- ソースキューから DLQ へ退避されたときに、検知と通知が行われる。
- DLQ からソースキューへ書き戻す再実行の手順が、想定どおりに行える。
