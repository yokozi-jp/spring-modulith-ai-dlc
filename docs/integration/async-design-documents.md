# 非同期処理の設計文書

非同期処理には、なぜ非同期にしたかという設計意図と、イベントの伝わり方を示すフロー図を残す。
送信経路が一つでも、メッセージのインタフェース定義を作る。
キューの一覧と DLQ の運用一覧には、インフラの設定から読み取れない情報だけを書く。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## 文書の紐づけ

フロー図、インタフェース定義、機能の設計書は、機能モジュール名とイベント型名で相互に紐づける。

## 設計意図とイベントフロー図

非同期処理の文書には、最初に「なぜ非同期なのか」を書く。
例は「外部 API の遅延から画面の応答を切り離すため」「負荷を平準化するため」である。
設計意図がないと、後の保守担当者が同期へ戻すべきかを判断できない。
判断の基準は[非同期化の判断基準](async-adoption-criteria.md)に従う。

イベントの連鎖とキューへの依存が分かるように、次のどちらかを作る。

- 各イベントの連鎖を示すイベントフロー図。
- 上流の Web API の設計書に Mermaid で書いたシーケンス図。

メッセージの種類が少なければ、システム構成図にまとめてよい。
非同期が連鎖する場合は、下流の文書から上流のイベントフロー図またはシーケンス図へリンクする。

## インタフェース定義

特定の Web API からしかキューへ送らない場合も、メッセージのインタフェース定義を作る。
一律に定義を置くと抜け漏れを防ぎやすく、コンシューマー側との認識違いを防げ、スキーマ変更時のやり取りと再実行の運用に必要な情報が残る。

- モジュール間のイベントは、モジュールルートに置くイベント型を契約とする（[バックエンドアーキテクチャ](../backend/architecture.md)）。
- 外部ブローカーへ送るメッセージは、送信先のキューやトピック、操作、ペイロードのスキーマを AsyncAPI で定義し、Git で管理する。

## キューの一覧

キューの一覧には、どのキューをどの業務処理のためにどのコンポーネント間で使うかを書く。
列は、キュー名、業務上の用途、プロデューサー、コンシューマー、DLQ とする。

保持期間や DLQ への転送条件などの設定は、IaC が管理していれば二重管理になるため一覧に書かず、IaC の該当ファイルへリンクする。

## DLQ の運用一覧

DLQ の運用一覧には、DLQ にメッセージが入ったときに誰が何をするかを書く。
列は、DLQ 名、担当者、対応の概要、回復手順へのリンクとする。
回復手順は Runbook として別の文書に書く。

## 機能の設計書

プロデューサーとコンシューマーの設計書は、Web API など通常の業務ロジックの設計書と同じく、データの CRUD とシーケンス図を書く。
