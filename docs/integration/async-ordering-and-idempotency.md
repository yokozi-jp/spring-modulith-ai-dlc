# 順序保証と冪等性

コンシューマーは常に冪等にし、基盤の重複排除は補助として使う。
処理順序に依存しない設計を目指し、厳密な順序が必要な場合だけ基盤の順序保証を業務エンティティ単位のグループで使う。
厳密な順序が必要なキューでは、回復不能なメッセージを DLQ へ退避しない。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## 冪等なコンシューマー

コンシューマーは、同じメッセージを二回以上処理しても結果が一回の処理と変わらないように作る。
二重の処理は、DB が保証する仕組みで止める。
使う仕組みは次のどれかである。

- **業務のキーの一意制約**：同じ業務のキーの行を二度作れないようにする（決済の記録の注文 ID）。
- **集約の楽観的ロック**：処理済みの状態を集約に持ち、ロック番号を比べて更新する（[jOOQ の Repository](../backend/class-roles/jooq-repository.md)）。
  同じメッセージが同時に二つ届いても、後の一方は更新の競合で失敗する。
- **処理済みのメッセージ ID の一意制約**：ステータス管理テーブルのジョブ ID のように、処理したメッセージの ID を一意制約のある表に記録する（[非同期処理のステータス管理](async-job-status.md)）。

状態の確認（`order.isPaid()` など）だけで済ませない。
確認と更新の間に同じメッセージが届くと、どちらも確認を通るためである。
業務のキーの一意制約か集約の楽観的ロックで足りるときは、処理済みのメッセージ ID の表を作らなくてよい。
外部システムへの副作用は DB の仕組みで取り消せないため、外部システムに冪等性キーを渡す。

基盤が重複排除の機能を持つ場合は使う。
ただし、重複排除の有効期間は分単位のように短いことが多く、プロデューサーの二重送信も排除しきれないため、コンシューマーの冪等性を省略しない。
重複排除の有効期間を超えて重複を防ぐ必要がある場合や、高スループットのために基盤の重複排除を使えない場合は、コンシューマー側の重複判定だけで防ぐ。
HTTP API の冪等性キーも Exactly once を保証しないため、同じ考え方で併用する（[ADR-013](../adr/ADR-013-standardize-http-api-contracts.md)）。

## 順序保証

可能な限り、処理順序に依存しない設計にする。
メッセージを互いに独立させ、コンシューマーを冪等にすれば、順序の入れ替わりを許容できることが多い。
Spring Modulith の非同期リスナーも、イベントの発行順に処理されることを前提にしない。

厳密な順序が必要な場合は、FIFO キューのように基盤が保証する順序制御を使う。
メッセージにシーケンス番号を付けてアプリケーションで順序を判定する方式は、FIFO を使えず、かつコンシューマーを冪等にできない場合に限る。

順序を守る単位は、順序が必要な最小の業務エンティティの ID（注文 ID、利用者 ID など）でグループ化する。
固定値、乱数、粒度の粗い ID をグループに使わない。
固定値は全体を直列化し、粗い ID は一件の停止で同じグループの後続を止める。

- **ヘッドオブラインブロッキング**：処理できないメッセージが先頭に残り、同じグループの後続メッセージが処理されない状態。

## 順序を守るキューの回復不能エラー

厳密な順序が必要なキューでは、回復不能なメッセージを DLQ へ退避しない。
退避した時点で後続メッセージのロックが外れ、失敗した処理を飛ばして後続が進むため、業務上の順序が崩れる。

回復不能なエラーへの対応は、次の二つから選ぶ。

- **停止して手動で回復する**：エラーを永続的と判断した時点で通知し、メッセージを退避も削除もしない。回復するまで後続は止まるため、順序は保てるが可用性と運用負荷の面で不利である。
- **スキップする**：失敗したメッセージの内容を DB またはログへ保存して DLQ へ送り、後続の処理を続ける。失敗分は別途回復する。

スキップを選べるよう、結果整合性を業務要件として調整する。
業務要件で厳密な順序が必須な場合だけ停止方式にし、早期に回復できる運用体制を用意する。
一時的なエラーは、[非同期処理の失敗時の再試行と回復](async-failure-recovery.md)に従ってコンシューマー側で再試行する。

## メッセージロックのタイムアウト

外部ブローカーを使う場合は、メッセージロックのタイムアウトを次の方針で設定する。

- **メッセージロックのタイムアウト**：コンシューマーがメッセージを処理している間、他のコンシューマーからそのメッセージを見えなくする時間。Amazon SQS の可視性タイムアウトが該当する。

短すぎると処理中に別のコンシューマーが同じメッセージを取得して重複実行し、長すぎると一時エラー後の再試行が遅れてメッセージが滞留する。

- 処理時間を厳密に予測できないため、重複起動しても問題のない冪等な設計を前提にする。
- システム共通の基準値を決め、その値で明らかに問題になる処理だけ個別に調整する。
- 初期値は、メッセージの最大処理時間に安全マージンを加えた値にする。
- メッセージによって処理時間のばらつきが大きい場合は、タイムアウト値の半分などの一定間隔でロックの延長を要求するハートビートを入れる。
- 冪等にできず、重複起動を業務上許容できない場合は、タイムアウト前に処理をロールバックするキャンセル機構か、ハートビートを入れる。
