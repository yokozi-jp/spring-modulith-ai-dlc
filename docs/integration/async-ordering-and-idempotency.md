# 順序保証と冪等性

コンシューマーは常に冪等にし、基盤の重複排除は補助として使う。
冪等の仕組みはリスナーごとに選び、重複の判定は DB が直列にする操作で行い、すべてのリスナーの結果を全件の結合テストで確かめる。
処理順序に依存しない設計を目指し、厳密な順序が必要な場合だけ基盤の順序保証を業務エンティティ単位のグループで使う。
厳密な順序が必要なキューでは、回復不能なメッセージを DLQ へ退避しない。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## 冪等なコンシューマー

コンシューマーは、同じメッセージを二回以上処理しても結果が一回の処理と変わらないように作る。
二重の処理は、DB が保証する仕組みで止める。
仕組みはリスナーごとに次から選ぶ。

- **業務のキーの一意制約**：同じ業務のキーの行を二度作れないようにする（決済の記録の注文 ID）。
- **集約の楽観的ロック**：処理済みの状態を集約に持ち、ロック番号を比べて更新する（[jOOQ の Repository](../backend/class-roles/jooq-repository.md)）。
- **処理済みのメッセージ ID の一意制約**：ステータス管理テーブルのジョブ ID のように、処理したメッセージの ID を一意制約のある表に記録する（[非同期処理のステータス管理](async-job-status.md)）。

業務のキーの一意制約か集約の楽観的ロックで足りるときは、処理済みのメッセージ ID の表を作らない。
すべてのリスナーに一律に表を置かない理由は [ADR-129](../adr/ADR-129-check-all-listeners-for-idempotency-without-a-uniform-processed-message-table.md) にある。
外部システムへの副作用は DB の仕組みで取り消せないため、外部システムに冪等性キーを渡す。

### 重複の判定

リスナーが呼ぶ CommandHandler は、重複かどうかを次のどれかで判定する。

- **一意索引の `INSERT ... ON CONFLICT DO NOTHING`**：入れた行が 0 件なら処理済みとする。
- **`lock_no` を WHERE に書く `TableWriter.update`**：楽観的ロックの更新である（[ADR-054](../adr/ADR-054-detect-optimistic-lock-conflicts-by-update-count.md)）。
  `TableWriter.update` は 0 件の更新を `ConflictException`（種類 `version`）にする。
  CommandHandler はこの種類の例外を catch して集約を読み直し、操作が済んでいれば処理済みとする。
- **`SELECT ... FOR UPDATE` の後の判定**：行をロックしてから状態を読み、処理済みかを決める。

ロックを取らない SELECT で判定しない（`order.isPaid()` を見るだけで済ませる、など）。
上の三つでは、同時の 2 回目が 1 回目の行ロックを待ち、PostgreSQL の READ COMMITTED で 1 回目がコミットした行を見直す（[PostgreSQL の排他制御](../database/postgresql-concurrency-control.md)）。
ロックを取らない SELECT は 1 回目のコミット前の行を読むため、同時に届いた二つの配信がどちらも未処理と判定し、二重に処理する。
全件の結合テストの同時の 2 回は、この書き方のリスナーを失敗にする（[非同期処理のテスト](async-testing.md)の「冪等性のテスト」）。
ロックを取らない先読みは、外部システムの呼び出しを省く最適化としてだけ使い、判定は上の三つのどれかで行う。

一意索引の衝突と 0 件の更新は、例外にせず、処理済みとして正常に終える。
例外にすると、イベント出版が `FAILED` に残る。
2 回目の配信が毎回同じ衝突で失敗する書き方では、定期の再投入が方針の回数の上限まで失敗を繰り返し、出版は `ABANDONED` で archive の表へ移る（[ADR-079](../adr/ADR-079-resubmit-failed-event-publications-periodically-with-shedlock.md)）。
一意制約の違反（SQLSTATE `23505`）を catch して続けることはできない。
PostgreSQL は違反した時点でトランザクションを中断し、以後の文を受け付けないためである。

### 処理済みのメッセージ ID の表の形

処理済みのメッセージ ID の表を使うときは、次の形にする。

- 受け取るモジュールのスキーマに置く。
- 主キーを `(tenant_public_id, イベントの本文が持つ ID, リスナーの ID)` にする。
  リスナーの ID は、イベント出版の `listener_id`（リスナーのメソッドの完全修飾名と引数の型）と同じ値にする。
- CommandHandler の `handle` のトランザクションの初めに `INSERT ... ON CONFLICT DO NOTHING` で書き、0 件なら業務の処理をせずに返す。

### 全件の結合テストが確かめる範囲

全件の結合テストは、すべての `@ApplicationModuleListener` に同じ本文のイベントを順に 2 回と同時に 2 回届け、業務の表の中身と外部システムの呼び出しを、1 回だけ届けたときと比べる。
テストが漏れなくリスナーを集められるのは、`ClassRoleArchTest` の `eventListenersAreApplicationModuleListeners` と `applicationListenerIsNotImplemented` が、`@ApplicationModuleListener` 以外の受け方を禁じているためである。

テストで確かめられない次の二つは、規約とレビューで守る。

- 同時の 2 回は、1 回目をコミットの直前で止め、その間に 2 回目を流す一つの順だけを作る。
  ほかの順で届いたときの振る舞いは、上の「重複の判定」の書き方で守る。
- 外部システムの呼び出しは、メソッドと引数の組の集合で比べるため、同じ組を 2 回呼ぶことを許す。
  同じ組の 2 回目を外部システムが二重に処理しないことは、外部システムに渡す冪等性キーで守る。
  順の 2 回目で外部システムを呼ばないことは、リスナーごとのテストで確かめる（決済では `OrderConfirmedListenerTest` の `secondDeliveryDoesNotChargeAgain`）。

基盤が重複排除の機能を持つ場合は使う。
ただし、重複排除の有効期間は分単位のように短いことが多く、プロデューサーの二重送信も排除しきれないため、コンシューマーの冪等性を省略しない。
重複排除の有効期間を超えて重複を防ぐ必要がある場合や、高スループットのために基盤の重複排除を使えない場合は、コンシューマー側の重複判定だけで防ぐ。
HTTP API の冪等性キーも Exactly once を保証しないため、同じ考え方で併用する（[ADR-013](../adr/ADR-013-standardize-http-api-contracts.md)）。

## 順序保証

可能な限り、処理順序に依存しない設計にする。
メッセージを互いに独立させ、コンシューマーを冪等にすれば、順序の入れ替わりを許容できることが多い。
Spring Modulith の非同期リスナーも、イベントの発行順に処理されることを前提にしない。

厳密な順序が必要な場合は、FIFO キューのように基盤が保証する順序制御を使う。
メッセージにシーケンス番号を付けてアプリケーションで順序を判定する方式は、FIFO を使えず、かつコンシューマーを冪等にできない場合に限る。

順序を守る単位は、順序が必要な最小の業務エンティティの ID（注文 ID、利用者 ID など）でグループ化する。
固定値、乱数、粒度の粗い ID をグループに使わない。
固定値は全体を直列化し、粗い ID は一件の停止で同じグループの後続を止める。

- **ヘッドオブラインブロッキング**：処理できないメッセージが先頭に残り、同じグループの後続メッセージが処理されない状態。

## 順序を守るキューの回復不能エラー

厳密な順序が必要なキューでは、回復不能なメッセージを DLQ へ退避しない。
退避した時点で後続メッセージのロックが外れ、失敗した処理を飛ばして後続が進むため、業務上の順序が崩れる。

回復不能なエラーへの対応は、次の二つから選ぶ。

- **停止して手動で回復する**：エラーを永続的と判断した時点で通知し、メッセージを退避も削除もしない。回復するまで後続は止まるため、順序は保てるが可用性と運用負荷の面で不利である。
- **スキップする**：失敗したメッセージの内容を DB またはログへ保存して DLQ へ送り、後続の処理を続ける。失敗分は別途回復する。

スキップを選べるよう、結果整合性を業務要件として調整する。
業務要件で厳密な順序が必須な場合だけ停止方式にし、早期に回復できる運用体制を用意する。
一時的なエラーは、[非同期処理の失敗時の再試行と回復](async-failure-recovery.md)に従ってコンシューマー側で再試行する。

## メッセージロックのタイムアウト

外部ブローカーを使う場合は、メッセージロックのタイムアウトを次の方針で設定する。

- **メッセージロックのタイムアウト**：コンシューマーがメッセージを処理している間、他のコンシューマーからそのメッセージを見えなくする時間。Amazon SQS の可視性タイムアウトが該当する。

短すぎると処理中に別のコンシューマーが同じメッセージを取得して重複実行し、長すぎると一時エラー後の再試行が遅れてメッセージが滞留する。

- 処理時間を厳密に予測できないため、重複起動しても問題のない冪等な設計を前提にする。
- システム共通の基準値を決め、その値で明らかに問題になる処理だけ個別に調整する。
- 初期値は、メッセージの最大処理時間に安全マージンを加えた値にする。
- メッセージによって処理時間のばらつきが大きい場合は、タイムアウト値の半分などの一定間隔でロックの延長を要求するハートビートを入れる。
- 冪等にできず、重複起動を業務上許容できない場合は、タイムアウト前に処理をロールバックするキャンセル機構か、ハートビートを入れる。
