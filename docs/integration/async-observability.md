# 非同期処理のトレースと監視

非同期処理の呼び出しでは、OpenTelemetry のトレースコンテキストを必ずメッセージのメタデータで引き継ぎ、独自のトレース ID を採番しない。
ステータス管理テーブルにはトレース ID とスパン ID を記録する。
監視はキューの滞留と DLQ の滞留時間を必須とし、アプリケーションのメトリクスは SLO がある場合に限って検討する。

用語は[メッセージングの設計](async-messaging-design.md)の定義に従う。

## トレースコンテキストの伝播

トレース ID とスパン ID は、Micrometer Tracing が扱う OpenTelemetry の値を使う。
独自のトレース ID や request ID を採番しない（[ADR-015](../adr/ADR-015-structure-and-protect-observability-data.md)）。
ログとトレースの相関は[可観測性データの規約](../observability/conventions.md)に従う。

- 非同期処理を呼び出すときは、トレースコンテキストを必ず引き継ぐ。
- トレースコンテキストはペイロードの本文に入れず、メッセージのメタデータで渡す。外部ブローカーでは W3C Trace Context の `traceparent` をメッセージの属性やヘッダーへ載せる。再実行や回復のときに、本文を変えずにトレースを切り替えられるようにするためである。
- Spring Modulith の非同期リスナーでも、発行元のトレースがリスナーの実行スレッドへ伝播し、リスナーのログに同じ `traceId` が付くことを確かめる。

## ステータス管理テーブルのトレース情報

[非同期処理のステータス管理](async-job-status.md)のテーブルには、`trace_id` と `span_id` の列を持たせる。
起動の親子関係を SQL で辿る必要がある場合は `parent_span_id` も持たせ、再帰 CTE で起動順を復元する。
トレース ID を区切り文字でつないで親子関係を表す設計は、キーが長大になるため使わない。

ジョブ ID とトレース ID は別の値であり、ジョブの一意性にトレース ID を使わない。

## 監視の種類

監視するメトリクスは次の二つに分ける。

- **基盤のメトリクス**：キューのメッセージ数、最古メッセージの経過時間、コンシューマーの停止など、基盤が提供する値。キューの滞留とコンシューマーの停止を検知する。
- **アプリケーションのメトリクス**：処理時間、成功率、失敗率など、コードに計装して出す値。処理のレイテンシ、エラー率、スループットを検知する。

基盤のメトリクスの監視を必須とする。
外部ブローカーを導入するまでは、未完了のイベント出版の件数と最古の発行日時が、キューのメッセージ数と最古メッセージの経過時間に当たる。

アプリケーションのメトリクスは、処理のレイテンシやエラー率に SLO が定められている場合だけ導入を検討する。
SLO がある場合も、基盤のメトリクスだけで対応できないかを先に検討する。
すべての失敗を処理し切ることが求められる業務システムのように SLO を設けない領域では、基盤のメトリクスと適切なログで足りる。

## DLQ の監視

DLQ の滞留時間は、検知の方式にかかわらず監視する。
例として、1日以上残っているメッセージがあれば通知する。

DLQ への退避の検知には、次の二つの方式がある。

- **DLQ のメトリクス**：DLQ のメッセージ数が1以上になったら通知する。アプリケーションがクラッシュしても検知できるが、原因の分析には追加の調査が要る。
- **アプリケーションのログ**：コンシューマーが失敗を検知した時点で詳細なエラーログを出し、ログ監視で通知する。詳細を記録できるが、ログを出す前にクラッシュすると取りこぼす。

次の基準で選ぶ。

- 基盤の再試行で救済される可能性がある場合は、DLQ のメトリクスで監視する。救済された失敗を通知すると誤報になり、運用者が通知を信頼しなくなるためである。この場合、アプリケーションのログは INFO などに下げ、トレース ID で辿れるようにする。
- アプリケーションが再試行の回数を厳密に把握し、再試行しても失敗したと判断できる場合は、アプリケーションのログで監視し、DLQ のメッセージ数による通知は行わない。

## 処理遅延の監視

処理遅延が許されない非同期処理では、次の二つの観点で監視する。

- **レイテンシ**：最古メッセージの滞留時間で、コンシューマーの処理能力の不足を検知する。
- **スループット**：一定時間に処理したメッセージ数と送信されたメッセージ数の比で、詰まらずに流れているか、プロデューサーが送信できているかを検知する。
