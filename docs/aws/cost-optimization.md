# AWSのコストの可視化と削減

AWSのコストは構成で大きく変わるため、設計の段階で各サービスの課金体系を確かめる。
アカウントを組織、環境、システム種別で分けてコストの責任を区切り、システム種別はタグで代用してよい。
コンピューティングの割引はCompute Savings Plans、S3のストレージクラスはIntelligent-Tieringを第一候補にする。

## 課金体系

- 構成を決める前に、使うサービスが時間、スペック、データ量、回数のどれで課金されるかを確かめる。
- IAMやVPCのように無料のサービスも、組み合わせる有料のリソース（ENI、Elastic IP、ログの配信先など）の課金を確かめる。

## 可視化

- アカウントを「組織、環境、システム種別」の組み合わせで分ける。ネットワークの通信料のようにタグで按分できない費用があり、部門の予算ごとに負担を厳密に分けるにはアカウントで区切る必要があるためである。
- 一つの部門が管理する範囲（予算の出所が同じ範囲）では、システム種別をタグで代用してよい。
- タグは、組織（会社、部門、プロジェクト）、環境（本番、検証、開発）、用途（システム種別）、機能（フロントエンド、バックエンドなど）で分ける。
- 支払総額の最小化だけを目的に、一つのアカウントへまとめない。アカウントの分け方は[AWSアカウントの分離と構成](account-structure.md)に従う。

## 請求代行の事業者

AWSの請求を代行する事業者（リセラー）を使う。
請求額が数パーセント下がることが多いためである。

契約の前に、次の事象が今後の利用計画に支障がないかを確かめる。

- サポートの窓口が事業者になり、AWSのサポートへ直接問い合わせられない。
- AWSのコンソールの金額と請求額に差が出て、正確な利用額がわかりにくい。
- AWSアカウントのルートユーザーを事業者が持つ場合がある。

## Savings Plans

- Compute Savings Plansを使う。Fargateに適用され、リージョンや構成が変わっても割引が自動で適用されるためである。EC2を使わないため、EC2 Instance Savings Plansは使わない。

## S3のストレージクラス

- Intelligent-Tieringを第一候補にする。用途ごとにストレージクラスを使い分け、ライフサイクルポリシーで移行を作り込むと、設定が複雑になり運用の負担になりやすいためである。
- 128KB未満のオブジェクトは、Intelligent-Tieringでも低頻度アクセスの階層へ移らない。小さなファイルを大量に置く場合は、別のストレージクラスかストレージを検討する。
- Glacier Flexible RetrievalとGlacier Deep Archiveは、オブジェクトごとに約40KBの管理情報が課金される。小さなファイルは一つにまとめてから置く。
- 保持期間を過ぎたデータの削除は[情報の機密性の分類と取り扱い要件](data-classification.md)に従う。

連携用のストレージは[連携ファイルの保持と削除](../integration/interface-file-retention.md)に従う。
