# 情報の機密性の分類と取り扱い要件

監査対象のAWSリソースを一覧にし、保存するデータの機密性レベルを設計の初期にラベル付けする。
ラベルごとに保管、アクセス制御、暗号化、削除、監査ログの要件を決めて文書にし、AWSのサービスで実装する。
設定値の準拠の確認は[全アカウントで有効にするAWSのセキュリティサービス](security-services.md)で自動化し、この文書では情報の扱いを定める。

## 監査の二つの軸

- **基盤監査**：基盤やサービスの設定値が、セキュリティ基準に準拠しているかを確かめる監査。Security Hub CSPMとAWS Configで多くの項目を自動で検出できる。
- **情報監査**：扱う情報の機密性に応じて、基準に適合した保管と管理ができているかを確かめる監査。マネージドサービスでは自動で検出しにくい。

組織が準拠する基準を定めていない場合も、この文書の項目を最低限決める。

## 機密性のラベル付け

- アカウント、VPC、サブネット、EC2、S3バケット、RDSなど、基準が適用されるリソースを一覧にする。
- 一覧の各リソースに、保存するデータの機密性レベルを付ける。この一覧が監査対象の全体像になる。
- 機密性レベルは組織の分類に従い、組織に分類がなければ次を使う。

- **公開**：誰がアクセスしてもよい情報。製品カタログ、プレスリリースなど。
- **社外秘**：外部に公開してはならない情報。顧客との打合せ資料、企業名だけの顧客リストなど。
- **機密**：漏洩すると企業の競争力や信頼を損なうおそれのある情報。財務情報、技術情報、個人情報を含む顧客情報など。
- **極秘**：漏洩すると企業の存続に関わるおそれのある情報。合併や買収の計画、高度な技術情報など。
- **個人情報**：特定の個人を識別できる情報。マイナンバーを含む特定個人情報と、クレジットカードの会員データは、個人情報とも区別して扱う。

## ラベルごとに決める要件

セキュリティの基準は次の項目を求めるが、具体的な値を示さないことが多い。
組織が業務の要件から値を決め、ラベルごとに文書にする。

- **保管**：バックアップの頻度、保管場所、復旧手順の定期的な確認。
- **アクセス制御**：最小権限の原則に基づき、アクセスできる利用者を必要最小限にする。利用者とグループごとに、職務、役職、部署、機密性レベルからアクセスできる範囲を決める。
- **暗号化**：保管中と転送中のデータの暗号方式と強度、鍵の管理方式、ローテーション。
- **削除**：不要になったデータを復元できない状態にする時期と方法。個人情報は、利用目的の達成を確認したら遅延なく消去する。
- **監査ログ**：取得の有無、監査の間隔、保持期間、改ざんと不正アクセスからの保護。

秘密のローテーションは次のとおりにする。

- システムが自動でローテーションできる秘密（DBのパスワード、暗号鍵など）は、漏洩時の被害を抑えるため定期的にローテーションする。
- 人が記憶するパスワードは、十分な強度とMFAを前提に、定期的な変更を強制しない。頻繁な変更を強制すると、予測しやすい弱いパスワードが選ばれやすくなるためである。

## AWSでの実装

- **保管**：AWS Backupで、監査対象のリソースごとにバックアップの頻度と保存先のリージョンを設定する。DBのバックアップの世代と保管先は[PostgreSQLのバックアップと災害対策](../database/postgresql-backup-and-recovery.md)に従う。
- **アクセス制御**：人とロールには、IAMポリシーで必要な操作だけを許可する。リソースの側では、S3のバケットポリシーやKMSのキーポリシーで、アクセスを許可するアカウントを限定する。クロスアカウントのアクセスや公開は、リソースの側のポリシーで制御する。
- **暗号化**：KMSの対称キー（キー仕様`SYMMETRIC_DEFAULT`）を、単一のリージョンで使う。DRの方針で複数のリージョンが必須の場合や、各リージョンでサービスを提供する場合に限り、マルチリージョンキーを検討する。
- **多層の暗号化**：S3の二層の暗号化（DSSE-KMS）は、金融、医療、政府機関などの要件が多層の暗号化を求める場合に限って検討する。通常はSSE-KMSで足りる。
- **削除**：バックアップはAWS Backupのルールの保持日数で削除する。ログやファイルは、S3のライフサイクルポリシーで削除する。バックアップの削除をS3のライフサイクルポリシーと二重に設定しない。
- **監査ログの保管**：長期の保管はS3に置き、何のログかがわかるバケットに分ける。CloudWatch Logsは保管量あたりの費用が高いため、数週間から数か月の保管で足りる場合に使う。

アプリケーションのログの保持期間は[可観測性データの規約](../observability/conventions.md)に従い、この文書の監査ログと混ぜない。
複数のリージョンを使うかは[災害対策と事業継続の要件](../nfr/disaster-recovery.md)に従う。

## 定期的な見直し

- 新しい脅威、技術の変化、法規制の変更に合わせて、ラベルと要件を定期的に見直す。
- リソースごとに管理する部門が異なる場合も、監査部門が横断して情報を管理し、監査できる運用の流れを決める。
