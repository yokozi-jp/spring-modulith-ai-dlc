# 全アカウントで有効にするAWSのセキュリティサービス

Security Hub CSPM、AWS Config、CloudTrail、GuardDuty、Inspector、Macie、Firewall Manager、IAM Access Analyzerを、開発と検証を含むすべてのデプロイ環境で有効にする。
各サービスはOrganizationsと統合し、セキュリティサービスのアカウントから設定を配布して検知結果を集約する。
組織にセキュリティの要件が別にある場合は、その要件を優先する。

## 有効にするサービス

次のサービスを有効にする。
有効にしたサービスの検知結果はSecurity Hub CSPMへ集める。
有効にするたびに費用が増えるため、省いてよい条件に当たる環境では無効のままにしてよい。

- **Security Hub CSPM**：各サービスの検知結果を集約し、セキュリティ基準への準拠を評価する。必須とする。
- **AWS Config**：リソースの設定を継続的に記録する。必須とする。
- **CloudTrail**：AWSの操作を記録する。必須とする。
- **Inspector**：EC2、コンテナイメージ、Lambdaの脆弱性を検知する。これらを一切使わない場合や、別の脆弱性スキャンで同じ範囲を網羅できる場合は省いてよい。
- **GuardDuty**：マルウェアの活動、不正アクセス、偵察行為を検知する。ごく小規模で外部からのアクセスがほとんどない場合は省いてよい。別の脅威検出の製品を使う場合も併用を基本にする。
- **Macie**：S3の公開状態と機密データを検知する。S3を使わないアカウント、またはS3に機密情報を一切置かないアカウントでは省いてよい。
- **Firewall Manager**：WAFのルールとセキュリティグループを組織全体で管理する。アカウントが少なく、手作業で管理できる規模なら省いてよい。
- **IAM Access Analyzer**：外部からの意図しないアクセスと、長期間使われていないIDを検知する。IAMポリシーが単純で、手作業で確認できるごく小規模な環境なら省いてよい。

各サービスの管理の委任先は[AWSアカウントの分離と構成](account-structure.md)のセキュリティサービスのアカウントとする。

## Security Hub CSPM

- Organizations内の全アカウントと全リージョンの結果を、セキュリティサービスのアカウントへ集約する。
- セキュリティ基準は、要件がなければ「AWS 基礎セキュリティのベストプラクティス」と「CIS AWS Foundations Benchmark」の最新版を有効にする。
- 省庁向けのシステムでは「NIST SP 800-53」も、クレジットカードの決済を含むシステムでは「PCI DSS」の最新版も有効にする。
- 基準に新しい版が出たら、旧版と新版を同時に評価し、段階的に新版へ移る。

検知結果の扱いは[セキュリティの検知結果の分類と対応](security-findings.md)に従う。

## CloudTrail

- 管理イベント、データイベント、ネットワークアクティビティイベントを証跡に記録する。
- データイベントは、すべて記録するとログ量と費用が膨らむため、イベントセレクターで対象を絞る。
- ネットワークアクティビティイベントは、環境内のVPCエンドポイントを対象にし、イベントセレクターで対象を絞る。
- 証跡では、ログファイルの整合性の検証を有効にする。
- 証跡は、監査とログのアカウントのS3バケットへ保存する。
- 保持期間は監査基準から決め、基準がなければ最低1年にする。1年はPCI DSSが定める監査ログの保管期間に合わせた値である。
- Insightsイベントは、監査ログの取得を目的としては有効にしない。対象を細かく絞れず、費用が増えやすいためである。

監査ログを含む情報の保持期間の決め方は[情報の機密性の分類と取り扱い要件](data-classification.md)に従う。

## GuardDuty

- 保護プランはすべて有効にする。
- 監視対象のサービスがない場合や、別の製品で同じ対策を取っている場合は、その保護プランを省いてよい。たとえばコンテナに別のマルウェア対策を入れている場合は、ランタイムモニタリングを省いてよい。
- 保護プランは委任した管理者のアカウントから一括で設定し、各アカウントでの設定漏れを防ぐ。
- 検知結果はS3へエクスポートする。GuardDutyの検知結果は90日で削除されるためである。

## Inspector

- 検知結果をSecurity Hub CSPMへ連携する。
- ECRのスキャンは、プログラミング言語のパッケージも対象にする拡張スキャンにする。ワークロードはFargateで動かし、EC2を使わないため（[ADR-041](../adr/ADR-041-run-ecs-tasks-on-fargate.md)）、ECRのスキャンが脆弱性管理の主な範囲になる。
- 脆弱性への対応は、露出度が高く資産の重要度も高い環境から優先する。
- CVSS以外の基準も使う脆弱性管理のツールを導入している場合は、そのツールの評価で優先度を決める。InspectorはCVSSだけで評価するため、多くの脆弱性が最高の重要度になるためである。

本番へデプロイするイメージの脆弱性と署名の検証は[ADR-020](../adr/ADR-020-sign-and-attest-container-images.md)に従う。
CIでの依存関係の検査は[Lintとテストのリファレンス](../tooling/lint-and-test.md)の`scan-vulns`を参照する。

RDSとAuroraのデータベースエンジンや、ElastiCacheのRedisなど、マネージドサービスのエンジンの脆弱性はInspectorの対象にならない。
PostgreSQLは[PostgreSQLのバージョンアップ](../database/postgresql-version-upgrade.md)に従って定期的に上げる。
その他のエンジンも、サポート情報とセキュリティ修正の確認を定期の運用に含める。

## Macie

- セキュリティサービスのアカウントから、各アカウントへ設定を展開する。
- バケットの公開と暗号化の状態を監視するポリシーの監視と、機密データの自動検出の両方を使う。
- 機密データの自動検出は、マネージドデータ識別子を検知ルールに使う。
- マイナンバーや郵便番号など日本固有の個人情報はマネージドデータ識別子にないため、扱う場合はカスタムデータ識別子を加える。
- 機密情報を置くことが前提で、堅牢化と監視をしているバケットは、自動検出の対象から外してよい。
- 検知結果をSecurity Hub CSPMへ連携する。
