# セキュリティの検知結果の分類と対応

重要度が「重要」と「高」の検知結果は必ず対応し、「中」以下は計画を立てて半年以内に対応する。
想定外の設定変更による「重要」は即座に、「高」は翌営業日を目途に直す。
常時監視していない環境では、「重要」と「高」を即時に通知する。

有効にするサービスとセキュリティ基準は[全アカウントで有効にするAWSのセキュリティサービス](security-services.md)に従う。

## 重要度

Security Hub CSPMは検知結果に重要度を自動で付ける。

- **重要**：悪化を防ぐため、直ちに修復する。例は、リスクの高いポートへの無制限のアクセスを許すセキュリティグループ、公開されたRDS、ルートユーザーのアクセスキー。
- **高**：短期の優先事項として対処する。例は、EC2のパブリックIPv4アドレス、通信を許可するVPCのデフォルトのセキュリティグループ。
- **中**：中期の優先事項として対処する。例は、MFAのないコンソールのIAMユーザー、EBSのデフォルト暗号化の無効、VPCフローログの無効。
- **低**：独自の対応は要らない。例は、タグのないIAMロール、未使用のElastic IP。

## 想定外の設定変更による検知

運用中に想定外の設定変更で検知された結果は、次の期限で直す。

- **重要**：即座に修正を完了させる。
- **高**：翌営業日を目途に対応する。

## 検知結果の分類

セキュリティ基準を有効にした直後など、まとまって検知された結果は次のパターンに分類する。

- **A**（重要、高）：設定を見直す。1か月以内に「解決済み」にする。
- **B**（重要、高）：この環境では例外として許容する。例外の理由を記録し、「無効化」にする。
- **C**（重要、高）：設計上回避が難しい。理由を記録して暫定対策を検討し、1か月以内に実施してから「抑制済み」にする。
- **D**（中）：急がない。「通知済み」にし、半年以内に対応する予定を決める。
- **E**（低）：許容する。重要度が「中」に上がるまでは対応しない。

対応が追いつかずに未対応の結果を積み上げると、運用者が通知を確認しなくなる。
必須の対応は「重要」と「高」に絞り、「中」以下は計画に組み込んで解消する。

## 開発と検証の環境

本番と同じ厳密さを求めると開発の速度を損なうため、次のとおり範囲を絞る。

- セキュリティ基準は「AWS 基礎セキュリティのベストプラクティス」と「CIS AWS Foundations Benchmark」に限ってよい。
- 分類と対応はパターンA、B、Cだけにする。
- 「中」と「低」は月次などの頻度で棚卸しし、リスクを受容するか、バックログに積んで対応を計画するかを決める。

## 即時通知

定期的な監視の運用がない環境（開発環境など）では、「重要」と「高」の検知結果をメール、チャット、チケット管理システムのいずれかへ即時に通知する。
EventBridgeのルールでSecurity Hub CSPMの検知結果を絞り込んで通知する。
開発や検証の環境でも、誰でもアクセスできるポリシーを誤って作ると、数日以内に攻撃を受けることがあるためである。
