# レビューコメントの書き方と承認

レビューコメントには意図を示すラベルを付け、`MUST`と`ASK`が解決するまで承認しない。
指摘は修正の方向が分かるように具体的に書き、論理的に説明できない指摘はしない。
指摘は最初のレビューで出し切り、同じ問題は該当箇所すべてにコメントする。

## 基本姿勢

レビューはコミュニケーションであり、相手への敬意を保って書く。
レビュアーとレビュイーの間に上下関係を作らない。
良い点は`LGTM`のラベルで具体的に伝える。

## ラベル

コメントの先頭に`[MUST]`のようにラベルを付ける。

承認の前に解決が必要なラベルは`ASK`、`Q`、`MUST`だけである。

- **`LGTM`**：良い点の評価。レビュイーは返信しなくてよい。
- **`ASK`、`Q`**：質問。レビュイーは回答する。
- **`MUST`**：必須の修正。レビュイーはコードを修正するか、修正しない理由を返信する。
- **`SHOULD`**：修正の提案。レビュイーはできる限り修正し、見送る場合は理由を返信して、Issueを作り次のリリースまでに対応する。
- **`IMO`**：個人の意見。対応するかはレビュイーが決め、リアクションか返信で応える。
- **`NITS`**：細かな指摘。扱いは`IMO`と同じである。

修正を求めるときは`MUST`か`SHOULD`を使い、要求を質問の形で書かない。
`ASK`は理解するための質問に限る。

## 指摘の書き方

- 「可読性が低い」のような評価だけで終えず、どの箇所をどう直してほしいかを書く。
- 直し方をレビュイーに考えてほしい場合は、そのことをコメントに書く。
- 理由を論理的に説明できない違和感は、指摘しない。
- 根拠になる公式文書や規約があれば、URLを添える。

## 指摘を出し切る

最初のレビューで指摘を出し切る。
2回目以降のレビューで新しい問題に気付いた場合は、前回見落としたことを書いたうえで指摘する。

指摘が多くても省略しない。
同じ問題が複数の箇所にあるときは、「横展開してください」で済ませず、該当箇所すべてにコメントする。

## Suggested changes

修正内容が一意に決まるtypo、コードコメントや文書の言い回しは、Suggested changesで示す。
変数名の変更のように一箇所だけ直すとビルドやテストが壊れる修正は、Suggested changesにせずコメントで示す。
教育のためにレビュイー自身に直させるのは、Suggested changesで繰り返し示しても直らない場合に限る。

## 投稿とレビューの終了

コメントはAdd single commentで一件ずつ投稿し、レビュイーがすぐに読んで返信できるようにする。
レビューを終えたら、ApproveかRequest changesでレビューを提出し、終わったことをレビュイーへ伝える。

## 承認の判断

承認の前に解決が必要な指摘がなければ、残りの指摘への対応を待たずに承認する。
承認後に指摘を反映したcommitを追加すると承認は取り消され、再承認が必要になる。
先に承認した指摘を検討せずにマージするレビュイーには、対応を確認してから承認してよい。
