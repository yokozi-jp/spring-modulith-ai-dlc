# レビュアーの進め方

レビュー依頼には自分の作業より優先して反応し、すぐに見られないときは確認する時期を返す。
レビュイーが見落としやすい観点を重点的に確認し、分からない点は質問し、自信のない領域は詳しい人へ回す。
動作確認はCIとテスト戦略に任せ、レビュアーはローカルで再現しなくてよい。

## 依頼への反応

- コードレビューを自分の作業より優先する。
- すぐに見られない場合は、確認する時期をコメントするか、代わりにレビューできる人へ依頼する。
- レビューするPull RequestではReviewersに自分を設定する。

## 確認の進め方

base branchが`main`以外のPull Requestは、意図した向き先かを最初に確認する。
レビュイーの経験や担当範囲から見落としやすい観点と影響範囲を、重点的に確認する。
何を人が確認するかは[レビューで人が確認する範囲](../code-review/review-scope.md)に従う。

## 動作確認

レビュアーはローカルでの動作確認を必須にしない。
テストの成否はCIで確認し、品質の担保は[バックエンドのテスト戦略](../backend/testing-strategy.md)と[フロントエンドのテスト戦略](../frontend/test-strategy.md)に従う。
CIで確認できない点（画面の見た目など）は、レビュイーに[Pull Requestテンプレート](../../.github/PULL_REQUEST_TEMPLATE.md)の「CI 以外で確認したこと」へエビデンスを貼るよう求める。

## 分からない点

意図が分からない箇所は、分かったことにせず質問する。
レビュイーがテックリードでも若手でも、質問を控えない。

- 不明点が少なければ、レビューコメントで質問する。
- 不明点が多ければ、ビデオ会議のような同期の会話で確認し、日程はレビュアーから調整する。

自信のない領域は、無理にレビューせず詳しい人へ回す。
業務要件や機能要件が不明確な場合はプロダクトの責任者へ、非機能要件に自信がない場合はアーキテクトへ回す。

## 指摘が多い場合

指摘が多くても、[レビューコメントの書き方と承認](review-comments.md)に従ってすべてコメントする。
作業量が多い場合は、同期の会話で確認することをためらわない。

新しく参加したメンバーに指摘が多い場合は、レビューとは別に次のフォローをする。

- 指摘が多くても問題ないことを伝える。
- 指摘の背景にある規約や採用技術を説明する場を設ける。
- ペアプログラミングで一緒に修正する。
