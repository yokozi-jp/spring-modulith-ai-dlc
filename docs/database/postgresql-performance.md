# PostgreSQLの性能対策と負荷分散

実行計画はプランナーに任せ、想定どおりにならない場合だけヒント句で固定する。
読み込みの負荷はリードレプリカで分散し、書き込みの負荷はスケールアップで受ける。
リモートキャッシュは、チューニングとリードレプリカで解決できない場合に限って導入する。

## ヒント句と実行計画

- 開発時はヒント句を書かず、プランナーが作る実行計画に任せる。
- 実行計画が想定どおりにならない、または安定しない場合に限り、ヒント句かWITH句による書き換えで固定する。
- 結合方式を制限するパラメータは、アプリケーションから`SET LOCAL`で設定せず、ヒント句の中に`Set(...)`で書く。SQLのコメントとして扱われ、SQL単体で再現できるためである。
- ヒント句を付けた理由をSQLの近くにコメントで残す。

ヒント句には`pg_hint_plan`拡張が必要になる。
拡張機能は[PostgreSQLのサーバー設定と拡張機能](postgresql-server-configuration.md)に従う。

プランキャッシュの動作（`plan_cache_mode`）は既定の`auto`にする。
100を超えるパーティションがある場合と、同じSQLがある回数以降に遅くなる場合に限り、`force_custom_plan`または`force_generic_plan`を検討する。

## 接続プール

接続プールの大きさと接続取得の待ち時間は、[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)の接続予算に従う。
接続の最大寿命は必ず設定し、HikariCPの`max-lifetime`を無効にしない。
不安定になった接続を定期的に破棄して、自律的に復旧させるためである。

## スケールの選び方

パラメータとSQLの調整で性能要件を満たせない場合に、DBの処理能力を増やす。

- **読み込みの性能不足**：リードレプリカを追加する。稼働率が低いリードレプリカは減らす。
- **書き込みの性能不足**：インスタンスのサイズを上げる。
- **ローカルストレージの不足**：不要なログを削除できない場合に、インスタンスのサイズを上げる。

インスタンスのサイズは小さく始め、性能テストの結果で必要なサイズまで上げる。
シャーディングはシステムへの影響が大きいため、通常は選ばない。

## リードレプリカの使い方

リードレプリカを導入した場合は、DBを参照するだけの処理（Web APIのGETなど）をリードレプリカへ、書き込みを伴う処理をプライマリへ接続する。
参照が大部分で最後に書き込む処理を両方へ振り分ける方式は、設計判断が難しくなるため、理由がある場合に限る。

- 接続先はDNS名で指定し、フェイルオーバーに追随できるようにする。
- 運用でのデータ調査はリードレプリカへ接続する。

プライマリからリードレプリカへの反映には遅延がある。
更新の直後に一覧を再検索するような処理で古いデータを表示できない場合は、参照の要求にプライマリから読むオプションを設ける。
反映の遅延が数十ミリ秒程度と小さく、古いデータを一時的に表示しても再読み込みで済む構成では、対策を取らなくてよい。

## リモートキャッシュの導入条件

DBの前段に置くキャッシュサーバー（Redisなど）は、まずキャッシュなしのチューニングとリードレプリカで対処し、それでも解決できない場合に限って導入する。
キャッシュとDBの整合性の維持、構成要素の増加による運用とテストの負担が増えるためである。

次のように、DBへの高負荷が明らかな場合は導入を検討する。

- キャンペーン時にアクセスが急増するような、読み込みが大部分を占める処理。
- 読み込みの負荷が高いセッション管理。
- ダッシュボードのような、計算や集計の結果の再利用。

## キャッシュの更新方式

キャッシュを導入する場合は、次のどちらかの方式にする。

- **Write Through**：DBへの書き込みと同時にキャッシュへも書き込む。キャッシュを常に最新に保てるが、DBとキャッシュの両方への書き込みの整合性を設計する必要がある。
- **Write Behind**：集計のような時間のかかる処理の結果を、定期的にキャッシュへ書き込む。キャッシュとDBの値に差が出るため、業務ロジックはDBの値を正として実装する。

キャッシュにない場合にDBを読んで保存するRead Through（Cache Aside）は使わない。
キャッシュとDBの値の差を許容できない場合が多いためである。
DBへの書き込みを非同期で後回しにするWrite Backは、データを失うおそれがあるため使わない。

キャッシュの有効期限（TTL）は必ず設定し、容量を超えたときの破棄方式はLRUなど効果を確認したものを選ぶ。
