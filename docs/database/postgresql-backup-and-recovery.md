# PostgreSQLのバックアップと災害対策

サーバー障害とデータセンター障害には、自動復旧と複数のアベイラビリティゾーンの構成で備える。
復旧の方式はRPOとRTOから決め、バックアップは自動バックアップを基本にする。
直近の世代に加えて週次の世代を残し、手動のバックアップは別のリージョンへ複写する。

## 緊急事態ごとの対策

- **データセンター内のサーバー障害**：自動復旧で備える。必須とする。
- **落雷や竜巻によるデータセンターの停電や破損**：複数のアベイラビリティゾーンの構成で備える。必須とする。
- **一つの地方全体の災害**：国内の複数リージョンの構成で備える。プロジェクトごとに決める。
- **国内の複数の地方で同時に起きる災害**：海外を含む複数リージョンの構成で備える。プロジェクトごとに決める。

単一障害点を作らない。
複数リージョンの構成は、事業継続計画（BCP）と費用に依存するため、システムの都合だけで決めない。

## 復旧要件

- **RPO**：目標復旧時点。どの時点までデータを戻す必要があるか。
- **RTO**：目標復旧時間。システムの復旧にどれだけ時間をかけられるか。

RPOとRTOを定義し、バックアップとリストア、パイロットライト、ウォームスタンバイ、マルチサイトのどの復旧シナリオにするかを決める。

## バックアップの方法

- 基本は、マネージドサービスの自動バックアップ（ポイントインタイムリカバリ）を使う。
- 自動バックアップの保持期間より古い時点を残したい場合に、手動のスナップショットを使う。

スキーマの切り戻しでバックアップを確認する手順は[DBのデプロイと切り戻し](runbook-deploy-and-rollback.md)に従う。

## バックアップの世代

直近の世代に加えて、それより前の時点のバックアップも残す。
誤操作によるデータの書き換えが数週間後に発覚した場合や、ランサムウェアによるデータの汚染から復旧するためである。

- 直近の世代（日次3世代など）は自動バックアップで残す。
- それより前の世代（週次4世代など）は手動のスナップショットで残す。
- 手動のスナップショットは別のリージョンへ複写する。
- 新しいバックアップを取得してから古いバックアップを削除し、規定の世代数を下回る時間を作らない。
