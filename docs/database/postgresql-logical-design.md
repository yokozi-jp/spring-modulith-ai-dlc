# PostgreSQLのテーブル論理設計

テーブルはマスタ、トラン、ワーク、サマリの種別に分け、第3正規形を基本とする。
区分値は連番のコード値で持ち、定義はソースコードで管理する。
論理削除フラグは作らず、業務上の意味を持つカラムか物理削除で表す。

## 対象

この規約は、モジュールが所有する業務テーブルに適用する。
Spring Modulithのイベント出版テーブルのように、フレームワークがスキーマを定めるテーブルには適用しない。
スキーマの所有は[ADR-011](../adr/ADR-011-use-module-owned-database-schemas.md)に従う。

## テーブル種別

- **マスタ**：顧客や商品のように、システムが参照するリファレンスデータを持つテーブル。改廃しない。
- **トラン**：売上や取引のように、日々発生するイベント、契約、操作を記録するテーブル。保持期限を過ぎたら改廃する。
- **ワーク**：トランやマスタへの反映、画面や帳票への出力のために中間結果を持つテーブル。短い保持期限で改廃する。I/F受信ワークとI/F送信ワークもこの種別に含める。
- **サマリ**：日次や月次の集計結果を持つテーブル。保持期限を過ぎたら改廃する。

種別ごとの接頭辞は[PostgreSQLの命名規約](postgresql-naming.md)で定める。
種別ごとの保持期限と改廃方法は[PostgreSQLのパーティションと改廃](postgresql-partitioning-and-retention.md)で定める。

## 正規化

第3正規形を基本とする。
非正規化は、インデックス設計と実行計画の調整では応答要件を満たせず、結合回数を減らす以外に手段がない場合に限る。

## バリュードメイン

**バリュードメイン**：カラムが取りうる値の集合。`numeric(10, 2)`や性別区分がこれに当たる。ISO 11179の呼称で、ドメイン駆動設計のドメインと区別する。

カラムを設計するときは、同時にバリュードメインを定義する。
請求先顧客コードと取引先顧客コードのように同じ意味のカラムは、同じバリュードメインへ対応させ、同じデータ型と桁数を使う。

## 区分値

**区分値**：性別区分や購入区分のように、業務上の意味を持つ値の集合。

- 区分値は`01`、`02`のような連番のコード値で持ち、`unpurchased`のような意味のある文字列にしない。
- 「不明」や「適用不能」を表すコード値を体系に含め、NULLで代用しない。
- 区分値と名称の対応はソースコードまたは定義ファイルで管理し、区分値管理テーブルを作らない。
- 定義ファイルを正とする場合は、そこからコードを生成する。
- データ基盤へ連携するときは、区分値ごとの参照テーブルを連携用に作る。

区分値カラムの型は[PostgreSQLのデータ型](postgresql-data-types.md)に従う。

## スナップショット属性

**スナップショット属性**：受注時の商品単価のように、マスタの値をトランへ複写したカラム。

スナップショット属性には、複写元と別の名前を付ける。
たとえば商品マスタの「商品単価」を複写したカラムは「受注商品単価」とする。

## 導出属性

**導出属性**：受注の合計金額のように、同じテーブルの他のカラムから計算できる値。

導出属性は、次のどちらかに当てはまる場合だけカラムとして持つ。

- 画面や帳票に表示する、価格のような重要な値である。
- 計算に複雑な業務ロジックが必要で、分析者が別カラムで参照する方が扱いやすい。

## 真偽値の代替

`boolean`のカラムを作る前に、情報を増やせる別の型で表せないか確認する。

- **日時にする**：`is_verified`の代わりに、NULL許容の`timestamptz`の`verified_at`を持つ。
- **区分値にする**：`is_completed`の代わりに、未処理を既定値とする状態区分を持つ。
- **件数にする**：`has_comments`の代わりに`comment_count`を持つ。件数は更新のたびに書き換えるため、更新負荷が増える。

## 論理削除

`deleted_flg`のような論理削除フラグは作らない。
削除を表したい場合は、次の順で検討する。

1. 退職、既読、有効期間切れ、廃盤、承認状態のように、業務上の意味を持つカラムで表す。
2. 本当に削除する要件なら物理削除し、誤操作からの復元や監査での参照が要件にあるときだけアーカイブテーブルへ退避する。

法令や契約でアーカイブなしの削除が求められる場合は、退避しない。

## 多言語データ

画面の文言だけを多言語化する場合は、DBを変更しない。
APIとSPAの文言のローカライズは[ADR-016](../adr/ADR-016-localize-api-and-spa-messages.md)に従う。

一つのDBで同じエンティティを複数の言語で表示する場合は、表示ラベルをマスタからラベル用のテーブルへ正規化し、応答を返すときに結合する。
非同期処理の通知のように`Accept-Language`を受け取れない処理で言語が必要なら、利用者の言語をユーザーマスタに持つ。
