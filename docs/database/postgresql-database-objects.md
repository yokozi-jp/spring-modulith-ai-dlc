# PostgreSQLのテーブル以外のDBオブジェクト

業務ロジックはアプリケーションに置き、関数とトリガーに持たせない。
ビューとマテリアライズドビューは入れ子にせず、使う場面を限る。
テーブル継承とdblinkは使わず、他システムのDBとはI/FかWeb APIで連携する。

## 関数

関数は、一般的な事実に基づく処理か、業務上ほとんど変わらない処理に限って作ってよい。
Oracleからの移行で使う互換関数や、体系を持つSKUコードから品番を取り出す補助関数がこれに当たる。

テーブルを参照する関数は作らない。
テーブル間の依存関係が見えなくなり、リリースで想定外の障害を招くためである。
`CREATE OR REPLACE FUNCTION`による関数の更新はロックを伴うため、リリース時の影響を確認する。

## トリガー

トリガーは使わない。
次の用途も、アプリケーションで明示的に実装し、テストで検証する。

- 作成日時などの共通カラムの登録。
- 物理削除する行の別テーブルへの退避。
- 変更履歴の別テーブルへの記録。
- 登録前のデータ整合性の検証と、関連テーブルの参照整合性の維持。

監査のようにアプリケーション以外の要件から変更履歴が必要な場合と、他の方法では要件を満たせない場合に限り、理由をPull Requestに書き、レビューで合意してから使う。

関数とトリガーに業務ロジックを持たせないため、pgTAPなどによるDB単体テストは書かず、アプリケーションのテストで検証する。
DBを使うテストの書き方は[バックエンドのDBテスト](../backend/testing-database.md)に従う。

## ビュー

- ビューを元に別のビューやマテリアライズドビューを作らない。
- カラムは必要なものだけを定義し、元のテーブルの全カラムを並べない。
- 3箇所以上から使われる場合に限って作る。
- 更新可能ビューに対してUPDATEやDELETEを発行しない。
- `CREATE TEMPORARY VIEW`を使わない。スロークエリとして検知したSQLを単体で再実行できなくなるためである。
- 定期的に棚卸しし、使われていないビューを削除する。

ビュー自体にはインデックスを作れないため、アクセスの仕方に合わせて元のテーブルのインデックスを確認する。

## マテリアライズドビュー

マテリアライズドビューは、元のテーブルとの差を許容でき、アプリケーションの高速化に大きく寄与する場合に限って使う。
ビューと同じく、入れ子にせず、カラムを絞り、使われていないものを削除する。

- 更新の時刻と間隔を、マテリアライズドビューを作るchangesetの`comment`に書く。
- 更新は`REFRESH MATERIALIZED VIEW CONCURRENTLY`で行い、更新中も参照できるようにする。`CONCURRENTLY`にはユニークインデックスが必要になる。
- 集計結果を参照専用で持つ場合は、実テーブルをTRUNCATEして入れ直すサマリテーブルより、マテリアライズドビューを優先する。
- パーティションごとにデータを入れ替える必要がある場合は、マテリアライズドビューはパーティション化できないため、実テーブルにする。

## テーブル継承

テーブル継承（`INHERITS`）は使わない。
共通カラムは各テーブルに直接定義する。
継承を使ったパーティショニングも使わない。

## 一時テーブル

一時テーブルは、次の条件をすべて満たす場合に使ってよい。

- 使うことで処理が速くなる。
- 画面からの要求のようなオンライン処理で使い、定時処理では使わない。
- そのトランザクションの中だけで使い、消えても問題がない。

一時テーブルは`ON COMMIT DELETE ROWS`を付けて作り、トランザクションの終了時に行を消す。
接続プールで接続を使い回すと、一時テーブルのメモリ（`temp_buffers`）を接続数分確保し続けるため、メモリの見積もりに含める。
後で性能調査が見込まれる処理は、実テーブルへ切り替えやすい形にしておく。

定時処理の中間データには、スロークエリを再現しやすいワークテーブルを使う。
ワークテーブルに挿入した行は、コミットするまで統計情報に反映されないため、同じトランザクションの後続のクエリの実行計画が想定と変わることがある。

## LISTEN/NOTIFY

PostgreSQLのLISTEN/NOTIFYによるPub/Subは、使う前にADRで判断する。
モジュール間のイベントにはSpring Modulithのイベント出版を使っており、役割が重なるためである。
モジュールの構成は[ADR-001](../adr/ADR-001-adopt-spring-modulith-modular-monolith.md)に従う。

## dblinkとpostgres_fdw

dblinkとpostgres_fdwは、自システムから接続する場合も、他システムから接続される場合も使わない。
スキーマが他システムと密結合になり、相手のDBの障害やバージョンアップが自システムへ波及するためである。

- DB間でデータを連携する場合は、システム間のI/F（ファイル）を作る。
- データの鮮度が重要な場合は、Web APIを作る。
- 他システムに自システムのテーブルをdblinkやpostgres_fdwで参照させない。

相手のシステムがI/Fを作れないなど避けようがない場合は、次のように使い方を絞る。

- 参照だけに限り、更新しない。自システムが参照される場合は、リードレプリカへ接続させる。
- 自システムのテーブルを更新させない。
- dblinkではなくpostgres_fdwを使う。
- テーブル名に`fdw_`の接頭辞を付けたビューを作り、必要なカラムと行だけを公開する。
- そのビューだけにアクセスできるロールを作る。

一度だけの初期データ移行も、同じ条件で使う。
OLAPから外部表で読み込む場合の例外は[PostgreSQLと他のデータストアの連携](postgresql-data-integration.md#olapへの連携)に従う。
