# PostgreSQLの時間で変わる業務データ

営業日単位の登録や集計が必要な場合は、システム日付と別に業務日付を管理テーブルで持つ。
適用期間付きデータは開始日と終了日をNOT NULLの`date`で持ち、排他制約で期間の重なりを防ぐ。
マスタの世代は履歴テーブルへ分け、アプリケーションが同じトランザクションで記録する。

## 業務日付

**業務日付**：システム日付と別に管理する、業務上の日付。営業時間が深夜をまたぐ店舗の営業日などを表す。

次のどれかが必要な場合は、業務日付を管理する。

- システム日付とずれた営業日単位で登録や集計を行う。
- 日をまたぐ処理や画面操作で、データの整合性を保つ。
- 障害調査や結合テストで、特定の日付の動作を再現する。

業務日付は次のように扱う。

- 業務日付は業務日付管理テーブルに`date`で登録し、オンライン用とバッチ用を区分して持てるようにする。
- 業務日付管理テーブルは、日替わりの処理で自動的に更新する。
- 業務日付を持つかどうかはモジュールごとに業務要件で決め、将来別のサービスへ切り出す可能性が高いモジュールは最初からモジュール単位で持つ。
- 作成日時や受注日時のように実際に発生した時刻には、業務日付ではなく`Clock`から取ったシステム時刻を使う。そのため、業務日付と受注日時の日付はずれることがある。
- 複数のモジュールやシステムが連携する処理では、最上流で業務日付を取得し、下流には引数で渡す。下流は業務日付管理テーブルを参照せず、渡された値を正とする。

複雑な定時処理がなく、パーティションテーブルもないかデータ量が限られるアプリケーションでは、業務日付を管理しなくてよい。

日付だけの値の型は[日時とタイムゾーンの規約](../datetime/timezone-conventions.md)に従う。

## 適用期間付きデータ

**適用期間付きデータ**：来月からの販売単価のように、開始日（`start_date`）と終了日（`end_date`）で適用期間を持つデータ。

- 主キーはサロゲートキーにする。
- 業務キーと`end_date`の組にユニークインデックスを張り、最新の行をインデックスで取得できるようにする。
- 排他制約で期間の重なりを防ぐ。重なりは防げるが、期間の抜けは防げないため、アプリケーションで検証する。
- 開始日と終了日はNOT NULLにし、期限がない場合は最小`0001-01-01`、最大`9999-12-31`を使う。
- `infinity`と`-infinity`を使わない。Javaの標準の日付型やDWHへの連携で変換が必要になるためである。
- 開始日と終了日を範囲型（`daterange`など）のカラムにしない。
- 開始日と終了日の判定にどの日付（システム日付、受注日、出荷予定日など）を使うかは、業務要件で決める。

```sql
CREATE TABLE m_unit_price (
    unit_price_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    item_id BIGINT NOT NULL,
    unit_price NUMERIC(10, 2) NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    EXCLUDE USING gist (
        item_id WITH =,
        daterange(start_date, end_date, '[]') WITH &&
    )
);
CREATE UNIQUE INDEX uk_m_unit_price ON m_unit_price (item_id, end_date);
```

排他制約に必要な拡張機能は[PostgreSQLの制約とインデックス](postgresql-constraints-and-indexes.md#排他制約)に従う。

## 世代管理

**世代**：マスタの値を更新したときに、更新前の値を参照できるように残したもの。適用期間とは別の概念である。

- 最新の世代だけを本体のテーブルに持ち、過去の世代を追記だけの履歴テーブルに持つ。
- 履歴テーブルへの記録は、アプリケーションが本体の更新と同じトランザクションで行い、テストで検証する。トリガーで記録しない。
- 過去の世代を含めて一覧表示する要件が多く、データ件数も少ないマスタに限り、同じテーブルに世代番号を持たせてよい。

履歴テーブルの接頭辞は[PostgreSQLの命名規約](postgresql-naming.md#テーブル名)に従う。

## 操作時の地域タイムゾーン

利用者が操作した時点の地域の時計の時刻を後から再現する必要がある場合は、`timestamptz`の日時と別に、IANAタイムゾーンIDをカラムに持つ。
UTCからのオフセットではなく地域IDを持つ理由と型の扱いは、[日時とタイムゾーンの規約](../datetime/timezone-conventions.md)に従う。

定時処理を利用者ごとの地域の0時に動かす場合も、利用者のタイムゾーンIDをユーザーマスタに持つ。
