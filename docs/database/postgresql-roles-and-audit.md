# PostgreSQLのロールと監査

保守運用者の権限は、ログインできないロールに付け、そのロールを個人ごとのDBユーザーへ付与する。
ロールは管理者、メンテナンス、読み取り専用に分け、共有アカウントを作らない。
監査ログはpgAuditのセッション監査で取り、保守運用ユーザーの操作はすべて記録する。

## 対象

この規約は、保守運用者がDBへ接続するためのロールとユーザー、および監査ログに適用する。
アプリケーションとマイグレーションが使う資格情報とロールの分離は、[DB接続情報とロール分離](connections.md)に従う。

## ロールの設計

- ロールにはログインさせず、権限はロールからDBユーザーへ付与する。
- 各ロールの権限は、最小権限の原則に従い実用の範囲で絞る。
- ロールの継承は許可するが、入れ子を深くしない。継承元の権限が単純なら、継承せずに平らに管理する。

保守運用者のロールは、目的ごとに分ける。

- **`{接頭辞}_ope_admin`**：管理者のロール。ユーザーの作成とロールの付与を含むすべての操作ができる。
- **`{接頭辞}_ope_maintainer`**：メンテナンスのロール。データパッチとデータの参照ができる。
- **`{接頭辞}_ope_readonly`**：読み取り専用のロール。データの参照だけができる。

`{接頭辞}`はシステムを識別する短い名前とする。
スキーマ変更はマイグレーションのジョブだけが行い、保守運用者のロールには`CREATE`、`ALTER`、`DROP`を与えない。
マイグレーションの経路は[DBマイグレーション規約](migrations.md)に従う。

## DBユーザーの払い出し

- アプリケーションのユーザーと保守運用者のユーザーを分ける。
- 保守運用者のユーザーは、監査で作業者を特定できるよう、個人ごとに払い出す。
- メンテナンス以上のロールを付与する個人には、読み取り専用のユーザーも別に払い出す。
- 人の入れ替わりが激しく個人ごとの払い出しが運用に耐えない場合に限り、会社や部署の単位で払い出す。
- ロールごとに一つのユーザーを作って共有しない。

ユーザー名は次の形式にする。

- **個人単位**：`{接頭辞}_ope_{組織名}_{個人名}`、読み取り専用は`{接頭辞}_ope_{組織名}_{個人名}_readonly`
- **組織単位**：`{接頭辞}_ope_{組織名}`、読み取り専用は`{接頭辞}_ope_{組織名}_readonly`

踏み台サーバーを個人ごとに払い出し、DBユーザーを組織単位にする場合は、踏み台の操作ログとDBの監査ログを突き合わせて作業者を特定できるようにする。

## 監査ログの取得

監査ログは`pgAudit`で取る。
「誰が」「いつ」「どのリソースに」「どの操作をして」「どうなったか」を記録する。
`log_statement = all`は、接続情報が出ず性能への影響が大きいため使わない。

基本はユーザー単位のセッション監査で取る。
セッション監査でログが膨大になる場合に限り、テーブルや列の単位のオブジェクト監査を併用する。

## 監査の対象

アプリケーションのDML（READとWRITE）は、アプリケーションのログで追跡できるため監査の対象にしない。
アプリケーションのユーザーが通常行わない操作と、保守運用者の操作を対象にする。
権限上実行できない操作は、調査を容易にするため対象から外す。

- **アプリケーションのユーザー**：`DDL`を対象にする。`FUNCTION`などを権限上許可している場合は、それも対象にする。
- **保守運用者のユーザー**：`ALL`を対象にする。
- **保守運用者の読み取り専用ユーザー**：`READ`を対象にする。

## 監査ログの通知

監査ログは出力と同じ粒度で通知せず、対応が必要な場合だけ通知する。
たとえば、個人情報を含むテーブルを読み取り専用ユーザーが参照したときに、事前の申請と照合する運用がある場合に通知する。
