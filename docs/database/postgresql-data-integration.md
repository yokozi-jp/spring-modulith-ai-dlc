# PostgreSQLと他のデータストアの連携

マスタデータの配布は、定期的なファイル連携を基本にし、鮮度が必要な場合は変更を非同期で送る。
全文検索エンジンへの複写は、アプリケーションが同期的に両方へ書き込む。
OLAPへの連携は、そのOLAPが他の用途に広がるかどうかで方式を選ぶ。

## 対象

この規約は、PostgreSQLを正のデータストアとし、他のシステムやデータストアへデータを渡す場合に適用する。
DBをdblinkやpostgres_fdwで直接つなぐことの制限は[PostgreSQLのテーブル以外のDBオブジェクト](postgresql-database-objects.md#dblinkとpostgres_fdw)に従う。

## マスタデータの配布

下流のシステムがマスタを参照するだけの場合は、次の方式から選ぶ。
複数のシステムが同じマスタを編集する場合は、マスタデータ管理の仕組みを別に検討する。

- **定期的なファイル連携**：連携先向けにマスタを抽出したファイルを定期的に作る。基本はこの方式にする。
- **変更の非同期送信**：マスタが変わった時点で差分を送る。鮮度が必要な場合に、ファイル連携と組み合わせる。

DBの共有とWeb APIでの都度参照は、システム間の結合と性能の問題が大きいため使わない。

ファイル連携では、数百万件程度までは全件を連携し、連携先は受信のたびにマスタを入れ替える。
件数が多い場合は、最終更新日で差分を抽出する。
差分の抽出に共通カラムの`updated_at`は使わず、業務用の更新日時のカラムを定義する。
共通カラムの扱いは[PostgreSQLの共通カラム](postgresql-common-columns.md)に従う。

- 関連する複数のテーブルを連携する場合は、整合性を確認できたデータだけを配信用のテーブルへ移し、そこから連携する。
- 連携先の要望に合わせてテーブルを結合したファイルを作らない。連携先が増えるたびにファイルが増えるためである。

変更の非同期送信には、CDCで随時反映する方式と、1時間ごとなどに最終更新日で抽出する方式がある。
定時の抽出はDBの負荷が問題になるため、リードレプリカから参照する。

## 全文検索エンジンへの複写

PostgreSQLを正とし、検索の処理を全文検索エンジン（OpenSearchなど）へ移す構成では、PostgreSQLのデータの一部を全文検索エンジンへ複写する。

- アプリケーションが、PostgreSQLと全文検索エンジンの両方へ同期的に書き込む。責任の分担が明確になり、ローカルを含む各環境でテストしやすいためである。
- 遅延などの制約で同期的に書き込めない場合に限り、論理デコードで変更を取り出して非同期に複写する方式を検討する。

全文検索エンジンを導入する条件は[PostgreSQLのサーバー設定と拡張機能](postgresql-server-configuration.md#全文検索の手段)に従う。

## OLAPへの連携

集計を多用するOLAP（DWH）を業務システムのDBと分ける場合は、次の方式から選ぶ。

- そのOLAPを一つの業務領域でしか使わない場合は、OLAPから外部表で定期的にロードしてよい。
- 将来データ基盤へ育つ場合は、依存を下げるため、定期的に連携用のファイルを作って投入する。
- アプリケーションからOLTPとOLAPの両方へ書き込む方式は、データの鮮度がどうしても必要な場合に限る。OLAPの性能に引きずられて応答が遅くなるためである。
