# PostgreSQLのデータ型

使うデータ型の種類を絞り、値の種類ごとに決めた型を使う。
文字列は桁数を指定した`varchar(n)`、連番は`bigint`の`GENERATED ALWAYS AS IDENTITY`、金額は`numeric(p, s)`にする。
DOMAIN、ENUM、生成列は使わず、JSONは自システムで解釈しないデータに限る。

## 対象

この規約は、モジュールが所有する業務テーブルのカラムに適用する。
Spring Modulithのイベント出版テーブルのように、フレームワークがスキーマを定めるテーブルには適用しない。

## 値の種類ごとの型

- **コード**：`varchar(n)`。商品コードのように値が数字だけでも文字列にする。
- **区分**：`varchar(n)`とし、NOT NULLにする。値が数字だけでも区分値はコードとして扱う。
- **絶対時刻**：`timestamptz`。扱いは[日時とタイムゾーンの規約](../datetime/timezone-conventions.md)に従う。
- **日付**：`date`。パーティションキーに使うときはNOT NULLにする。
- **年月**：`yyyy-MM`形式の`varchar(7)`。パーティションキーに使うときはNOT NULLにする。
- **数量**：`integer`または`bigint`。連番に対応する数量は`bigint`にする。既定値を0にしない。
- **連番**：`bigint`のIDENTITY列とし、NOT NULLにする。
- **係数**：`numeric(p, s)`。割引率や税率に使う。既定値を0にしない。
- **金額と計算結果**：`numeric(p, s)`。正確な値が必要な金額や使用量に使う。既定値を0にしない。
- **文字列**：桁数を指定した`varchar(n)`。
- **フラグ**：`boolean`とし、NOT NULL、既定値`false`にする。`boolean`の前に[真偽値の代替](postgresql-logical-design.md#真偽値の代替)を検討する。
- **UUID**：`uuid`。`varchar(36)`にしない。

## 使わない型

- **`char(n)`**：桁数に満たない値が空白で埋まり、比較が一致しなくなる。`varchar(n)`を使う。
- **`text`と桁数のない`varchar`**：システム間連携の定義と容量見積もりに桁数の上限が要る。`varchar(n)`を使う。
- **`serial`と`bigserial`**：SQL標準のIDENTITY列を使う。
- **`smallint`**：型の選択肢を減らすため、`integer`か`bigint`を使う。
- **`real`**：精度が6桁程度しかないため、浮動小数が必要なら`double precision`を使う。
- **`money`**：桁数と精度を指定した`numeric(p, s)`を使う。

`timestamp without time zone`と`time with time zone`は、[日時とタイムゾーンの規約](../datetime/timezone-conventions.md)が定める場合だけ使う。

## IDENTITY列

連番の主キーは`GENERATED ALWAYS AS IDENTITY`で定義し、`GENERATED BY DEFAULT`を使わない。
アプリケーションのINSERTではIDENTITY列を指定せず、`DEFAULT`キーワードと`OVERRIDING SYSTEM VALUE`も書かない。
changesetから生成されるDDLが`GENERATED ALWAYS`になっていることを確認する。

```sql
CREATE TABLE m_color (
    color_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    color_name VARCHAR(50) NOT NULL DEFAULT ''
);
```

## 文字列の既定値

文字列のカラムはNOT NULLにし、既定値を空文字`''`にする。
NULLを空文字へ変える処理は、カラムごとに書かず、Infrastructure層のデータアクセスで一律に行う。
空文字の比較には`= ''`と`<> ''`を使い、文字列のカラムに`IS NULL`を使わない。

空文字はNULLと異なり、ユニークインデックスで重複として扱われる。
ユニークインデックスを張る文字列のカラムでは、空文字が複数行に入らないことを確認する。

## JSONと配列

構造を持つデータは正規化して格納し、`json`、`jsonb`、配列の型を使わない。
次の場合に限り、`json`または`jsonb`を使ってよい。

- 外部のWeb APIの応答を、記録のためにそのまま保存する。
- システム間連携で、自システムでは解釈せずに受け渡す。

挿入の速さを優先するなら`json`、容量を抑えるなら`jsonb`を選ぶ。
JSONの構造の検証はアプリケーションでJSON Schemaなどを使って行い、CHECK制約で行わない。
カラムの`remarks`（カラムコメント）にJSON Schemaの場所を書く。
JSONの中の値で検索する必要が出たら、インデックスを張らず正規化する。
配列も同じ条件と方法で扱う。

## 大きなバイナリ

画像や文書のように大きくなりうるバイナリは、DBのラージオブジェクトに保存せず、オブジェクトストレージに保存してDBにはそのパスだけを持つ。
オブジェクトストレージへの書き込みはDBのトランザクションに含まれないため、失敗時のエラー処理と再試行を設計する。

## 生成列

生成列は使わない。
値の計算は業務要件に近く、式の変更に`ACCESS EXCLUSIVE`ロックと全行の書き換えが必要になるためである。
計算した値をカラムに持つかどうかは[導出属性](postgresql-logical-design.md#導出属性)の基準で決める。

## 独自型

- **DOMAIN**：使わない。定義の変更とDOMAINの解除がテーブルロックを伴い、値の検証はアプリケーションのリリースで変える方が容易である。
- **ENUM**：使わない。値の削除に型の作り直しと`ACCESS EXCLUSIVE`ロックが必要になる。値を削除しないと確定しているカラムに限り、理由をchangesetの`comment`とPull Requestに書き、レビューで合意してから使う。
- **ltreeと拡張機能の型**：使わない。性能または開発の効率に大きな利点がある場合に限り、ENUMと同じ手順で合意してから使う。

区分値は`varchar(n)`で持ち、値の検証はアプリケーションで行う。
