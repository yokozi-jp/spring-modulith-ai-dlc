# PostgreSQLのバージョンアップ

マイナーバージョンは四半期から半年に一度、定期的に手動で上げる。
メジャーバージョンは、使用中のバージョンのサポート終了が1年以内になった時点で上げる。
自動アップグレードは使わず、更新の種類ごとに決めた検証を行ってから適用する。

## 対象

この規約は、ステージングと本番のPostgreSQLに適用する。
ローカルとCIで使うPostgreSQLのコンテナイメージの更新は、[ADR-021](../adr/ADR-021-group-dependabot-minor-and-patch-updates.md)のDependabotの運用に従う。

PostgreSQLは、メジャーバージョンを年に一度、マイナーバージョンを3か月に一度公開する。
メジャーバージョンは公開から5年間、マイナーバージョンでサポートされる。

## 更新の頻度

- マイナーバージョンは、セキュリティ修正を取り込むため、四半期から半年に一度定期的に上げる。
- メジャーバージョンは、使用中のバージョンのサポート終了が1年以内になった時点で上げる。
- 特定のバージョンに固定して数年後にまとめて上げる運用はしない。

システムの計画には、メジャーバージョンアップの間隔（3年から5年など）、業務の閑散期に合わせた時期、移行先のバージョンを含める。
移行先は検証時点の最新バージョンを原則とし、拡張機能の対応などに課題があれば一つ前のバージョンにする。

## 適用の方法

マネージドサービスの自動マイナーバージョンアップグレードを無効にし、手動で適用する。
リリースノートで差分を確認して影響を調べる期間を確保し、適用のタイミングをチームで合意するためである。

## 更新の種類ごとの検証

- **メジャーバージョンアップ**：自動テスト、ステージング環境での動作確認、スロークエリの調査、拡張機能の動作確認を行い、メンテナンスの時間帯を確保する。
- **マイナーバージョンアップ**：自動テストとステージング環境での動作確認を行い、メンテナンスの時間帯を確保する。
- **パッチだけの更新**：自動テストを行う。

## メジャーバージョンアップの移行計画

メジャーバージョンアップでは、次の項目を含む移行計画を作ってから実施する。

1. 背景と目的。
2. 移行先のバージョン。
3. リリースノートの調査結果。
4. 影響の確認対象（DBスキーマと関数、DBアクセスライブラリ、アプリケーションのSQL、拡張機能）。
5. テストを行う環境。
6. テストの確認項目（機能の互換性、データの整合性、性能、リソースの使用量）。
7. 更新の手順。
8. 移行リハーサルの計画と振り返り。
9. 作業の日程とメンテナンスの時間帯。
10. 当日の実施スケジュール。
11. 実施後の監視項目と体制。
12. 切り戻しの計画。
