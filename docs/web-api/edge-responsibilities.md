# 入口とAPIの機能配置

レート制限、リクエストサイズの上限、低速な送信による攻撃への対策、応答の圧縮は、APIの前段にある入口に置く。
入口にはルーティングと横断的な制御だけを持たせ、業務ロジックやリクエストとレスポンスの変換を持たせない。
処理の打ち切りは呼び出し元のキャンセルを基本とし、非同期タスクには最長実行時間を決める。

## 入口の範囲

**入口**：ブラウザとバックエンドのあいだに置き、パスでSPAとAPIへ振り分けるリバースプロキシ、CDN、WAFの総称。
入口の構成とパスの振り分けは[ADR-014](../adr/ADR-014-use-same-origin-spa-security-boundary.md)に従う。

## 入口に持たせる機能

- **レート制限**：大量の呼び出しを遮断し、超過したら`429 Too Many Requests`と`Retry-After`ヘッダーを返す。
- **リクエストサイズの上限**：巨大なヘッダーと本文を拒否する。アプリケーションへ届いた超過は413を返す。
- **低速な送信への対策**：本文を少しずつ送り続けて接続を占有する攻撃（Slow DoS）を遮断する。
- **応答の圧縮**：JSONの応答をgzipで圧縮する。
- **攻撃文字列の検知**：SQLインジェクションやXSSの文字列を検知する。

攻撃文字列の検知は第二防御であり、アプリケーションでもSQLのパラメータをバインドし、HTMLへの出力をエスケープする。
認証と認可は入口に持たせず、[ADR-007](../adr/ADR-007-session-based-auth-with-oidc-pkce.md)に従いアプリケーションで行う。
応答のキャッシュは[APIのリクエストヘッダーとレスポンスヘッダー](headers.md)の`Cache-Control`に従う。

## 入口に持たせない機能

入口には、リクエストとレスポンスの変換、複数APIの集約、業務ロジックを持たせない。
機能の実装先が複数あると、テストでの品質保証と変更時の影響調査が難しくなるためである。

## 利用者単位のレート制限

利用者やAPIアクセスキーの単位でレート制限が必要になり、入口で実現できない場合だけ、アプリケーションで実装する。
その場合は、DBではなくキャッシュサーバーで回数を数え、制限を超えたら入口と同じく429と`Retry-After`を返す。

## タイムアウト

- 入口のタイムアウトは、アプリケーションの処理時間の上限より短くしない。
- 画面から呼ばれるAPIの処理を打ち切るかは、利用者への応答の要件に合わせて呼び出し元が判断し、キャンセルする。
- 非同期APIで作成したタスクはキャンセルする利用者がいないため、あらかじめ決めた最長実行時間で打ち切る。
- 応答時間の要件を超えたリクエストは、トレースIDで後から調査できるようにする。

アプリケーションから外部への呼び出しのタイムアウトは[ADR-019](../adr/ADR-019-define-resilience-and-capacity-guardrails.md)に従う。
