# HTTPメソッドの使い分け

参照はGET、作成はPOST、更新はPUTを基本とし、PATCHは部分更新が必要な場合だけJSON Merge Patchで使う。
GETに本文を付けず、検索条件をURLで表せない場合だけPOSTで検索する。
更新系の応答本文はフロントエンドが必要とする場合だけ返し、DELETEは204を返す。

## 使うメソッド

業務APIでは次のメソッドを使い、CONNECT、OPTIONS、TRACEを業務の操作に割り当てない。

- **GET、HEAD**：参照に使う。安全かつ冪等である。
- **POST**：作成、非同期処理の受付、カスタムメソッド、URLで表せない検索に使う。冪等ではない。
- **PUT**：既存リソースの全体の置き換えに使う。冪等である。
- **PATCH**：部分更新に使う。冪等とは限らない。
- **DELETE**：削除に使う。冪等である。

## 検索にPOSTを使う条件

参照にはGETを使う。
次のいずれかに当てはまる場合に限り、検索条件をリクエストボディに入れてPOSTで検索する。

- 検索条件が入れ子になり、クエリパラメータで表しにくい。
- 一括検索のキーが多く、URLがTomcatの上限（既定8KB）を超えうる（[アプリより前に拒否される要求](edge-responsibilities.md#アプリより前に拒否される要求)）。
- 個人情報や秘密情報のように、URLやログに出してはいけない値を条件に含む。

POSTで検索した場合も、成功時のステータスコードはGETと同じ200にする。
GETのリクエストボディに検索条件を入れない。
HTTP実装によって本文が無視または拒否されるためである。

## QUERY

本文を持つ安全で冪等な検索のメソッドとして、RFC 10008が`QUERY`を定めた。
業務のAPIでは使わない。
Spring Framework 7.1.0より前は対応せず、使う理由のあるエンドポイントもない。
`QUERY`を使うエンドポイントを作るときは、次を確かめる。

- Spring Frameworkの版（7.1.0以降）。
- Spring Securityの`HttpFirewall`が受け付けるメソッド。今は受け付けず、400になる。
- CSRFトークンの検査の対象。
- 前段のCDNとリバースプロキシが`QUERY`を通すか。
- OpenAPIとOrvalの生成物が`QUERY`を扱えるか。

## 作成

リソースの作成にはPOSTを使い、PUTでリソースを新規作成しない。
PUTで作成すると、作成時に払い出すはずの識別子をクライアントが指定する設計になるためである。
識別子を払い出すだけのAPIも作らない。

作成に成功したら201を返し、作成したリソースのURIを`Location`に入れる（RFC 9110 15.3.2）。
理由は[ADR-050](../adr/ADR-050-define-backend-class-roles-and-naming.md)に示す。

## 更新

リソースの更新にはPUTを使う。
次の場合に限り、PATCHを使う。

- クライアントがリソースの全量を持たない。
- 大きなテキスト項目を持つなど、通信量を減らす必要がある。

PATCHのリクエストボディはJSON Merge Patch（RFC 7396）にし、`Content-Type: application/merge-patch+json`で送る。
フレームワークの都合で対応できない場合だけ`application/json`も受け付ける。
JSON Merge Patchでは`null`が項目の削除を表す。
応答で値のない項目を`null`ではなく省略で表す規約は、[レスポンスボディ](response-body.md)に従う。

JSON Merge Patchは配列の一部の要素だけを更新できない。
このような部分更新が必要になったら、PATCHにこだわらずPUTのエンドポイントを設ける。

企業ネットワークの中間機器がPATCHを遮断する利用者を対象にする場合に限り、POSTと`X-HTTP-Method-Override: PATCH`で代用する。

## 更新系の応答本文

POST、PUT、PATCHの応答本文にリソースを含めるのは、フロントエンドがその値を使う場合だけにする。
更新後に画面が改めてGETする場合は、リソースを返さない。

DELETEは204を返す。
削除した子リソースの件数のような情報を返すのは、フロントエンドが削除後にその情報を使う場合だけにする。
削除前の確認画面で件数を見せるだけなら、GETで取得できるようにする。

## 再試行への備え

POSTとPATCHも、タイムアウト後の再試行で処理が重複しないよう、一意制約などを使ってできる限り冪等に設計する。
そのうえで、更新の操作には`Idempotency-Key`を求め、成功して応答を失った要求の再送に1回目と同じ応答を返す。
決定の理由は[ADR-126](../adr/ADR-126-require-idempotency-key-on-all-non-safe-business-apis.md)にある。

- **対象**：テナントを選んだ後の業務のAPIのうち、GETとHEAD以外のすべての操作（POST、PUT、PATCH、DELETE）。
  OpenAPIの契約の外の経路（ログインとログアウト）と、テナントを選ぶ前の操作（テナントの選択）は対象にしない。
- **形式**：引用符で囲んだUUIDを1行で送る（`Idempotency-Key: "<UUID>"`）。
  キーはクライアントが利用者の操作ごとに採番し、キーを払い出すAPIを作らない。
- **記録の分け方**：テナント、利用者、キーの組ごとに記録する。別のテナントと別の利用者は、同じキーを使っても互いの記録に当たらない。
- **保存期間**：成功した要求のキーと結果を、受け付けてから24時間保存する。
  期限を過ぎたキーは新しいキーとして扱い、定期のジョブが記録を消す（[テーブルごとの保持期限と個人データの有無の一覧](../database/table-retention-and-personal-data.md#改廃の方法)）。
- **再送**：保存期間の中で同じキーと同じ内容の要求が届いたら、処理をもう一度実行せず、1回目と同じ応答（201と`Location`、204など）を返す。
  認可は再送でも毎回確かめる。
  内容は、操作と、パス、クエリ、本文の値である。どれかが違う要求は400になり、同じキーの要求の処理中は409になる（[HTTPステータスコードの選択](status-codes.md#前提)）。
  2xx以外で終わった要求のキーは残さないので、誤りを直して同じキーで送ると処理される。
- **クライアントの再試行**：同じキーで自動で再試行するのは、ネットワークの失敗、5xx、408、429、処理中の409だけにする。
  利用者が失敗の通知を見て操作し直すときは、新しいキーを採る。
