# 設計判断の進め方

課題に対しては、実現手段より先にあるべき姿を書き、現状との差を示してから手段を選ぶ。
あるべき姿に届かない場合は、段階、次善案、何もしない案を比べて着地点を決める。
案が決まらないときは、選択肢を出し尽くしてから複数の観点で比べ、捨てた案と理由を記録する。

## 対象

この規約は、設計上の課題、仕様変更、障害対応のうち、アーキテクチャや複数モジュールに影響する対応方針を決めるときに適用する。
一つのモジュールの内部で閉じる日常的な実装選択には適用しない。

## あるべき姿から考える

1. 課題に対して、現在の制約を外した場合のあるべき姿を書く。
2. あるべき姿と現状の差を書き出す。
3. 差を埋める手段を、優先度と実現性で比べて選ぶ。

目の前の事象だけを見て、実現手段から議論を始めない。
全体への影響を見ずに手段を選ぶと、課題ごとに方針の異なる対応が積み重なり、アーキテクチャの一貫性が崩れるためである。

## 着地点の決め方

あるべき姿を書いたら、差を埋める作業を誰がいつまでに行うかまで見積もる。
次の問いに答えられない案は、そのまま採用しない。

- チームの誰が実施できるか。
- 費用に見合う効果があるか。
- 今やるべき優先度か。

全部を一度に実施できない場合は、次の観点で着地点を決める。

- **段階**：今回どこまで対応し、残りをいつ着手するかを分けて決める。
- **次善案**：あるべき姿より劣るが現状より良くなる案を採るか、何もしないかを決める。次善案の実現コストが高ければ採用しない。
- **検討コスト**：着地点の検討に時間をかけすぎない。関係者を集めて早く決める。

## 選択肢の発散と収束

案が一つに決まらないときは、最初から一つの正解を探さず、選択肢を増やしてから絞る。

- 採用案のほかに、出せるだけの代替案を出す。
- 案は、コスト、性能、保守性、チームのスキルなど複数の観点で比べる。
- 一つに絞りきれない場合は、二つか三つの候補に絞って議論の叩き台にする。

選択肢を機械的に増やすときは、次の方法を使ってよい。

- **SCAMPER**：有力な案に、代用する、組み合わせる、他から適応する、拡大または縮小する、別の用途に使う、取り除く、逆転または再編成する、の七つの問いを当てて別案を作る方法。
- **ロジックツリー**：「状態をどこに持つか」のような問いに対し、クライアント、BFF、バックエンド、DB のように置き場所ごとに案を分け、検討の抜けを探す方法。

## 判断の記録

- [ADR の運用ルール](../adr/conventions.md)の作成基準に当たる判断は、Proposed の ADR を起こす。
- 検討して捨てた案は、ADR の Alternatives Considered に捨てた理由とともに書く。
- 段階に分けて残した対応は Issue にし、着手の時期を書く。Issue の操作は[Issue tracker](../agents/issue-tracker.md)に従う。
