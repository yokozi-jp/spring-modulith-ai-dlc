# 設定と規約の使い分け

フレームワークの標準の規約で足りる箇所は規約に任せ、設定を書かない。
規約から外れる動作は、コードか設定ファイルに明示的に書き、暗黙の独自ルールにしない。
独自のルールを作った場合は docs の規約に書き、ツールで検出できるものは検査で強制する。

## 用語

- **明示的な設定**：振る舞いをコードや設定ファイルで宣言する方式。
- **設定より規約**（CoC）：フレームワークが定める標準のルールに従うことで、設定を省く方式。

## 使い分け

- 長く保守し、メンバーが入れ替わるシステムでは、規約と明示的な設定を組み合わせる。このリポジトリはこの形をとる。
- Spring Boot の自動構成は規約として使い、既定を変える場合だけ Bean 定義や設定値で明示する。
- 規約から外れる箇所では、規約に逆らう回避コードを書かず、フレームワークが用意した設定や拡張点で明示する。
- 明示的な設定が増えて業務ロジックが読みにくくなった場合は、フレームワークの既定に戻せないかを先に検討する。

設定値の置き場所と注入方法は[ADR-008](../adr/ADR-008-single-application-yaml-external-config.md)に従う。

## 暗黙の独自ルールを残さない

- 標準の規約から外れ、しかもコードにも設定にも書かれていないルールを作らない。新規参加者とコーディングエージェントは、公開された規約と書かれた設定を読めるが、プロジェクト固有の暗黙のルールは推測できないためである。
- 独自のルールを作った場合は、該当する領域の docs に書く。
- ツールで検出できるルールは、検査に組み込む（[アーキテクチャの制約の自動検証](architecture-fitness-functions.md)）。
