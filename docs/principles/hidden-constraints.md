# 明文化されていない要件と制約の洗い出し

設計を始める前に、明文化された機能要件と非機能要件に加えて、まだ言語化されていない要件と制約を観点表で洗い出す。
洗い出した制約は、検討する選択肢を絞る前提として明文化する。
業務上の Must と確認できない項目は作り込まず、緩めた条件か後から変えられる設計にとどめる。

## 対象

この規約は、新しいシステム、新しい機能モジュール、外部システムとの新しい連携の設計を始めるときに適用する。
非機能要件を定義する手順は[非機能要件定義の進め方](../nfr/definition-process.md)に従い、この文書は設計者が追加で確かめる観点だけを定める。

## 確かめる観点

初期に表へ出にくい要件を、次の観点で関係者に確かめる。

### 事業環境の変化

- **利用者の増加**：数年先（目安は5年後）の利用者数、同時接続数、アクセス数。予測できなければ仮説の値を置いて合意する。
- **海外展開**：将来の海外展開の有無。ある場合は多言語対応、マルチテナント、各国の法令への対応を確かめる。
- **組織変更**：部署や関連会社の再編の有無と、再編のときにシステムが何を変える必要があるか。

### 既存資産と外部依存

- **移行**：既存システムからの業務とデータの移行要件。データモデルの大幅な変更や DB の分割をしても現実的に移行できるか。
- **既存システムとの連携**：相手システムの技術的な制約。たとえば相手が即時応答に対応しない場合のデータ整合の保ち方。
- **依存先の継続性**：利用する外部サービスや OSS がサポート終了を迎えるリスク。

### 運用とコスト

- **予算**：計画上の上限予算と、構築中のコスト上振れの許容範囲。
- **事業継続と災害復旧**：バックアップと災害復旧の要求水準。システム単体ではなく全社の計画に合わせる。
- **運用体制**：引き継ぎ先の体制とスキル。運用担当が扱える技術か、手順書が要るか。

### 具体化の参照先

確かめた内容は、次の文書に従って具体化する。

- 多言語対応は[ADR-016](../adr/ADR-016-localize-api-and-spa-messages.md)に従う。
- マルチテナントは[PostgreSQLのマルチテナント設計](../database/postgresql-multitenancy.md)に従う。
- 災害復旧は[災害対策と事業継続の要件](../nfr/disaster-recovery.md)に従う。
- 既存システムとの連携は[システム間連携の方式選択](../integration/interface-integration-patterns.md)に従う。

観点の抜けを点検するフレームワークは[非機能要件のフレームワークと用語](../nfr/frameworks.md)から選ぶ。

## 制約の明文化

- 洗い出した制約（「特定ベンダーへのロックインを避ける」など）は、検討する選択肢を絞る前提として設計文書に書く。
- 関係者が暗黙に持つ方針も制約として書き出し、合意する。制約がないと選択肢が絞れず、決定が遅れるためである。
- 技術選定に関わる制約は、既存の ADR と矛盾しないかを [ADR インデックス](../adr/index.md) で確かめる。

## どこまで設計に入れるか

- 観点表やフレームワークの項目を埋めること自体を目的にしない。
- 業務上の Must と確認できた項目だけを、設計で作り込む前提にする。
- Must ではない項目は、緩めた条件で合意するか、後から変えられる設計にとどめる。
- 「念のため」を理由に水準を上げない。過剰品質の判断は[非機能要件定義の進め方](../nfr/definition-process.md)の判断の原則に従う。
