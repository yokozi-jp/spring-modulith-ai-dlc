# 薄いラッパーの判断基準

外部ライブラリは、原則として独自のラッパーを被せず直接呼ぶ。
破壊的変更が多いと分かっている外部依存か、機能が増えることが確実な箇所に限り、ラッパーを検討する。
ラッパーを導入する場合は、規約への明記、生の API の呼び出しを禁じる検査、既存コードの一斉置換を同時に行う。

## 用語

- **薄いラッパー**：外部ライブラリや外部 API の呼び出しを、変換や判断をほとんど加えずに独自のインタフェースで包んだモジュール。
- **浅いモジュール**：提供する機能に比べて、独自のインタフェースを学ぶコストが大きいモジュール。薄いラッパーはこれに当たる。

モジュールの深さの語彙は[深いモジュールを設計するスキルの日本語リファレンス](../agents/matt-pocock-skills/codebase-design.md)にある。

## 対象

この規約は、外部ライブラリや外部 API を包む共通関数、クラス、コンポーネントをプロジェクト内に作るときに適用する。
次は対象外とする。

- オニオンアーキテクチャの層の境界にある Infrastructure の Adapter と Application の `port`。置き方は[バックエンドの層の責務](../backend/layers.md)に従う。
- `components/ui` に置く UI primitive。置き方は[フロントエンドのUIとスタイル](../frontend/ui-and-style.md)に従う。
- 専門のチームが組織横断で保守し、文書と採用実績がそろった共通フレームワーク。

## 直接呼ぶもの

- 入力検証のライブラリ（Zod など、[ADR-023](../adr/ADR-023-adopt-tanstack-form-and-zod.md)）と UI ライブラリは直接呼ぶ。型と機能が複雑で、包むと抽象が漏れるためである。
- TanStack Table に専用の共通ラッパーを作らない（[ADR-028](../adr/ADR-028-adopt-tanstack-table.md)）。
- 生の API を使わせると開発者が間違えやすいという懸念には、ラッパーではなく次で対処する。
  - docs の規約とサンプルコードを用意する。
  - 第三者が定めた標準仕様や、ライブラリ側の拡張点（フック、ミドルウェア、設定）があれば、それを使う。
- ライブラリの版上げで呼び出し元の変更が避けられない場合は、ラッパーで隠さず、呼び出し元を書き直す。

## ラッパーを検討してよい場合

- 破壊的変更が多いと分かっている外部 API など、変更の影響を一箇所で止められる見込みがある場合。
- 最初は薄くても、分岐や機能が増えることが確実な場合（開発環境だけログインを省く分岐が入る認証処理など）。

判断では、そのラッパーが独自のインタフェースを学ぶコストを上回る機能を提供するかを確かめる。
呼び出しを横流しするだけなら作らない。

## 導入する場合のルール

1. そのラッパーを使う処理と使い方を docs の規約に書き、サンプルコードを示す。
2. 生の API の直接呼び出しを ArchUnit や Lint の規則で禁じ、CI で検出する。
3. 既存コードの生の API の呼び出しを、同じ変更でラッパーへ置き換える。

生の API とラッパーの呼び出しを混在させない。
