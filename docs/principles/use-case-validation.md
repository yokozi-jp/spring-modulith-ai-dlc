# ユースケースによるアーキテクチャの机上検証

最も確度の高い正常系のユースケースだけで、仮のアーキテクチャを描く。
異常系、エッジケース、将来の拡張などのユースケースを別に洗い出し、テストデータとして仮のアーキテクチャを机上で検証する。
成り立たないユースケースがあれば、アーキテクチャを直すか、ユースケースを見直すかスコープから外す。

## 対象

要件とアーキテクチャのどちらも固まっていない段階で、システム全体の構造（同期と非同期の境界、構成要素の分割、外部連携の方式など）を決めるときに適用する。
アプリケーション内部の構造が既存の規約で決まっていても、システム全体の構造は要件で変わるため、この検証を省かない。

## 手順

1. 最も確度の高い正常系のユースケースだけを入力にして、アーキテクチャの骨格を描く。細部は決めず、データの流れと構成要素の責務の分担を決める。
2. 異常系、エッジケース、大量処理、将来の拡張のユースケースを一覧にする。
3. 一覧の各ユースケースについて、骨格のままで無理な依存や非機能のボトルネックが生じずに成り立つかを机上で確かめる。
4. 成り立たない場合は、骨格を直すか、ユースケースを見直す。骨格とまったく合わないユースケースは、初期リリースのスコープから外すかを関係者と議論する。
5. 一覧のユースケースがすべて成り立つか、スコープから外れるまで、3と4を繰り返す。

## 注意点

- 確度の低いユースケースは仮説として扱い、それに合わせて骨格を作り込まない。発生が確定したユースケースだけを、作り込む前提にする。
- 初期のユースケースだけに合わせて骨格を固めない。ユースケースが変わったときに成り立たなくなるためである。
- 検証で決めた構造のうち [ADR の運用ルール](../adr/conventions.md)の作成基準に当たるものは、ADR に記録する。
