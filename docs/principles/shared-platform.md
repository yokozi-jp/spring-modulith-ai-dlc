# 共通基盤を作るかの判断と範囲の決め方

共通基盤は、多数の利用者の相乗りが確実な場合か、セキュリティやコンプライアンスを仕組みで強制する必要がある場合に限って作る。
それ以外は、各システムでの個別実装か、クラウドや SaaS の直接利用を選ぶ。
作る場合は提供価値とやらないことを先に書き、利用者の要望はその範囲に照らして受けるか断るかを決める。

## 用語

- **共通基盤**：認証、データ連携、ログ収集、CI と CD のように、複数のシステムやモジュールが共通に使う仕組み。

## 作るかの判断

基盤化を検討する動機ごとに、次のように判断する。

- **重複投資の排除**：構築の重複は防げるが、全利用者が依存する単一障害点になり、高い可用性と運用体制が要る。相乗りする利用者が少ない見込みなら、重複を許して各システムで作る。
- **セキュリティと統制の強制**：全社で必達のルール（共通認証、監査ログの収集など）は、基盤で強制してよい。利用者の負担が増えるため、利用方法の文書と導入の手順をそろえる。
- **開発の手間の解消**：クラウドや SaaS の機能を少し使いやすく包むだけの基盤は作らず、クラウドや SaaS を直接使う。

基盤化を検討してよいのは、次のどちらかを満たす場合に限る。

- 多数（目安は10以上）の利用者の相乗りが確実で、運用コストを上回る規模の効果が見込める。
- セキュリティやコンプライアンスの観点で、仕組みによる強制が要る。

このリポジトリ内で機能モジュールをまたぐ共通コードを作る場合は、バックエンドは[バックエンドアーキテクチャ](../backend/architecture.md)の全体設定の節に、フロントエンドは[フロントエンドアーキテクチャ](../frontend/architecture.md)の共有コードの節に従う。

## 提供価値とやらないこと

1. 統制や投資効率の要件を、利用者の手間が減る形の提供価値に言い換えて一文で書く。たとえば「監査ログを必ず送る」ではなく「このライブラリを組み込めば監査要件を意識せずに済む」と書く。
2. 提供価値から外れるもの（特定の利用者の業務ロジックの変換、クラウドの設定の単純な包み直しなど）を、やらないこととして書く。
3. 範囲の境界にある要望を受けたら、次の基準で判断し、提供価値とやらないことの記述を更新する。
   - 特定の利用者だけに依存し、汎用性を損なう要望は断る。
   - 他の利用者にも効く課題の解決なら、抽象化して基盤に取り込む。
   - 全体のために受ける特定の要望は、基盤の本体ではなく付属機能として切り離して提供する。

## 基盤の作り方

- 要望をそのまま機能にせず、課題の原因を分析し、汎用の機能で解けないかを先に検討する。
- 利用者の内部事情を知らずに済む標準のインタフェースを提供し、標準の形式で受けて処理する。
- 利用者が基盤の担当者を介さずに設定や変更をできるセルフサービスの仕組みを、最初から用意する。
- 複数の利用者が依存するため、可用性の目標と、更新時に利用者を止めない手順を決める。可用性の定め方は[可用性要件の定め方](../nfr/availability-requirements.md)に従う。
- 提供価値と範囲は、[ユースケースによるアーキテクチャの机上検証](use-case-validation.md)の手順で検証する。
