# 設計の作り込みの程度と段階的な再構築

設計は、現在の要件を満たす最小の構成から始め、将来の変化への備えは根拠を説明できる箇所だけに入れる。
最終形を最初から作らず、作り替えを前提にして、再構築する箇所ときっかけを先に書いておく。
再構築ポイントを書くことで、今やらないことを明示して合意する。

## 小さく始める

- 迷ったら、構成要素が少なく単純な案を選ぶ。
- 将来の変化に備える仕組み（分散、抽象化、汎用化）は、その変化が起きる根拠を説明できる場合だけ入れる。
- 目先の要件だけに合わせて、変更の入口を塞がない。モジュールの境界と依存方向は最初から守る。

## サービスの分割

このリポジトリは、境界を検証できるモジュラーモノリスから始める（[ADR-001](../adr/ADR-001-adopt-spring-modulith-modular-monolith.md)）。
モジュールの分け方と依存は[バックエンドアーキテクチャ](../backend/architecture.md)に従う。
個別サービスへの切り出しは、独立したスケールやデプロイの要件が実際に生じてから ADR で決める。

## 抽象化を入れる箇所

- 抽象化は、変更や差し替えが見込まれる不安定な箇所に限って入れる。
- 層の分け方は[ADR-002](../adr/ADR-002-package-by-feature-onion-architecture.md)と[バックエンドの層の責務](../backend/layers.md)に従い、それ以上の抽象を先回りして作らない。
- 外部ライブラリを独自のインタフェースで包むかは[薄いラッパーの判断基準](thin-wrappers.md)に従う。

## 段階的な再構築

最初から完成形を作らず、利用状況と事業の段階に応じて作り替える方針をとる。

- 作り替えを前提にすることを、関係者と事前に合意する。
- 将来作り替える箇所、そのきっかけになる指標（利用者数、データ量など）、作り替えの影響範囲を設計文書に書く。たとえば「データ量が一定を超えるまでは単一の DB のスケールアップで対応し、超えたらパーティションの導入を検討する」と書く（[PostgreSQLのパーティションと改廃](../database/postgresql-partitioning-and-retention.md)）。
- 再構築ポイントより先への備えは、今は作らないことを明示して合意する。
- ADR に関わる再構築ポイントは、その ADR の Consequences に書く。
