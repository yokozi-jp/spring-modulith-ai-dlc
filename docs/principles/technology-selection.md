# 技術選定の原則

揮発性の高い領域は主流の技術を薄く使い、重要な基盤領域は業界標準で実績のある技術を使い、競争優位を担う業務領域だけを自ら設計する。
標準から外れる独自の構成は、業務上の課題を解く理由を説明できる場合に限り、ADR に理由を書いて採用する。
新しい技術に挑戦する箇所は、システムの中で少数に絞る。

## 領域ごとの選び方

- **揮発性の高い領域**（UI ライブラリ、CI と CD のツールなど）：主流の技術を選び、独自の作り込みをせず薄く使う。数年で入れ替わる前提で、入れ替えやすさを優先する。
- **重要な基盤領域**（認証、DB など）：業界標準で実績のある技術を選ぶ。独自の工夫や再発明をしない。
- **競争優位を担う業務領域**（ビジネスロジック、独自の提供価値）：既存の型に当てはめず、ドメインに合わせて自ら設計する。

このリポジトリの既存の技術選定は [ADR インデックス](../adr/index.md) にある。
既存の選定から外れる技術を使う場合は、[ADR の運用ルール](../adr/conventions.md)に従って ADR を起こす。

## 独自の構成を採るかの判断

独自のアーキテクチャやルールを提案するときは、次の三つのどれに当たるかを判断する。

- **採用してよい**：業務上の競争優位を得るために標準を外れる場合（特殊なマルチテナント要件、極端に低いレイテンシ、特殊なハードウェアとの連携など）。「なぜ必要か」に業務課題で答えられる。
- **採用しない**：新しい技術を試したい、経歴に書きたいといった個人の動機による場合。
- **慎重に判断する**：開発生産性や独立したデプロイなど、技術上の課題を理由にする場合（標準のアーキテクチャの独自改良版を作る、チームごとに複数のサービスを作るなど）。公式の文書がなく、新規参加者とコーディングエージェントの学習コストと運用の負荷が増える。採用するなら、標準の方式で解けない理由を ADR に書く。

## 驚きを最小にする

- 新規参加者が「なぜこの構成なのか」と迷う一風変わった構成を避け、広く知られた構成を選ぶ。
- 標準から外れた箇所は、コード、設定、docs のいずれかに明示する（[設定と規約の使い分け](configuration-and-convention.md)）。

## 新しい技術に挑戦する箇所

- リスクを取って新しい技術を使う箇所は、システムの中で少数に限る。
- ある領域で新しい技術を選んだら、他の領域は実績のある技術にする。
- 競争優位に直結しない足回りの部分では、新しい技術に挑戦しない。
