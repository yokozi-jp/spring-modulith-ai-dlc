# 送るメールの形と宛先

1 通のメールの宛先は TO の 1 人にし、本文はプレーンテキストにする。
本文に秘密を書かず、ファイルを添付せず、サービスの画面へのリンクにする。
取引に伴う連絡のメールに広告を混ぜず、From の表示名は「サービス名と送る目的」にしてドメインとそろえる。

## 宛先

- 1 通の宛先は TO の 1 人にし、CC と BCC を使わない。
  宛先を並べると受信者どうしにアドレスが見え、CC を使うと誰が対応するのかが曖昧になるためである。
- 複数の人に同じ内容を知らせるときは、宛先ごとに 1 通ずつ送る。

## 本文に書かない情報

- パスワード、トークン、本人確認が要る情報を本文に書かない。
- 利用者に見せる情報は、サービスの画面へのリンクを本文に書き、ログインした後の画面で表示する。
- 画面へのリンクには、知るだけで操作できる値（秘密のトークン）を載せない。
  リンクの先の操作は、ログインした利用者に許すかをサーバーで確かめてから行う。
  ファイルのダウンロードのリンクだけは例外とし、[添付](#添付)に従う。

## 添付

- ファイルを添付しない。
  添付は送った後に取り消せず、迷惑メールの判定を厳しくされやすいためである。
- ファイルを渡すときは、期限のあるダウンロードのリンクを本文に書く。
  ダウンロードの URL は、知る人なら誰でもファイルを取れる bearer URL になる。
  URL は推測できない値にし、短い期限を付ける。
  期限は 24 時間（原文が例に挙げる値）を目安にし、ファイルの性質に合わせて決める。
- 機密性の高いファイルは、URL を知るだけで取れる形にせず、ダウンロードの前に利用者に再認証を求める。

## 広告

- 取引に伴う連絡のメールに、広告や宣伝を書き足さない。
  契約の成立の確認や発送の通知のような取引に伴う事務連絡は特定電子メール法のオプトインの規制の対象外だが、広告を書き足すと別に同意が要る場合があるためである。
- 新機能の案内のように、取引に伴う事務連絡に当たるかがはっきりしないメールは、送り始める前に法令を確かめる。

## From

- From の表示名は「サービス名と送る目的」にする（例：「サービス名 ご注文の確認」）。
  モバイルのメールアプリは長い表示名を途中で切るので、サービス名を先頭に置く。
- 表示名に日本語を使うときは、UTF-8 で符号化する。
- 表示名と From のアドレスのドメインをそろえ、表示名のサービスと関係のないドメインから送らない。
- From のドメインは、[送信ドメインの認証と評判](sending-domain.md)に従って認証したドメインにする。

## 本文の形式

- 本文はプレーンテキストにし、HTML メールを送らない。
- HTML メールを足すときは、この規約を改めてから足す。

## 送る回数の上限

- メールを送る機能に回数の上限が要るときは、[入口とAPIの機能配置](../web-api/edge-responsibilities.md#利用者単位のレート制限)に従って置き場所を決める。

- このリポジトリの規約に合わせて抜粋、再構成、改変している。取り込みの方針は [ADR-040](../adr/ADR-040-import-future-architecture-guidelines.md) に従う。
- 原文は、電子帳簿保存法の保存のために BCC を使うことを認める。
  この規約は BCC を使わない。
  保存が要るメールを送るときは、原文が BCC の代わりに挙げる方法（送った書類と検索に要る情報を DB やストレージに保存する）を検討する。
- 原文は、請求書や領収書のような定型の書類の直接の添付を認める。
  この規約は、どのファイルも添付しない。
  定型の書類を送る機能を足すときに、この規約を見直す。
- 原文は、HTML 版とプレーンテキスト版をマルチパートで送ることを勧める。
  この規約はプレーンテキストだけにする。
