# 依頼、報告、相談のメッセージ

件名と一文目で、対象と目的（確認、相談、報告）が分かるようにする。
報告は事実で止めず、書き手の見解と読み手に求める行動まで書く。
意思決定を求めるときは結論から、障害の報告やエスカレーションでは状況から書く。
問いには、問われた要素へ直接答える。

## 対象

この規約は、Issue、Pull Request、レビューコメント、チャット、エージェントの作業報告のように、読み手に判断や行動を求める文章に適用する。
記事、書籍原稿、ADR の論証の構成は [日本語技術文書の文章規範](japanese-tech-writing.md) に従う。
設計書や規約文書に何を書くかは [文書の目的と書く内容](technical-writing-document-content.md) に従う。

## 依頼にそろえる事項

依頼や確認を書く前に、読み手が期待する分量と粒度を見積もる。
チャットで長文を書かず、判断を求める文書で要点だけにしない。

依頼や確認には、次の事項をそろえる。

- **相手**：依頼する相手を名指しし、その相手が判断する権限を持つことを確かめる。
- **判断材料**：影響、リスク、作業量、代替案のように、相手が判断に使う材料を書く。材料がそろわなければ、先に裏取りをする。
- **範囲**：環境、画面、モジュールのように対象を特定し、Issue や文書の URL を添える。
- **期限**：書き手が希望する期限と、超えると業務に影響する最遅の期限を分けて書く。
- **求める行動**：共有、選択、承認のどれを求めるかを書く。

書き上げたら、読み手の立場で「それで何をすればよいか」に答えられるかを確かめる。

## 事実、解釈、見解

報告は、次の三つを区別して書く。

- **事実**：観測した状況や調査の結果。
- **解釈**：事実から導いた課題や見通し。
- **見解**：取るべき行動の提案。

報告は事実と解釈で止めず、見解まで書く。
見解を出せない場合や、共有だけが目的の場合は、一文目で共有だけであることを示す。
障害の記録や課題の更新には、担当者、期限、行動を組にした次の行動を書く。

## 件名と一文目

- 件名やタイトルだけで、対象と求める行動が分かるようにする。「〜について」で終わる件名にしない。
- Pull Request のタイトルは Conventional Commits の形式に従い、説明の部分で対象と変更を具体的に書く。
- 件名がない媒体では、一文目で目的（確認、相談、報告）を示す。
- 一文目は、前回の合意や既知の課題のように読み手がすでに知っている事柄から始め、未知の情報や依頼を唐突に置かない。
- 前提の補い方は読み手の知識に合わせる。専門外の読み手には前提の用語を説明し、専門家には背景を長く書かない。

## 間が空いたやり取り

数日ぶりに再開するスレッドや、長く開いている Issue を更新するときは、読み手が経緯を覚えていない前提で書く。
冒頭に、前回までの決定事項と残っている課題を短く書く。
個別の議論や報告が続くときは、全体の予定のうちどこにいるかを定期的に示す。

## 本論の順序

- 意思決定や承認を求めるときは、結論、理由、具体例の順に書く。作業の過程は書かないか、後ろに回す。
- 障害の報告やエスカレーションでは、状況、課題、実施した行動、結果の順に書き、相手と状況を同期してから依頼する。
- 結論を末尾で言い直さない。同じ主張の繰り返しは、文章規範の「冗長の排除」に反する。

## 問いへの答え方

- Yes か No で答えられる問いには、結果を先に書き、理由を後に書く。
- 「いつ」「だれが」「何を」と問われたら、その要素に直接答える。状況の説明だけで終えない。
- 答えが出ていなければ、未定であることと、回答できる時期を先に書く。

悪い例：「担当チームに確認中で、まだ返事がありません。後でリマインドします」。
良い例：「現時点では未定です。明日の定例の後に回答します」。

## 最小限の型

読み手に行動を促す、または許可を得るメッセージは、依頼事項と意図を組にする。
必要に応じて、期限と、達成できないときに連絡してほしい条件を加える。

```text
@reviewer 機能 A を参考に、機能 B の実装を進めてください。来週から機能 C に着手したいからです。
```
