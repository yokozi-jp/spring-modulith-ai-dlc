# 文書の目的と書く内容

文書は目次から書き始め、口頭の説明なしに単独で読めるようにする。
作業や挙動を並べず、文書の目的に合わせて、判断の理由、変更が解決する課題、読み手にとっての価値を書く。
方針を選んだ記述にはトレードオフを書き、詳細なデータは付録へ分ける。
規約文書では必須と推奨を区別し、良い例と悪い例を組で示す。

## 構成の決め方

- 短いメッセージを除き、本文の前に目次を作り、情報を伝える順序を決める。
- 文書は、口頭の説明を前提にせず、単独で内容が伝わるように書く。
- 定型のテンプレートがあれば使い、目的に合わない項目は省く。ADR は [ADR テンプレート](../adr/adr-template.md) に、Pull Request は `.github/PULL_REQUEST_TEMPLATE.md` に従う。

## 目的ごとに書く内容

コードや Issue を読めば分かる「何をしたか」を、日本語に訳し直すだけの記述にしない。
文書の目的に合わせて、次の内容を書く。

| 目的                           | 文書の例                 | 書く内容                                                                 |
| ------------------------------ | ------------------------ | ------------------------------------------------------------------------ |
| 設計の妥当性の評価と将来の保守 | 設計書                   | 設計上の判断、比較した案、その案を選んだ理由                             |
| レビューと承認                 | Pull Request、提案       | 現状の課題やリスクと、変更がそれをどう解決するか。実装の詳細は補足に回す |
| 成果と進捗の共有               | 進捗報告、リリースノート | 利用者や技術にもたらした価値。作業量は書かない                           |

定型の文書や繰り返し作る報告では、各項目の内容が文書の目的に合っているかを、書くたびに確かめる。

## トレードオフ

- 方針や技術を選んだ記述には、選んだ案の利点と欠点、比べた案、選んだ理由を書く。
- 比較の軸が複数あれば、表で対比する。
- 戻しにくい判断の背景、制約、不採用案は ADR に記録する（[ADR の運用ルール](../adr/conventions.md)）。
- ADR を起こさない議事録や報告でも、決定事項だけでなく、決定の背景、制約、不採用案を残す。

## 付録への分離

- 本文には、結論と、判断を決めた評価軸の要約だけを書く。
- 全項目の比較表、測定の生データ、検討の経緯は、付録または別の文書に分け、本文からリンクする。

## 規約文書

- 必ず守る制約と推奨を、区別できる語で書く。同じ文書群の中では語を統一する。
- 例外を認める場合は、例外を適用できる条件を書く。
- 抽象的なルールだけで終えず、良い例と悪い例を組で示す。
- 機能要件を定める文書では、正常系に加えて、異常系と境界値の振る舞いを定める。

悪い例：「エラーメッセージは分かりやすく書く」。
良い例：「エラーメッセージには利用者が次に取る行動を書く。悪い例は『入力が不正です』、良い例は『パスワードは 8 文字以上にしてください』」。
