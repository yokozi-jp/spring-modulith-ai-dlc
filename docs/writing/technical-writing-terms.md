# 用語と具体例の使い方

用語は読み手が普段使う語に合わせ、定義どおりに、一つの概念に一つの語で使う。
略語は初出で正式名称を併記し、多義語は修飾語で範囲を特定し、曖昧な語には含むものと含まないものを書く。
定性的な基準は数値で定め、数値で定められない基準と境界値には具体例を添える。
読み手と合意済みの概念や、漏れなく範囲を定める場面では、例示しない。

## 用語の選び方

- 読み手が普段使う語に合わせる。業務の利用者向けにはその組織で通じる語を、開発者向けには業界で標準の技術用語を使う。
- 用語は、仕様や公式文書の定義どおりに使う。たとえば、認証と認可を取り違えない。
- 一つの概念に一つの語を対応させ、文書の中で呼び方を変えない。この規則は、文章規範の「視点と語り」と同じである（[日本語技術文書の文章規範](japanese-tech-writing.md)）。
- ドメインの概念は、`GLOSSARY.md` で定義された語を使う（[ドメイン文書](../agents/domain.md)）。

## 略語

- 略語は、初出で正式名称を併記する。例：Architecture Decision Record（ADR）。
- API や URL のように広く定着した略語と、読み手全員が共有している略語は、併記を省いてよい。
- 略語は、正式名称より大幅に短くなり、文書に何度も出る場合に限って使う。

## 定義

- 文書に固有の語や、文脈で意味が変わる語は、文書の冒頭か使う節で「**用語**：説明」の形で定義する。
- プロジェクト全体で使うドメインの語は、文書ごとに定義せず `GLOSSARY.md` に置く。
- 要件や設計を定める文書では、読み手の業務知識に頼って行間を読ませない。多義語は冒頭で定義する。

## 多義語と曖昧な語

文脈で解釈が分かれる語は、修飾語を補うか、別の語で具体化する。
解釈が分かれやすい語には、次のものがある。

- **トランザクション**：業務の一連の処理か、DB トランザクションか。
- **サービス**：業務として提供する機能か、アプリケーションの層か、OS のプロセスか。
- **ユーザー**：画面を操作する利用者か、システムのアカウントか、テーブルの行か。
- **環境**：ハードウェアか、開発、検証、本番の区分か。

悪い例：「エラー時はトランザクションをロールバックする」。
良い例：「エラー時は DB トランザクションをロールバックし、外部 API で確定した操作は取り消しの API で戻す」。

- 時期や組織によって意味が揺れる語（バックログなど）は、その文書での意味を書く。
- 曖昧さが残る語は、含むものと含まないものを併記する。例：「この文書の性能は、画面操作の応答時間を指し、非同期処理の所要時間を含まない」。

## 具体例を使う場面

- 定性的な表現は、まず数値で定める。例：「大容量」ではなく「10 MB 以上」と書く。
- 数値で定められない基準は、代表例を添えて解釈の幅をそろえる。
- 境界値と異常系の振る舞いは、具体的な値で示す。期限日のような日時の境界には、判定に使うタイムゾーンも書く（[日時](../datetime/index.md)）。

## 具体例を控える場面

- 読み手と合意済みの概念に、一部だけを例示しない。例に挙げなかった項目が対象外だと読まれるためである。
- 範囲を漏れなく定める必要があるときは、例示しない。定義済みの文書への参照、全量の列挙、包含と除外の条件のいずれかで書く。
- 例を理解するのに説明が要る複雑な規則は、例示せず、決定表や状態遷移図にする（[箇条書きと表による構造化](technical-writing-structure.md)）。
